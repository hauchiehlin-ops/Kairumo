# 自己架一台協同中繼（跨網域協同）

> 這份文件回答一件事：**隊友不在同一個網路時，線上協同怎麼用。**

---

## 先講結論：協同從來沒有被綁在同一個 Wi-Fi 上

核心的位址檢查（`collab_check_server`）允許這些位址：

| 位址 | 允許 | 什麼時候用 |
|---|---|---|
| `wss://` 任何主機 | ✅ | **跨網域、跨國都可以** |
| `ws://127.0.0.1`、`ws://…​.local` | ✅ | 房主自己這台（App 會自動在這裡開中繼） |
| `ws://10.*`、`ws://172.16–31.*`、`ws://192.168.*` | ✅ | 同一個區域網路 |
| `ws://169.254.*` | ✅ | Wi-Fi Direct / 連結本地 |
| `ws://100.64–127.*` | ✅ | **Tailscale / ZeroTier 這類覆蓋網路** |
| `ws://` 公開 IP 或網域 | ❌ | 被擋下，訊息是「必須用 wss://」 |

**為什麼公開網路上一定要 TLS：** oplog 本身是端對端加密的（AES-256-GCM），
中繼看不到筆記內容。但**房號、成員名單與流量樣態是明文**，而明文 WebSocket
可以被中間人直接改寫或重導。這一條不打算放寬。

**為什麼我們不提供一台公用中繼：** 見 `architecture.md` §0 的 D5 ——
沒有後端伺服器是這個產品的定位，不是待辦。中繼永遠是使用者自己掌握的那一台。

---

## 三種取得 wss:// 位址的方式（由易到難）

### 方式一：虛擬區域網路（最省事，什麼都不用架）

所有裝置裝上 [Tailscale](https://tailscale.com/)（或 ZeroTier）並登入同一個帳號。
它們會拿到 `100.x.y.z` 的位址，彼此就像在同一個網段裡。

1. 房主照常按「開始多人協同」。
2. 房主查自己的 Tailscale 位址（Tailscale App 裡看得到，例如 `100.101.102.103`）。
3. 隊友把「協同伺服器位址」填成 `ws://100.101.102.103:9002`。

**不需要 TLS** —— 那是私有網段，而且 Tailscale 自己已經是加密通道。
這也是唯一一種「房主用平板也能當房主」的跨網域做法。

### 方式二：把房主那台的中繼打通道出去（不必伺服器、不必帳號）

房主那台如果是電腦，一行指令就夠：

```bash
cloudflared tunnel --url http://localhost:9002
```

它會印出一個 `https://xxxx.trycloudflare.com`。隊友把位址填成：

```
wss://xxxx.trycloudflare.com
```

（把 `https` 換成 `wss`，不用加連接埠。）關掉終端機通道就結束。

> 通道服務看得到的只有密文 —— 內容在離開裝置前就加密了。
> 但**房號與成員名單它看得到**，所以這是「臨時用」的做法，不是長期方案。

### 方式三：自己架一台（長期使用）

在任何有公開位址的機器上：

```bash
# 1. 編譯
cargo build --release -p padnote-relay

# 2. 執行（只監聽本機，TLS 交給前面那一層）
HOST=127.0.0.1 PORT=9002 ./target/release/padnote-relay
```

前面放一個會終結 TLS 的反向代理。Caddy 只要兩行：

```caddyfile
relay.example.com {
    reverse_proxy 127.0.0.1:9002
}
```

大家把「協同伺服器位址」填成 `wss://relay.example.com`。

nginx 的話記得加 WebSocket 的升級標頭：

```nginx
location / {
    proxy_pass http://127.0.0.1:9002;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;   # 心跳是 20 秒一次，但別讓長連線被砍
}
```

## 中繼實際上做了什麼

看 `crates/padnote-relay/`。它非常小，而且**刻意什麼都不記**：

- 房間是記憶體裡的一張表，最後一個人離開就消失。
- 每個房間留最近 200 則 oplog，給中途加入的人補資料用（`catchup`）。
- 它**不落盤、不記錄、不解密** —— 它連解不解得開都不知道，因為金鑰只在
  邀請連結的 `#key=` 那一段裡，從來沒有經過中繼。

所以「用別人的通道服務」在內容上是安全的；要連房號與成員都藏起來，
就用方式一或方式三。

## 常見狀況

**填了 `ws://` 的公開網域，被擋下來。**
那是設計行為，訊息是「這個中繼在公開網路上，必須用 wss://（加密）」。
換成 `wss://`，或改用方式一。

**連上了，但對方寫的東西看不到。**
加入時只貼了房號，沒有貼整條邀請連結 —— 金鑰在 `#key=` 那一段。
這時介面上會有一則橘色提醒。跟房主要完整連結，重新加入一次。

**連線一直斷。**
反向代理的讀取逾時太短。心跳是 20 秒一次，把 `proxy_read_timeout` 調到
一小時以上。
