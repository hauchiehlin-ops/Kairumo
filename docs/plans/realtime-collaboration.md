# 即時協同編輯：設計方案

> 目標三條：**即時**（別人的每一個動作，自己的畫面在一瞬間看得到）、
> **正確**（所有參與者最後看到的內容完全相同，與訊息到達的先後無關）、
> **不衝突**（同時動到同一個東西時，有確定、可預期的結果，而且盡量讓它根本不發生）。

## 1. 現況與問題（2026-10-15 檢查）

| # | 問題 | 實際後果 |
|---|---|---|
| 1 | 每一筆廣播的 Lamport 時鐘都是 `1`（`broadcastOplog(lamport: 1)` 的預設值，沒有人傳別的值） | 沒有任何先後依據 |
| 2 | 收到就套用，**以到達順序為準**；自己的修改則是先套用、後廣播 | A、B 同時改同一個物件：A 的畫面最後是 B 的版本、B 的畫面最後是 A 的版本 —— **兩邊永久不一致** |
| 3 | 筆跡以「整頁 `PKDrawing`」廣播（`drawing_replace`），收到的一方**整頁取代** | A、B 同時各畫一筆：彼此的那一筆互相蓋掉 —— **筆跡遺失** |
| 4 | 廣播散落在各個操作裡逐一手動呼叫 | 框選搬移、圖層順序、置於筆跡下、核取方塊、紙張樣板、**復原／重做**都沒有廣播 |
| 5 | 斷線補發以 `last_lamport` 過濾 | 時鐘全是 1，補發永遠是空的 |
| 6 | Android 加入房間後**不送也不收**任何內容操作（`onOplog` 沒有接上、沒有呼叫 `broadcastOplog`） | Android 實際上沒有即時協同 |
| 7 | 「對方正在編輯」只是視覺提示：沒有到期、沒有搶同一個物件時的裁決，框選與工具列不理它 | 仍可能兩人同時改同一個物件；對方當機後物件永遠鎖住 |
| 8 | 復原以整個物件的快照還原 | 會把別人之後對同一物件的修改一起蓋掉 |

## 2. 原則

1. **本機先套用，立刻廣播**（optimistic）：自己的操作不等網路，畫面零延遲；同一個事件迴圈內送出。
2. **收斂性**（Strong Eventual Consistency）：任兩台收到同一組操作，不論順序、不論重複，結果一定相同。
   做法是讓每一種資料的合併規則都**可交換、可結合、冪等**。
3. **先避免、再裁決**：會劇烈衝突的互動（拖曳、縮放、在同一個文字方塊打字）用「編輯租約」讓它根本不會同時發生；
   租約搶輸、網路分區之類漏網的情況，再由確定性的規則裁決。
4. **復原只退自己的動作**，而且不蓋掉別人之後的修改。
5. **中繼伺服器保持笨**：只轉送與暫存。正確性不依賴伺服器排序，三份中繼實作（Swift 區網、Android 區網、Rust 雲端）不必同步改版。

## 3. 時鐘

每一個操作帶 **Lamport 時戳 `(lamport, userId)`**：

- 送出時：`clock = clock + 1`，以新的 `clock` 為這個操作的時戳。
- 收到時：`clock = max(clock, 收到的 lamport)`。
- 全序比較：先比 `lamport`，相同再比 `userId`（字串比較）。

性質：若 B 改之前**已經看過** A 的修改，B 的時戳一定大於 A —— 「後改的贏」符合因果。
真正同時（彼此都沒看過對方）時，以 `userId` 決定，所有人算出同一個結果。

## 4. 各種資料的合併規則

### 4.1 物件（圖片、文字方塊、形狀、連接線、表格、連結、3D、錄音卡、討論圖釘、紙膠帶）

**欄位層級的「最後寫入者勝」（LWW register per field）**：

- 每個物件的每個欄位（`x`、`y`、`width`、`textColorHex`、`text`…）各自記一個時戳。
- 收到修改時，**只套用時戳比本機新的那些欄位**。
- 好處：A 搬動圖片（改 `x/y`）、B 同時改它的邊框色（改 `borderColorHex`）—— 兩個修改都保留，不是誰蓋掉誰。
- 新增 = 所有欄位一起寫入；刪除 = 寫入特殊欄位 `#deleted = true`。刪除與修改也走同一套比較：
  後發生的贏；同時發生時由 `userId` 決定。刪除後收到較舊的修改不會讓物件復活。

### 4.2 頁面層級的設定（圖層順序、置於筆跡下、核取方塊、紙張樣板）

核取方塊等頁面層級設定視為「虛擬物件」（`meta`），同樣走欄位 LWW；紙張是 `page` 物件的 `paper` 欄位。
堆疊順序與「置於筆跡下方」自協定 4 起是**每個物件自己的欄位**（`z`、`under`，見 §8.7）——
兩人同時調不同物件的層級時兩邊都保留（舊做法是整頁一份陣列，其中一人的會被蓋掉）。

### 4.3 筆跡

**只增不改的集合，加上墓碑**：

- 每一筆有一個穩定的 id（Apple 端以單筆的內容雜湊；Android 端用核心的 stroke id）。
- 操作只有兩種：`ink_add`（加入這幾筆）與 `ink_remove`（移除這幾個 id）。
- 加入與移除各自冪等、彼此可交換 —— 兩人同時畫，兩筆都在；A 擦掉自己的筆畫，不會動到 B 剛畫的。
- 套索搬動 = 移除舊的 id + 加入新的一筆。
- **不再整頁取代。** 舊版送來的 `drawing_replace` 改以「加入缺少的筆畫」處理，不刪除任何東西。

### 4.4 文字方塊的內容

- 有人在打字時，該方塊被**編輯租約**鎖住（見 §5），其他人只能看、不能同時打字，
  因此 `text` / `runs` 走欄位 LWW 就足夠正確。
- 打字的內容即時廣播（每次變更都送），對方看到的是逐字出現。
- 第三階段：改用核心既有的文字 CRDT（ADR-0004）傳遞字元層級的插入／刪除，
  讓兩人可以同時在同一個方塊打字。

## 5. 衝突避免：編輯租約

會持續一段時間、而且同時進行一定會亂掉的互動，開始前先取得**租約**：

| 互動 | 何時取得 | 何時釋放 |
|---|---|---|
| 選取物件（含拖曳、縮放、旋轉的把手） | 選取時 | 取消選取 |
| 就地編輯文字方塊 | 開始編輯時 | 結束編輯 |

框選不取得租約（在場資訊一次只帶一個選取 id），但**別人持有租約的物件不會被框到**；
框選的批次搬移與別人的修改同時發生時，由 §4 的 LWW 保證一致。

規則：

1. 租約隨「在場資訊」（presence）廣播，**每秒續約**；**5 秒**沒有續約即視為失效
   （對方當機、斷線，物件不會永遠鎖住）。
2. 物件被別人持有時：顯示對方的顏色外框與名字；本機不能選取、拖曳、編輯，
   也不會被框選或工具列改到；點它會提示「XX 正在編輯」。
3. **同時搶同一個物件**（兩人在同一瞬間選取）：雙方都會收到對方的租約，
   以**使用者 id 較小者**為準 —— 每一台都算得出同一個答案，不需要額外的訊息；
   搶輸的一方自動取消選取並看到「XX 正在編輯」。
   （不用時戳：Rust 中繼以型別解析在場資訊，額外的欄位會被丟掉；用 id 不必改中繼。）
4. 租約是體驗層的保護；即使漏網（例如網路分區時兩邊都以為自己拿到），
   §4 的 LWW 仍保證最後一致。
5. 選取 id 一律以**正規形式**比對（`stableBlockId`，打字的 `text:` 前綴保留）：Apple 的附件 id
   是大寫 UUID、Android 是核心的小寫 id，不正規化的話兩個平台的租約互相看不見。
   收到在場資訊時與比對時都換算，送出的仍是本機 id（舊版也看得懂）。

## 6. 協同中的復原／重做

1. **只退自己的動作**：別人的修改不進自己的復原紀錄（現行即如此）。
2. 復原產生的是**新的操作**（新時戳），與一般修改一樣立刻廣播。別人的畫面同步退回。
3. **不蓋掉別人之後的修改**：復原要還原的每一個欄位，若現在的值是別人在我之後寫的
   （欄位時戳的 `userId` 不是我），就保留別人的值、只還原其餘欄位。
4. 筆跡的復原只移除**自己的**那一筆（以 id），別人同時畫的筆畫不受影響。

## 7. 傳遞與可靠性

- 每個操作帶 `op_id`；收到重複的直接略過（合併規則本來就冪等，這只是省工）。
- 離線期間的操作排入佇列，重連後依序送出（現行已有）。
- **中繼序號**：中繼替每個房間的每個操作配一個遞增的 `seq`（整份狀態的往來 `state_*` 不配、不暫存）。
  客戶端記住看過的最大值，**重連時以 `last_seq` 補發** —— 以時鐘過濾會漏掉「時鐘較小但較晚到」的操作，序號不會。
  舊版中繼不認得 `last_seq`，照 `last_lamport = 0` 從頭補；合併冪等，重複套用沒有副作用。
- **暫存上限**：2000 筆或 32 MB（先到者為準；新圖片整張帶在操作裡，只限筆數的話幾十張照片就能吃光記憶體）。
  要補的那一段已被擠出時，補發回覆帶 `truncated: true`，客戶端改向其他成員要整份狀態。
- **整份狀態**（加入房間、補發不完整）：
  1. 要的一方送 `state_request {req, blobs}`（`blobs` = 自己已有的圖片雜湊）。
  2. 其他成員依使用者 id 排序，第一名立刻回，其餘每多一名多等 0.7 秒、看到有人回了就不回 ——
     排在前面的若是舊版（不會回），後面的人照樣補上。
  3. 回覆 `state_snapshot {req, to, part, parts, objects, ink}` 分段送（每段約 400 KB）：
     `objects` 是合併狀態的每個物件，欄位**依寫入時戳分組**（含已刪除的墓碑），沒有的圖片附上位元組；
     `ink` 只帶這次協同期間加入與擦掉的筆畫（之前就有的兩邊都有，見 §8.1）。
  4. 要的一方套用：沒有時戳的欄位（加入房間時就有的）以「房間起點」的時戳寫入 ——
     **勝過自己的起點、輸給任何一次真正的修改**，所以房間裡的內容優先於這台可能過期的檔案，
     但這台加入後真的改過的不會被蓋掉。兩邊內容不同的文字方塊以房間的全文為新基準重建字元 CRDT。
  5. 全部段落收齊後，**只有這台有的物件**（例如離線時新增的）當成新的送給房間 —— 寧可多不可少：
     使用者的新增不會因為加入房間而消失。（代價：房間在協同開始前就刪掉、沒有墓碑的物件會被補回去。）
- 版本：收到舊協定的操作種類（`attachment_upsert`、`drawing_replace`…）即判定對方版本較舊，提示更新 ——
  舊版看不懂新的操作種類，同房間混用會造成單向同步。舊版送來的操作仍會被接受：
  物件併入 LWW（以它自己的時鐘參與比較），筆跡一律當成「加入缺少的筆畫」，不刪除任何東西。
- 操作 id（`op_id`）放在 payload 裡：三份中繼都原樣轉送 payload，但不一定保留外層的其他欄位。

## 8. 跨平台線上格式（協定 3 → 4）

**原則：線上格式 = 套件格式。** 兩個平台早就各有一套互通的編解碼器（匯出 `.padnote` 用的），
線上傳的就是那一套 —— 不另外發明第三種表示法，也不傳任何平台自己的記憶體結構。

### 8.1 識別碼

| 東西 | 識別碼 |
|---|---|
| 物件 | 核心的區塊／物件 id（小寫 UUID）。Apple 端以 `stableBlockId(附件 id)` 換算 |
| 頁面 | 核心的頁面 id。Apple 端在 `NotebookDocument.pageIds` 保存，跟著頁面的新增、刪除、搬動走 |
| 筆畫 | 送出者給的 id（Android 用核心的 stroke id；Apple 用內容雜湊）。收到的一方記下「線上 id ↔ 本機筆畫」的對應。進入房間時，已有的筆畫全部記為「大家都有」—— 否則第一次在某頁下筆，整頁舊筆畫會以另一組 id 再送一次，對方多出一份 |
| 筆畫在套件裡的 id | 每筆附 `cid` = 這一筆在送出者套件裡的核心 id（Android = 線上 id；Apple = `PKStrokeId.make` 的內容身分，或它記著的送出者 id）。收到的一方**用 `cid`（沒有就用是 UUID 的線上 id）寫進自己的套件**，不另發新 id：同一筆在每一台的套件裡是同一個 id，檔案同步把送出者的筆畫檔帶過來時核心 `materialize` 去重。Apple 把這個 id 記在 `CollabInkIds`（每頁一份，內容指紋 → id），增量寫入與完整匯出都優先用它。舊版送的筆畫沒有可用的 id，照舊由收到的一方發 |

### 8.1.1 與背景檔案同步並存

即時協同（中繼通道）與檔案同步（Drive 焦點通道、整庫同步、區網）是兩條互不知道的路。規則：

- **協同中不匯入開著的那一本。** 匯入會用套件的合併結果換掉工作副本，編輯器重讀、協同影子被重設 —— 這台與房間分歧，差異也不會再送出。Apple 由 `CollabImportHold` 讓同步略過那一本的匯入（照常匯出、上傳）；Android 由 `CollabReloadGate` 延後重開 session。離開房間（或關掉編輯器）時補一次「匯出 → 匯入 → 重讀」。
- **協同擦除要記進本機的「已擦除」名單**（Apple `ErasedInkLedger`）：被擦掉的筆畫可能還在別台（不在房間裡）的筆畫檔裡，檔案同步帶回來時要濾掉，否則它復活、還被當成這台新加的再廣播給房間。協同加回同一筆時從名單拿掉。

### 8.2 操作種類

所有操作的 payload 都帶 `"proto": 3` 與 `op_id`。

**`obj_patch`** —— 物件與頁面的欄位修改（§4.1、§4.2 的 LWW）：

```json
{ "patches": [ { "type": "text", "id": "<block id>", "fields": { "page": "<page id>", "x": 120, "a.fontSize": 18 } } ] }
```

各型別的欄位（`a.` 開頭的是外觀 JSON 的鍵，`s.` 是樣式信封，`p.` 是信封 payload）：

| `type` | 欄位 |
|---|---|
| `text` | `page` `x` `y` `text`（**只在新增時**；之後的內容走 `text_ops`）、`a.*` = `TextBoxAppearance`（含 `runs`） |
| `image` | `page` `x` `y` `blob`（內容 SHA-256）、`a.*` = `ImageAppearance`（圖表也是圖片，規格在外觀裡）。新增時附 `#blob`（base64 檔案內容） |
| `table` | `page` `x` `y` `rows` `cols` `cells` `headerRow` `mergedCells`、`a.*` = `TableAppearance` |
| `shape` | `page` `kind` `x` `y` `width` `height` `cornerRadius` `label` `rotation`、`s.*` = `ShapeStyleMeta` |
| `connection` | `page` `from` `to`（形狀 id）、`s.*` = `ConnectionStyleMeta`（錨點、路徑、端點樣式、文字都在裡面） |
| `link` `model3d` `audio` | `page`、`p.*` = 套件中繼資料裡同一種物件的 JSON（兩平台的 `LinkCodec` 等） |
| `pin` `tape` `sticky` | `page`、`p.*` = 信封 payload（目前只有 Apple 端會畫） |
| `page` | `pos`（排序鍵，§8.4）、`paper`（紙張樣板 id） |
| `meta` | `order:<page id>`（堆疊順序）、`under:<page id>`（置於筆跡下）、`checked:<鍵>`（核取方塊） |

刪除：`"#deleted": true`。認不得的型別或欄位一律保留在合併狀態裡、不顯示 —— 另一個平台可能有這一邊還沒做的東西，
不能因為看不懂就把它丟掉，否則轉送回去時會把別人的資料抹掉。

**`ink_add` / `ink_remove`** —— 筆跡（§4.3）：

```json
{ "page": "<page id>", "strokes": [ { "id": "…", "tool": "fountain_pen", "rgba": "#1A1A1AFF", "width": 2.4,
    "points": [x, y, pressure, tilt, azimuth, dtUs, roll, …] } ] }
{ "page": "<page id>", "ids": ["…"] }
```

點的格式就是核心的 `StrokePoint`（`format-spec.md` §5.4），每點 7 個數字攤平。

**`text_ops`** —— 文字方塊內容的字元層級 CRDT（§8.3）：

```json
{ "id": "<block id>", "base": "<基準雜湊>", "text": "<套用後的全文>",
  "ops": [ { "o": "i", "id": "<site>:<n>", "after": "<id 或空字串>", "c": "字" }, { "o": "d", "id": "<site>:<n>" } ] }
```

### 8.3 同時在同一個文字方塊打字（RGA）

- 每個字（UTF-16 碼元，與逐字格式的位置單位相同）有一個全域唯一的 id `site:n`
  （`site` = 使用者 id，`n` = 那個人打的第幾個字）。
- 插入是「插在某個 id 之後」，不是「插在第幾個位置」—— 位置會因為別人同時插入而移動，id 不會。
- 同一個位置有好幾個人同時插入時，id 較大的排前面（所有人算出同一個順序）。
- 刪除只做墓碑標記，不真的移除 —— 別人可能正要插在它後面。
- **基準**：方塊建立時的文字（或開始協同時的文字）是基準，基準字的 id 是 `0:<位置>`。
  每次送出帶基準的雜湊；收到的一方基準不同（兩邊在協同開始前就不一致）時，退回以 `text` 全文取代並重建基準 ——
  結果仍然一致，只是那一次不是字元層級合併。
- 因為字元會合併，文字方塊**在打字時不再上鎖**；搬動與縮放仍然上鎖。在場資訊的選取 id 以 `text:` 開頭表示「正在打字」。
- **逐字格式以字元 id 錨定**：`a.runs` 仍以位置記錄（套件格式），但修改同時帶 `#ra` ——
  每段頭尾那兩個字的 id。收到的一方以自己的 CRDT 把 id 換回現在的位置，所以對方同時在前面打字、
  刪字都不會讓格式偏移；頭尾的字被刪了就往內縮，整段都刪了才沿用送來的位置。
  文字（`text_ops`）一律比帶格式的修改先送，對方套用格式時已經認得那些字。

### 8.4 頁面的新增、刪除、搬動

- 每一頁是一個 `page` 物件，欄位 `pos` 是**分數索引**排序鍵（字串，依字典序排列）。
- 頁面順序 = 未刪除的頁依 `(pos, id)` 排序。
- 新增：在前後兩頁的 `pos` 之間取一個新鍵；兩人在同一處同時新增 —— 兩頁都保留，以 id 決定先後。
- 刪除：`#deleted = true`。搬動：改 `pos`。同時搬同一頁：LWW，結果一致。
- 收到後依新的順序調整本機：補上缺的頁、刪掉被刪的頁、把頁搬到對的位置。
- 一開始的排序鍵由位置決定（`a0`、`a1`…的固定算法），兩台以同樣的頁序開始時算出同一組鍵。

### 8.5 兩條保護

- **還在等的不是被刪除。** 物件比它的頁（或連接線比兩端的形狀）先到時先擱著；
  擱著的物件本機還沒有，但下一次本機修改**不會**把它當成刪除送出去。
- **畫不出來的型別不是被刪除。** 這一版不認得的型別留在合併狀態裡、不顯示，也不會因為
  「本機沒有」而送出刪除 —— 新版加的物件不會被舊版刪掉。
- 圖表在線上是 `image`（`a.object = "chart"`，設定在 `a.chart.*`，附上算繪好的 PNG）：
  Apple 本來就把圖表當成帶設定的圖片，兩邊各自依設定重畫。

### 8.6 Android 的對照

| Apple | Android |
|---|---|
| `CollabCanonical.maps` / `write` | `AndroidCollabCanvas`（讀寫各物件儲存與 `NotebookMeta`；清單項目以 JSON 原樣進出） |
| `NotebookEditorView` 的 `publishCollabChanges` 等 | `AndroidCollabController`（送出、套用、頁面調整、文字 CRDT、筆跡） |
| 連續頁面模式直接讀寫 `notebook` | `ContinuousCollabBridge`：連續模式每一頁的引擎與儲存住在 `ContinuousPagesView` 的快取裡，協同經由它讀寫 |
| `RichTextEditorView` 的游標平移 | `TextBoxEditor(remoteRevision:)`：別人在同一個方塊打字時換上新內容，游標跟著原本旁邊的字走 |

別人的修改在兩個平台都**不是本機的復原步驟**（Android 以寫回後的內容為新的復原基準）。

### 8.7 堆疊順序（協定 4）

- 每個物件有 `under`（是否置於筆跡下方）；使用者排過順序的物件另有 `z`（分數索引排序鍵，與頁面的 `pos` 同一套）。
- 一頁的順序 = 該頁有 `z` 的物件依 `(z, id)` 排序。本機調整順序時只替**順序對不上**的物件換鍵 ——
  把一個物件移到最上層只送那一個物件的 `z`。
- 兩台以同一份順序開始時，以同一個算法算出同一組起始鍵。
- 寫回平台時換回各自的格式（Apple `objectOrderByPage`、Android `objectOrderByPage` 中繼資料，以頁次為鍵）。

## 10. 驗證

- 單元測試：合併規則的交換律、結合律、冪等性（同一組操作以所有排列套用，結果相同）。
- 衝突情境：同時改同欄位、同時改不同欄位、修改對刪除、刪除後收到舊修改、兩人同時畫、
  擦除與同時新增、復原遇到別人之後的修改、租約同時搶奪、租約過期。
- 多裝置手動驗證：兩台 iPad（或 iPad + Mac）同房間，逐條走上面的情境。
