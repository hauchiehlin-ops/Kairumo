# 錄音納入同步：方案與三個決策

> 2026-09-21。狀態：**方案，尚未動工**。
> 對應問題：「錄音檔是否屬於同步範圍？錄音資料夾可以跟筆記本一起放雲端嗎？」

---

## 0. 現況：Apple 的錄音從來沒有被同步過

| | 錄音存哪裡 | 格式 | 誰寫的 | 有沒有同步 |
|---|---|---|---|---|
| Android | 套件內 `media/audio/<uuid>.opus` | Ogg-Opus | **核心**（`session.feedAudio`） | ✅ |
| Apple | `Documents/Kairumo Record/<uuid>.m4a`（**套件外**） | AAC / m4a | `AVAudioRecorder` | ❌ |

三個可以指出來的事實：

1. 同步只搬套件內的錄音，而且只認 `.opus`
   （`padnote-storage/src/package.rs` 的 `audio_files()` 過濾副檔名）。
   Apple 的錄音兩個條件都不符合 —— 同步引擎**從來沒看過它**。
2. Apple 把錄音卡片插進筆記時，寫進套件的只有**卡片算繪出來的一張 PNG**
   （`NotebookPackageBridge.swift` 的 audio 區塊）。音檔本身沒有進去，
   所以另一台裝置拿到的是一張**播不出來的卡片**。
   這正是 `STATE.md` 常犯錯誤清單裡那一條，只是 Apple 端仍然在犯。
3. 反方向也不通：Apple 首頁的「最近錄音」讀本機的 `recordings.json`，
   所以**從 Android 同步過來的錄音永遠不會出現在那份清單上**。
   Android 是掃套件目錄（`RecordingIndex.kt`），所以它看得到。

## 1. 「錄音資料夾放雲端跟筆記本放一起」——已經是這個設計，但不要另開資料夾

`media/audio/` 就在套件內（`format-spec.md` §2），跟著筆記本一起同步。
Android 現在就是這樣運作的。

**不建議**在雲端另開一個獨立的錄音資料夾：

- 同步的單位是套件。獨立資料夾＝第二個同步單位，要重新處理刪除墓碑、
  命名衝突、孤兒清理、跨裝置收斂 —— 那些在套件這一層已經解過了。
- 跨單位「引用」檔案就是現在 Apple 的毛病：卡片在套件裡、音檔在外面，
  同步之後兩者分家。搬到共用資料夾只是換個地方犯同一個錯。
- 錄音屬於某一本筆記。跟著它走，刪筆記時錄音一起走，不留孤兒。

所以方向是：**把 Apple 對齊 Android**，不是再發明一種佈局。

## 決策 1：首頁直接錄音、還沒指定筆記本的那些要落到哪裡？

| 選項 | 內容 | 代價 |
|---|---|---|
| A | 每段錄音自動建一本新筆記本 | 筆記本清單被錄音洗版，使用者要一本一本刪 |
| **B（建議）** | 固定一本「錄音收件匣」筆記本，每段錄音成為其中一頁的錄音卡片 | 需要定義收件匣的身分；使用者可能不預期它出現在清單上 |
| C | 不允許無筆記本錄音：按下錄音前先選或建一本 | 多一步，而「趕快錄下來」正是這個功能的重點 |

**建議 B**，並且**收件匣用一個寫死的 UUID**。

寫死 id 不是偷懶，是正確性：兩台裝置各自建立的收件匣會收斂成**同一本**，
內容由 CRDT 合併。用隨機 id 的話，每台裝置一本收件匣，
使用者會看到「錄音收件匣」「錄音收件匣 2」「錄音收件匣 3」。

C 的代價比看起來大：錄音這個功能的價值在**按下去就開始錄**。
中間插一個「選筆記本」會讓人錯過要錄的那句話。

## 決策 2：統一成哪一種格式？

前提：**iOS 原生不解 Ogg-Opus**（`AVAudioPlayer` 播不動），
Android 原生支援 AAC/m4a 與 Ogg-Opus 兩者。所以「兩邊各錄各的」不可行 ——
Apple 會播不出 Android 錄的音。

| 選項 | 內容 | 代價 |
|---|---|---|
| **A（建議）** | 統一 Ogg-Opus（＝現行規格） | Apple 要新增**錄製**（AVAudioEngine → 核心 `feedAudio`）與**播放解碼**（核心新增 Opus decoder）兩條路 |
| B | 統一 AAC / m4a | 要改 `format-spec.md` §2 的檔案格式、Android 改錄 AAC、既有 Android 的 `.opus` 要遷移；核心的 Opus 編碼器閒置 |
| C | 兩種都接受，同步都搬 | **不解決問題** —— Apple 仍然播不了 Android 的 `.opus`，只是把不一致永久化 |

**建議 A**，理由有三個，第一個最重要：

1. **檔案大小直接影響這個 App 的定位。** 語音 Opus 24–32 kbps，
   一小時約 14 MB；同設定的 AAC 要好幾倍。同步走的是使用者自己的
   Google Drive（免費 15 GB），錄音是最會長大的那一類資料。
2. 規格已經寫死 Ogg-Opus，而且 Android 的既有檔案就是它。
   選 B 等於改檔案格式並遷移**已經存在的使用者資料**，風險反向更高。
3. 核心已經有編碼器與 Ogg 封裝，只缺解碼器 —— 而 `audiopus` 本來就有
   `Decoder`，`ogg.rs` 也已經有頁面解析（`ogg_opus_duration_us`）可以擴充。

**A 的代價要說清楚**：Apple 端不能再用 `AVAudioPlayer`。
播放要走「核心解碼 → PCM → `AVAudioEngine` / `AVAudioPlayerNode`」，
播放進度、波形、拖曳定位都要自己接。這是整個方案裡最大的一塊工。

順帶解掉一個已知的坑：長度一律由核心的 `ogg_opus_duration_us` 算。
兩個平台各自問系統 API 的話，同一段錄音會顯示不同秒數，
而使用者會以為同步壞了（`STATE.md` 已列）。

## 決策 3：既有的 `Kairumo Record/*.m4a` 怎麼辦？

| 選項 | 內容 | 代價 |
|---|---|---|
| **A（建議）** | 一次性轉檔成 Opus 並移入所屬套件 | AAC→PCM→Opus 是二次有損轉碼 |
| B | 原樣移入套件，讓核心也接受 `.m4a` | 兩種格式永久並存，每個讀取端都要記得處理兩種 |
| C | 不遷移，舊錄音留在原地、不同步 | 使用者的舊錄音永遠不會出現在別台裝置上，而且沒有任何提示 |

**建議 A**。Apple 端本來就有 m4a→16 kHz 單聲道 PCM 的程式碼
（`AudioTranscriber.swift` 為了轉錄已經在做這件事），直接重用它餵核心的編碼器。

二次轉碼的品質損失在語音上可以接受；真正要防的是**遷移失敗把原檔弄丟**。
所以：轉檔成功並驗證（可解碼、長度相符）之後才刪原檔，
而且原檔先移到 `Kairumo Record/migrated/` 保留，不是直接刪除。

C 看起來最安全，實際上最糟：使用者不會知道「舊的不同步、新的會同步」，
他只會發現有些錄音在另一台看得到、有些看不到，然後不信任整個同步。

## 2. 工作項

### R1 · 核心：Opus 解碼（`padnote-audio`）
- `OpusDecoder` + Ogg 頁面/封包讀取（擴充既有的 `ogg.rs`）。
- FFI：`decode_ogg_opus(path) -> Vec<f32>`（16 kHz 單聲道）與串流版本。
  整檔解碼對一小時的錄音會吃掉幾百 MB 記憶體，所以**串流版本是必要的**，
  不是優化。
- 測試：編碼→解碼往返的長度與取樣數一致；壞檔不 panic。

### R2 · Apple：錄製改走核心
- `AVAudioEngine` 取 PCM → 重新取樣 16 kHz 單聲道 → `session.feedAudio()`。
- 錄音落在所屬套件的 `media/audio/<uuid>.opus`。
- 移除 `AudioRecorderManager` 寫 m4a 的那條路（播放暫時保留，見 R3）。

### R3 · Apple：播放改走核心解碼
- `AVAudioPlayerNode` 吃解碼出來的 PCM；進度、波形、拖曳定位重接。
- 這是最大的一塊，建議獨立驗證再併。

### R4 · Apple：清單與卡片改用套件為真相來源
- 首頁「最近錄音」改成掃套件（對齊 `RecordingIndex.kt`），
  **從別台同步過來的錄音才會出現在清單上**。
- 錄音卡片的 `fileName` 改為套件相對路徑（對齊 Android 的 `AudioObject`）。
- 匯出到套件時不要再只放 PNG。

### R5 · 遷移
- 掃 `Kairumo Record/*.m4a` → 解碼 → 編碼成 Opus → 寫進對應套件
  （`linkedNotebookId`；沒有的就進決策 1 的收件匣）。
- 驗證後把原檔移到 `migrated/`。一次性，且可重跑。

### R6 · 同步與文件
- `gdrive_sync_media` 不必改（它已經在搬 `media/audio`）。
- `format-spec.md` §5 補上「錄音長度一律由核心算」。
- `PLATFORM-PARITY.md` 補一列。

**順序**：R1 → R3（先確認 Apple 播得動 Android 的錄音，這是整個方案的
成立條件）→ R2 → R4 → R5 → R6。
R3 先做是刻意的：它要是做不出可接受的播放體驗，決策 2 就得重新考慮，
而那時候還沒有遷移任何資料。
