# 帳號與跨裝置自動同步 —— 設計邏輯評估

> 對應需求：「如果應用程式設置登入帳密，評估在跨平台（跨設備）可自動同步該帳號筆記本的設計邏輯」
> 撰於 2026-09-13 · 2026-09-15 已由 ADR-0011 拍板

---

## 先講衝突點

專案已拍板的決策 **D5：不建後端伺服器**（即時協作／Web 版／遙測／金鑰託管都是
「產品定位，非待辦」）。而「登入帳密」在一般人的理解裡就是「有一台伺服器記得我
是誰」。這兩件事直接對撞，**必須先決定要不要改 D5**，否則後面的設計邏輯都是空的。

好消息是：使用者真正想要的東西（在 A 裝置寫、B 裝置打開就有）**不需要**帳號系統
也做得到，而且現有架構已經幫這件事鋪好了路。

---

## 現有架構已經解掉的部分

| 一般同步方案要處理的難題 | Kairumo 現況 |
|---|---|
| 多裝置同時編輯的衝突合併 | **不會發生**。架構不變式 1：每台裝置只寫自己 `device_id` 的檔案，append-only。檔案層級衝突在數學上不可能 |
| 合併伺服器 | 不需要。收斂邏輯在 `padnote-sync`，跑在裝置上，已有收斂測試 |
| 端對端加密 | 已有。`padnote-crypto` 的 envelope（XChaCha20-Poly1305 + Argon2id 包裝 DEK） |
| 傳輸 | D11 已取代 D3：正式自動同步走 Google Drive `appDataFolder`；本機資料夾保留為手動備援 |

**所以缺的只有一件事：讓 B 裝置知道「該去哪裡拿檔案」以及「用什麼金鑰解開」。**
那正是「帳號」在使用者心裡負責的事 —— 但它不一定要由伺服器來做。

---

## 四個選項

### 選項 A｜不做帳號，用使用者自己的雲端硬碟（維持 D5）

筆記本資料夾放進 iCloud Drive 或 Google Drive，兩台裝置指到同一個資料夾。

- **同步**：作業系統負責，我們不碰網路
- **「帳號」**：就是他的 iCloud／Google 帳號
- **跨平台**：iOS/macOS ↔ Android 要走 Google Drive（iCloud 在 Android 上沒有）
- **成本**：小。Apple 端已有雲端資料夾的路徑；Android 需接 Drive SDK
- **風險**：使用者要自己設定一次資料夾位置；換雲端供應商時要自己搬

### 選項 B｜密語金鑰（維持 D5，最接近使用者說的「帳密」）

使用者設一組**密語**（passphrase）。它不是登入密碼，是 Argon2id 的輸入，
用來包裝筆記本的 DEK。同一組密語在任何裝置上都解得開同一本筆記。

- **同步**：仍靠選項 A 的雲端資料夾
- **「帳密」的感覺**：有了 —— 開新裝置時輸入同一組密語就接上了
- **跨平台**：`padnote-crypto` 是 Rust 核心，兩個平台共用同一份實作
- **成本**：中。要做密語設定／變更、金鑰輪替、忘記密語的明確後果說明
- **風險**：**密語忘了就是永久失去那本筆記**。沒有伺服器就沒有「忘記密碼」
  這回事 —— 這件事必須在設定當下講清楚，而不是出事後才說

### 選項 C｜第三方登入 + 第三方儲存（維持 D5 的精神）

用 Google／Apple 登入取得身分，筆記存進該帳號的雲端硬碟。

- **「帳號」**：真的有登入畫面，符合使用者直覺
- **我們仍然沒有伺服器**：身分與儲存都是別人的
- **成本**：中偏高。兩套 SDK、兩套授權流程、上架審查會多問幾題
- **風險**：與 D5 的字面意思不衝突，但與「免帳號、免聯網就能用」的定位有拉扯。
  要確保**不登入也能完整使用**，登入只是多了同步

### 選項 D｜自建後端（**推翻 D5**）

自己的帳號系統與同步服務。

- **好處**：體驗最完整，換裝置零設定
- **代價**：伺服器費用、資料外洩責任、隱私權政策要整份重寫（目前寫的是
  「沒有帳號、沒有伺服器、不追蹤」）、營運與備份的長期人力
- **與 D5 的關係**：直接推翻。決策 D-05（長期維護與營收模式）目前是
  「全免費無後端 ⇒ 無營收」，養一台伺服器需要先解決這一題

---

## 建議

**選項 A + B 一起做，不做 C 與 D。**

理由：

1. **使用者要的是結果，不是帳號**。「在 A 寫、B 打開就有」用 A+B 完全達成，
   而且不必承擔伺服器的成本與責任。
2. **B 提供了「帳密」的心理模型**，又不製造一個我們必須永久維運的身分系統。
3. **現有架構的投資直接變現**：append-only 不變式讓同步不需要伺服器仲裁，
   `padnote-crypto` 的 envelope 本來就是為這個場景設計的。
4. **隱私權政策不必改**。目前寫的是「沒有帳號、沒有伺服器、不追蹤」——
   那是這個產品的賣點之一。

## 若採納，要做的事

| 項目 | 說明 | 相依 |
|---|---|---|
| S-A1 | 雲端資料夾選擇器（Apple 端已有部分） | — |
| S-A2 | Android 接 Google Drive（SAF 或 Drive SDK） | WP6 |
| S-B1 | 密語設定／驗證 UI，六國語系 | `padnote-crypto` |
| S-B2 | 首次配對流程：QR code 傳 DEK（決策 D-06 已在待決清單） | S-B1 |
| S-B3 | 金鑰輪替與「忘記密語」的明確警告文案 | S-B1 |
| S-B4 | 兩台裝置的端到端同步測試（實機，不是模擬） | 全部 |

**要先拍板的兩件事**：

1. 選哪一個方案（建議 A+B）
2. 若選 B：忘記密語 = 永久失去資料。這個代價你接受嗎？
   若不接受，唯一的替代是金鑰託管 —— 而那就是伺服器，回到選項 D

## 不建議的做法（記下來免得以後重新討論）

- **把密語當成「登入密碼」送到某個地方驗證** —— 那就是後端，而且是最糟的那種：
  有伺服器的責任，卻沒有伺服器的好處
- **用裝置 ID 當帳號** —— 換手機就失去一切
- **把 DEK 存在雲端硬碟裡** —— 等於沒有加密，雲端供應商看得到全部內容
