# 一致性閘門：讓實機驗證回去做它該做的事

> 提案日期：2026-09-22（v4.8.2）
>
> 問題不是「驗證得不夠多」，是**驗證的形狀不對**。
> 這份文件先把證據攤開，再提四道閘門，最後給一個可以明天就開始的第一步。
>
> **2026-09-22：四道全部完成並上線。** 執行結果記在文末「做完之後」。

---

## 1. 診斷：這半年修掉的 bug 是同一個形狀

把實際發生過的問題列出來，不挑好聽的：

| 事件 | 怎麼被發現的 |
|---|---|
| 里程碑 × 壓實：還原會吃掉那一刀**之前**的內容 | 我手動想像出一個情境才發現 |
| `AddTextBlock` 重播兩次不冪等，文字被抹成空白 | 修上一個之後才現形 |
| 掌拒收回窗傳了 500 **秒**（微秒當毫秒） | 讀呼叫端時看到的 |
| Opus 寫入端硬寫 `PRE_SKIP = 3840`，每段錄音掉前 80ms | 往返測試 |
| 加密 AAD 綁檔名，壓實改名後解不開 | 測試 |
| Android 轉錄是 56 行的殼，UI 卻說「轉錄成功」 | 人工盤點 |
| `models/manifest.json` 四個死 URL、湊整數的檔案大小 | 人工盤點 |
| 壓感常數 0.35 / 0.65 在 Apple 手抄一份 | 人工盤點 |
| 版面常數 1040 / 420 / 900 在三個地方各存一份 | 人工盤點 |
| `canonical_name` 與 `canonical_path` 混用，路徑被折平 | 測試 |
| 頁面搬移時 Android 沒搬逐頁資料 | 人工盤點 |
| 文件過期導致差點重做已經能用的功能 | **三次**，都是人工查證 |

### 它們可以歸成三類，而且只有三類

**A 類｜同一個事實有兩份表示，沒有任何東西強迫它們一致。**
座標在檔名裡也在現實裡；收回窗在核心是微秒、在 FFI 是毫秒；
pre-skip 是一個常數也是編碼器的真實 lookahead；版面常數三份；
文件的功能清單與程式碼；**兩端各寫一份的測試期望值**。

**B 類｜不變式存在，但只活在註解與人的腦子裡。**
「重播是冪等的」從來沒有被寫成一項檢查。
「每台裝置只寫自己的檔」寫在 `STATE.md`，沒有閘門。
「較長的是超集」、「還原只遮蔽區間內」同理。

**C 類｜介面宣稱的事情，底下沒有做到。**
Android 說轉錄成功；manifest 說那裡有模型；
**Apple 的 34 個測試檔存在，但從來沒有在 CI 執行過。**

### 為什麼實機驗證抓不到這些

一個都抓不到。A 類要兩份表示同時被看到才會現形；
B 類要特定的時序；C 類在畫面上完全正常。
實機能回答的是「手感對不對」「延遲有沒有感覺」——
那是它唯一能回答、而且沒有別的東西能回答的問題。

**把實機拿去找設計錯誤，等於用最慢、最不可重現的工具，去做它最不擅長的事。**

---

## 2. 缺的那條原則

> **一個事實只准有一個可執行的來源。**
> 第二份表示必須**由它產生**，或**被它驗證**；兩者都不是的，就是一個等著發生的 bug。

這不是新發明的規矩 —— **這個專案已經選過它三次**：

- `i18n/ui-strings.json` → 產生 Swift 與 Kotlin 字串表，CI 驗證一致（1,245 條）
- `ffi_screens` → `check-screen-parity.py` 掃兩端原始碼，**棘輪只准縮不准長**
- `layout_metrics` / `ink_width_scale` → 兩端改呼叫核心，不再各抄一份常數

三次都成功了。問題是它**沒有被當成原則套到其餘的地方**，
所以每一次都要等到有人踩到才補一塊。

## 3. 四道閘門

按「槓桿 ÷ 成本」排序。

### 閘門 2（先做，因為半天就能完成）｜Apple 的測試要真的跑

**現況**：CI 對 Apple 只做一件事 ——
`swiftc -parse` 檢查兩個檔的語法。34 個測試檔是裝飾品。

**做法**：`Test (macos-latest)` 這個 job **本來就已經在跑**（`cargo test`），
在它後面加上建 xcframework 與 `xcodebuild test`。

```yaml
- name: Apple 單元測試
  if: runner.os == 'macOS'
  run: |
    ./scripts/build-xcframework.sh
    xcodebuild test -project apple/Kairumo.xcodeproj -scheme Kairumo \
      -destination 'platform=iOS Simulator,name=iPhone 16' \
      -only-testing:KairumoTests
```

**只跑單元測試，不跑 UITests。** 介面測試會因為動畫與載入時序間歇失敗，
而**間歇失敗的閘門會在第三次紅的時候被關掉** —— 這件事
`check-screen-parity.py` 的說明裡已經寫過一次了。

**代價**：macOS runner 多 3–5 分鐘（機器已經在付費了）。
**擋掉**：C 類。而且它立刻讓既有的 34 個檔開始產生價值。

### 閘門 3（真正的投資）｜多裝置模型檢查

**這是唯一能找出「我沒想到的情境」的機制**，也是這份提案的重點。

今天那個資料遺失，我是**先猜到情境才寫得出測試**：
「如果沒有任何裝置留著被壓實吃掉的碎檔呢？」
猜對了是運氣。下一個 bug 我不一定猜得到。

**做法**：把 `s99_milestone_multi_device.rs` 從「三個寫死的劇本」
長成一個**狀態機模型**。

```
狀態：N 台裝置 + 一個共用資料夾 + 每台的已知檔案集合
動作（由種子化 PRNG 抽）：
  編輯（文字／筆畫／物件）   上傳（全部或隨機子集）
  下載（全部或隨機子集）     壓實自己的碎檔並刪雲端上被吃掉的
  建立里程碑                 還原到隨機一個里程碑
  離線一段時間               裝置消失（模擬重灌）
  新裝置加入（整包下載）     加密／解鎖
```

**每一步之後檢查四條性質**（這四條就是把 B 類寫成可執行的東西）：

1. **收斂**：看過同一組檔案的裝置，算出來的狀態必須逐位元組相同。
2. **不遺失**：任何一筆已經被同步出去的內容，只會因為**落在某次還原的
   遮蔽區間內**而消失 —— 其餘任何情況下消失就是 bug。
3. **冪等**：同一批操作套用兩次 == 套用一次。
4. **單調**：還原只准影響 `(cut, upto]` 區間，區間外的東西不准動。

**工程細節（不做這幾件事，模型檢查會變成沒人敢看的間歇紅燈）**：

- 種子化 PRNG，失敗訊息直接印出重現用的種子。
- **失敗時自動縮小**（shrinking）：把 300 步的劇本縮到最短的失敗序列，
  否則沒有人看得懂為什麼紅。
- **回歸種子庫**：每次找到的失敗種子存進 `tests/seeds/`，永遠重跑。
- CI 上跑固定步數（例如 200 步 × 50 個種子，數秒內），
  另外有一個 `--long` 模式給夜間或手動跑。

**代價**：2–3 天。
**擋掉**：B 類全部。今天那兩個 bug 都會在它面前撐不過幾十步。

### 閘門 1｜兩端跑同一組一致性向量

**現況舉例**（今天查證的，不是假設）：
`DocumentTemplateCatalogTest.kt` 檢查「區塊不可以掉到紙外面」，
`DocumentTemplateTests.swift` **沒有這一條**。
反過來 Swift 檢查「頁數要放得下所有區塊」，Kotlin 用另一種寫法檢查。
兩邊測的是同一件事的不同子集，而**沒有人知道哪一邊漏了什麼**。

這正是 A 類：同一個不變式，兩份表示，沒有東西強迫它們一致。

**做法**：核心的一支 Rust 測試**產生**向量檔（不是人手寫）：

```
docs/conformance/
  layout.json        給定寬度 → 欄數、間距、側欄是否並排
  page-guides.json   給定紙張 id → 版面線段與標籤鍵
  ink-curve.json     給定工具與壓感 → 線寬倍率
  doc-replay.json    給定 op 序列 → 區塊、頁數、可搜尋文字
  milestone.json     給定帶座標的 oplog → 看得見哪些 op
  templates.json     每個文件範本 → 區塊矩形、表格形狀、頁數
  symbols.json       符號面板分類與內容
```

兩端各加**一支**測試：讀向量、跑、比對。
CI 重新產生一次，有 diff 而沒有一起提交就紅（與 i18n 的 `verify` 同一個模式）。

**代價**：骨架 1 天，之後每個主題半天，可以逐步加。
**擋掉**：A 類的跨平台部分，而且**永久性地**消滅「兩端各寫一份期望值」。

### 閘門 4｜把承諾寫成數字

目前「即時性」與「穩定性」只是形容詞。

- **同步即時性**：排程器承諾 `DEBOUNCE_MS = 1500`、`PERIODIC_MS = 12000`，
  但**沒有任何東西斷言端到端真的做到**。
  在假 Drive 上加一項：A 編輯 → B 看得到的模擬時間必須 ≤ 承諾值。
  承諾改了測試就要跟著改 —— 那正是重點：改承諾要是一個**看得見**的動作。
- **墨跡延遲**：兩端都已經有 `InkLatencyMeter`，但沒有預算閘門。
  在核心定一個上限，兩端的既有量測超過就紅。
- **不准無聲吞掉錯誤**：Android 假轉錄那一類。
  我**不建議做成自動閘門** —— 判斷「這個 `runCatching` 是不是在騙使用者」
  需要語意，寫成 lint 會有大量誤報，然後被關掉。
  改成審查清單上的一行：**任何回報成功的路徑，都要指得出是誰保證了它。**

**代價**：1 天。
**擋掉**：讓「即時」「穩定」從感覺變成會紅的數字。

## 5. 誠實的部分

**這些閘門不做什麼**：

- 不保證手感。墨跡的「跟手」程度、掌拒的門檻要不要再鬆一點、
  文字方塊拖曳的阻尼 —— 這些**只有實機能回答**，而且應該由實機回答。
- 不保證跨平台的**視覺**一致。兩端的算繪本來就不同（PencilKit vs 自繪），
  逐像素比對會是一個永遠在紅的閘門。閘門 1 比的是**資料與版面數字**，不是像素。
- 不取代真的 Google Drive。網路錯誤、配額、權杖過期、410 游標失效
  ——`sync_conformance.rs` 的假 Drive 已經涵蓋協定層，
  但「Google 今天改了行為」只有真的打過去才知道。

**風險**：

- 閘門 3 如果沒有縮小與種子庫，會變成一個沒人看得懂的間歇紅燈，
  然後被關掉。**這是最可能的失敗方式**，所以那兩件事不是選配。
- 閘門 1 的向量如果用手寫，等於把 A 類問題原封不動搬到另一個檔案裡。
  **一定要由核心的測試產生。**
- 閘門 2 如果連 UITests 一起跑，會因為模擬器時序間歇失敗，同上。

## 6. 建議的第一步

不要四道一起開。順序是刻意的：

1. **今天／半天**：閘門 2。改 15 行 YAML，34 個測試檔立刻開始工作。
   很可能當場就有紅的 —— 那是收穫，不是壞消息。
2. **接下來 2–3 天**：閘門 3 的骨架，動作集合先只放
   「編輯／上傳／下載／壓實／里程碑／還原」，性質先只放收斂與冪等。
   跑得起來之後再加離線、裝置消失、加密。
3. **之後逐步**：閘門 1，從 `doc-replay.json` 與 `templates.json` 開始
   （那兩個現在就有已知的兩端不一致）。
4. **最後**：閘門 4。

做完之後，實機驗證的清單會從現在的
「同步對不對、還原對不對、轉錄真的有跑嗎」
變成
**「這樣寫起來順不順手」**。

那才是實機該回答的問題。

## 7. 做完之後（2026-09-22 實際執行結果）

四道閘門全部上線。**寫出來的第一天就抓到三個會掉資料的 bug，三個都是
「沒有人想到要去試」的情境。**

| 閘門 | 狀態 | 實際情況 |
|---|---|---|
| 2 Apple 測試進 CI | ✅ | 374 項、17 秒。**本機先跑過，全綠** —— 我原本預期會有紅的，沒有 |
| 3 多裝置模型檢查 | ✅ | CI 跑 24 種子 × 160 步（約 20 秒）；長時間版 300 × 400 步（23 分鐘）供夜間 |
| 1 一致性向量 | ✅ | 七組，兩端各一支測試讀同一份 |
| 4 承諾寫成數字 | ✅ | 同步可見延遲 + 墨跡延遲預算 |

### 閘門 3 抓到的三個 bug

**一｜壓實改變了重播順序，區塊被靜默丟掉**（縮小後七步）

壓實把 `0001-devA` 併進 `0003-devA`，那筆 `AddPage` 跟著檔名跑到
`0002-devB` 後面。裝置 B 的區塊先被重播，那一頁還不存在 —— 丟掉。
（`BatchOrigin` 修好了「座標」，但沒修「順序」。）

**二｜區塊比它的頁面先到就被丟掉**

`document.rs` 開宗明義說這個模型「所有變更都是可交換的操作，順序無關」。
**那句話是假的。** 部分同步與壓實都會造成這個順序。

**三｜時光機對它自己的快照說謊**（長時間版抓到，縮小後 18 步）

向量時鐘「每台裝置的最大 lamport」隱含「我拿到了 1..max 的每一筆」。
部分同步讓它變成謊話。A 還原掉一段內容；B 在還沒收到那筆還原時建里程碑；
B 補同步之後內容消失；B 還原回自己的里程碑 —— **內容回不來**。

### 這件事本身的教訓

第三個 bug 是**長時間版**抓到的，CI 那一輪（160 步）沒抓到。
亂數測試的覆蓋是機率性的 —— 所以回歸種子庫不是選配：
抓到過的每一顆種子都要存下來永遠重跑，否則「上次紅過、這次抽到別的所以綠了」
會讓人以為問題自己好了。

另外，**第一版的時序 3 測試是假綠的**：它靠「被壓實吃掉的碎檔還留在對面」
才過關。把雲端刪除模擬進去、再拿掉那個前提之後才紅。
寫測試的時候要問一句「它是因為對才綠，還是因為我沒模擬到那一步」。

### 現在實機驗證還剩什麼

只剩該由實機回答的：手感、延遲的主觀感受、掌拒門檻的鬆緊、
以及真的 Google Drive 帳號下的跨裝置同步。

**同步對不對、還原對不對、壓實會不會掉東西 —— 這些已經不必在 iPad 上試了。**
