Android 計畫

目標：做出可用的 Android 版，而且兩邊的筆記檔案要能互相打開。 這份計畫把「今天卡在哪、要做什麼、怎麼算做完」攤開，最後列出三件需要你拍板的事。

基準版本 v2.3.0（bundle 11） 2026-09-13 現況為實際查證，非推測

最先要決定的事

三條路線

這個決定會決定後面所有工作的形狀。原因很單純：Apple App 目前把筆記存成 notebooks_v1.json 加上 PKDrawing 的專有二進位， 而 PKDrawing 只有 Apple 平台解析得了。

建議

Android 從第一天就讀寫核心的 .padnote 格式；Apple 端補一座「匯入／匯出」橋接，把 PKDrawing 轉成核心筆畫。Apple 的儲存層之後再遷移。

工作包

要做的事，依相依順序

規模是「一個人全職」的粗估天數，用來排序而不是承諾。 驗收標準寫成可以當場檢查的條件 —— 沒有「大致可用」這種說法。

WP13–5 日

讓核心在 Android 編得出來

這是所有事情的前提，而且與路線選擇無關，可以馬上動工。

  • ort 改為 optional feature，並改用 load-dynamic，執行期載入 ONNX Runtime 的 Android AAR 內附 .so。
  • padnote-core 切出 asr / pdf 兩個 feature，讓 Android 第一版能先關掉語音。
  • 取得三個 ABI 的 libpdfium.so（arm64-v8a、armeabi-v7a、x86_64）。
  • 導入 cargo-ndk，產出 jniLibs/<abi>/libpadnote_core.so。

驗收：cargo ndk -t arm64-v8a -t x86_64 build -p padnote-core --release 成功產出 .so；關掉 asr feature 時 763 個既有測試仍全綠。

相依：無

WP22–3 日

Gradle 專案骨架與綁定整合

先讓一個空殼 App 能啟動並確實呼叫到 Rust。

  • 建立 android/app（Compose），設定 minSdk、ABI splits、jniLibs 路徑。
  • 把 UniFFI Kotlin 綁定的產生接進 Gradle task，跟 generate-bindings.sh 同一份來源。
  • CI 加 Android job：組 debug APK＋跑 Kotlin 單元測試。

驗收：模擬器安裝後啟動，畫面顯示 coreVersion() 回傳的版本字串；CI 產出可下載的 debug APK。

相依：WP1

WP34–6 日

把重複邏輯下沉到核心

現在做最便宜 —— 目前每一項都只有一份 Swift 實作，等 Android 也寫了一份就變成兩倍工。

  • 端對端加密改走 padnote-crypto，Swift 端換掉 CryptoKit 那份。
  • padnote-relay 透過 FFI 曝露，兩平台共用同一個中繼與同一份 JSON 協定。
  • 430 條介面字串移進 padnote-i18n，Swift 與 Kotlin 都從核心取字串。

驗收：iOS 與 Android 兩台裝置加入同一個協同房間，互相看得到筆畫與圖釘；關閉網路再恢復，離線佇列補送成功。

相依：WP2

WP45–8 日

檔案互通

依路線而定。轉換器一定要寫在 Apple 端 —— 只有 PencilKit 解析得了 PKDrawing，Android 沒有任何途徑。

  • 路線 1：Apple 端把 PKDrawing.strokes 的控制點餵進核心的 add_stroke(page_id, tool, color_rgba, base_width, points)，匯出 .padnote；Android 直接讀寫核心格式。
  • 路線 2：Apple 儲存層整個改用核心，另外寫一次性資料遷移（含備份與回滾）。
  • 兩條路都要有逐筆畫的往返比對測試。

驗收：iOS 建立的多頁筆記（含手寫、文字方塊、圖片、圖釘）在 Android 開啟後，筆畫數、座標、顏色、頁面高度與原稿一致。

相依：WP0 決策、WP2

WP58–12 日

Android 筆跡引擎

最大的一塊。PencilKit 在 Apple 是免費奉送，Android 這邊要自己寫，而且掌拒是手寫 App 的生死線。

  • Compose Canvas 繪製；用 MotionEvent.getHistorical* 取回 120Hz 的所有取樣點（只讀 getX() 會掉點）。
  • 壓力、傾斜、方位對應到核心的 StrokePoint。
  • androidx.graphics.lowlatency 前緩衝渲染降延遲（需 API 29+）。
  • 掌拒：依 getToolType() 與接觸面積過濾，S Pen 與一般觸控分開處理。
  • 預測筆跡用 MotionEventPredictor，且永不寫入持久化資料（既有架構不變式）。

驗收：手掌貼在螢幕上書寫不產生任何筆畫；筆尖延遲量測 ≤ 一般觸控繪圖 App 的水準；快速書寫不掉點。

相依：WP2

WP65–7 日

Android 平台功能

  • 錄音：AudioRecord 16kHz mono 餵進核心的 feed_audio。
  • 匯出與列印：核心已有 exportPdf / print_data，接上 PrintManager 與 ACTION_SEND。
  • 說明文件：既有的 HTML 手冊與隱私權政策直接放進 assets，用 WebView 呈現。
  • 權限：麥克風、相片、同網段連線（Android 13+ 的 NEARBY_WIFI_DEVICES）。

驗收：錄音→轉錄→匯出 PDF 一條龍跑通；匯出的 PDF 內容與畫布一致（Apple 端剛修好的同一個坑）。

相依：WP2（語音部分另需 WP1 的 asr feature）

WP72–3 日

手寫辨識（ML Kit Digital Ink）

核心的 HwrBackend 已經預留 MlKit 分支，架構決策 D2 也已經接受這個例外。

  • 接 ML Kit Digital Ink，模型按需下載（zh-Hant／en）。
  • 沒有 Google Play 服務的裝置要有明確的降級說明，不能靜默失敗。

驗收：手寫中英文各 20 句，辨識結果進入全文搜尋索引且搜得到。

相依：WP5

WP82–3 日

出可安裝的檔案

  • 簽章金鑰與 Play App Signing、版本號沿用現有的 bump-version.sh（再加 Android 的 versionCode / versionName）。
  • 產出 AAB 上內部測試軌；同時保留可直接安裝的 APK。
  • Play Console 的隱私權政策網址用現成那份。

驗收：內部測試軌可安裝執行；bump-version.sh 一次更新四處版本（Cargo、Apple、Android、文件）且無漂移。

相依：WP2；上架前需 WP5、WP6

已知地雷

會咬人的地方

ONNX Runtime 的 Android 版

load-dynamic 加官方 AAR 是最省事的路，但 ABI 與版本必須對齊。萬一走不通，第一版關掉語音功能 —— WP1 切出的 feature 就是為此準備的。

掌拒沒有系統級支援

Apple 內建，Android 要自己判斷。這是整個計畫裡最容易低估的一項，也是使用者最快感覺到「這 App 不能用」的地方。

前緩衝渲染的裝置差異

androidx.graphics.lowlatency 需要 API 29+，且各家 OEM 行為不一致。要準備一條「退回一般渲染」的路徑。

PKDrawing 的單向性

只有 Apple 平台解析得了，所以轉換器必須寫在 Apple 端。這條相依關係不能繞過，排程時要先排。

協同互通的位元組級一致

AES-256-GCM 的封裝方式與 JSON 協定欄位必須完全相同。與其兩邊各寫一次再對，不如 WP3 直接走同一份核心實作。

ML Kit 需要 Google Play 服務

部分裝置沒有。要嘛接受降級（手寫不轉文字），要嘛另找裝置端方案 —— 這會影響目標市場，建議一併決定。

走哪條路線？

路線 1（先互通後統一）、路線 2（一次到位）、路線 3（Android 單機）。 建議路線 1 —— 它最快讓「檔案可用」成立，而且把大改拆成可以分段驗收的段落。

Android 最低版本？

前緩衝渲染需要 API 29（Android 10）。 建議 minSdk 29，涵蓋率足夠，也免去為舊機另寫一條渲染路徑。

第一版要不要含語音轉錄？

若不含，ONNX Runtime 的 Android 風險直接歸零，M-A 會更快到。 建議第一版不含，等 Android 外殼站穩再補。
