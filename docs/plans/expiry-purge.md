# 過期資料的完整清除（回收桶與保留期限）

> 狀態：設計已定，分階段實作中。進度見文末「階段與驗收」。
> 決策日期：2026-09-30。

## 為什麼要做

現在「刪除」是**立刻、不可逆**的：

- 本機：`NotebookStore.deleteNotebook` 直接刪套件目錄、同步基準線與資料夾同步的副本。
- 雲端：`collect_garbage` 對有墓碑的筆記本，**下一輪就**把它所有檔案刪掉。
- 墓碑 `LibraryItem` 只有 `deleted: bool`，**沒有刪除時間**，所以「保留幾天」在資料格式上
  根本沒有依據。

後果：誤刪沒有反悔空間；而要清理的東西（已刪筆記本、被移除的錄音與媒體、
孤兒檔案、舊碎檔）沒有一個統一的「什麼時候可以安全地永久刪掉」的規則。

## 已拍板的三個決定

| 問題 | 決定 |
|---|---|
| 範圍 | 已刪筆記本（新增回收桶）、已刪錄音與媒體、舊同步歷史與孤兒檔案 |
| 期限與觸發 | 預設 30 天、自動清除；使用者可調（7／30／90 天或永不），並有「立即清除」 |
| 多裝置 | **等所有已知裝置都確認過才刪雲端** |

## 生命週期

```
使用者刪除 ──► 回收桶（deleted=true, deleted_at=t）
                 │  本機套件與雲端檔案都原封不動，可還原
                 ├── 還原 ──► deleted=false（更大的 lamport，收斂規則不變）
                 ▼
             期滿（now ≥ t + 保留天數）
                 │
                 ├── 本機：立刻永久刪除套件與基準線
                 └── 雲端：所有「活躍已知裝置」都確認過這個墓碑 ──► 永久刪除檔案
                            否則等待，並告訴使用者在等哪些裝置
```

## 資料格式（向後相容）

`LibraryItem` 新增 `deleted_at: Option<u64>`（Unix 秒）：

- `#[serde(default, skip_serializing_if = "Option::is_none")]` —— 舊版讀得進來、
  沒有時間的墓碑照舊序列化，位元組不變（格式相容閘門不會紅）。
- 時戳仲裁（`wins_over`）**完全不變**：`deleted_at` 只是墓碑的屬性，
  不參與誰贏。
- **舊墓碑（沒有 `deleted_at`）**：第一台觀察到它的裝置補蓋章
  （用更大的 lamport 重寫同一個墓碑，`deleted_at = 現在`）。保留期從那一刻起算，
  等於給舊資料一段完整的寬限期，**不會**因為升級而一夜之間清掉所有歷史刪除。
  多台裝置同時蓋章由 lamport 收斂到同一個結果。

## 「所有已知裝置都確認過」怎麼做

雲端佈局已經是 `sync/<device_id>/…`，**裝置可以從雲端列舉出來**。新增：

```
sync/<device_id>/ack.json     { "seenLamport": <u64>, "at": <unix 秒> }
```

- 每台裝置**只寫自己的** `ack.json`，內容是「我這台已經合併到的最大 lamport」與時間。
- 它是**單調暫存器**（`seenLamport`、`at` 只增不減）、單一寫入者 ——
  不違反「檔案層級衝突在數學上不可能」的不變式，因為沒有第二個寫入者。
- 墓碑 T 被裝置 D **確認** ⇔ `ack(D).seenLamport ≥ T.lamport`。
- 雲端永久刪除 T 的檔案的條件（全部要成立）：
  1. 已期滿；
  2. 每一台**必要裝置**都確認過 T；
  3. 這一輪已拉過最新雲端快照（沿用 `collect_garbage` 現有的前置檢查）。
- **必要裝置** = 已知裝置（`sync/<id>/` 底下有檔案，或有 `ack.json`）中，
  沒有「失聯」的那些。**失聯**：`ack.at` 距今超過 90 天。**沒有 ack 的舊版裝置**
  無法判斷最後出現時間，所以給更長的寬限：墓碑期滿後再過 90 天才不再等它。
  這讓一台被遺忘在抽屜裡的裝置**不會永遠卡住清除**，但也不會在它還可能回來的時候
  搶先把資料刪掉。
- 等待中的項目要**看得見**：回收桶顯示「等待 <裝置> 確認」。

## 各類資料的規則

| 類別 | 何時永久刪除 | 備註 |
|---|---|---|
| 已刪筆記本 | 期滿 + 裝置確認（雲端）／期滿（本機） | 本機不需等別台：那是自己的副本 |
| 筆記本底下的錄音與媒體 | 跟著筆記本走 | 它們都在 `notebooks/<id>/` 底下，筆記本清除時一併清掉 |
| 孤兒檔案（索引裡從沒有的 id） | 修改時間超過保留期 **且** 每台必要裝置在它寫進雲端之後都同步過 | **年輕的 `Unknown` 仍然絕不刪**：那可能是別台剛建立、索引還沒拉到 |
| 舊碎檔 | 已被壓實涵蓋（規格 §7.8）的，上傳成功後 | 現行規則不變 |

### 決定：個別被刪的錄音維持「立即刪除」，不套保留期

原設計把「已刪錄音」也放進保留期。實作前的調查推翻了它：

- 一段錄音刪除時，本機**立即**刪檔、雲端那份下一輪同步就刪（`media_delete_audio`，
  `ffi_gdrive.rs`）。
- 媒體墓碑的語意是「這個名字已經死了、不會復活」（`media_tombstone.rs` 開頭）——
  它是**只增不減的集合**，沒有「還原」。要讓一段錄音能還原，得改這個格式
  （墓碑要能被更大時戳的「復活」推翻），而且兩端都要有「最近刪除的錄音」畫面。
- **沒有還原路徑，延後刪除只會讓使用者多留一份看不到、用不了的雲端檔案**，沒有任何好處，
  卻增加「刪掉的錄音在別台復活」的風險面。

所以：個別刪錄音維持現狀（立即）；**整本筆記本被刪時**，它底下的錄音與媒體照樣跟著
筆記本走完保留期並可還原。若日後要做「最近刪除的錄音」，需要先改媒體墓碑格式，
屬於另一個設計。

## 不可違反的東西

1. **append-only**：不改別台的檔案；只刪，而且只刪「已被授權」的。
2. **`Unknown` 不被年輕時刪除**（`audit.rs` 的安全底線）：孤兒要同時滿足
   「夠老」與「所有必要裝置的索引都沒有它」。
3. **期限只在核心算**，平台只傳「現在幾點」與「保留天數」進來 ——
   與同步節奏放在核心是同一個理由（兩邊各算一份就會不一致）。
4. **永久刪除前先看得到**：回收桶列出每一項與剩餘天數；「立即清除」要二次確認。
5. 保留期選「永不」＝不自動清除，回收桶仍可手動清空。

## 平台範圍

核心（Rust）一份，兩端各接：

- Apple（iOS／iPadOS／macOS）：軟刪除、回收桶畫面、設定、啟動與同步後的自動清除。
- Android：同上，走同一組 FFI。
