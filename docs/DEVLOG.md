## 2026-09-16 · S-60：真字形，而且一個位元組的字型都沒有內嵌

待辦上寫的是「要畫真字得內嵌一份中文字型，授權要另外拍板」。**那個前提是錯的**，
所以那個決策不必做。

### 先查清楚壞的是什麼

`export_page_png` 不只餵縮圖，**它也是使用者按下「匯出 PNG」時走的那條路**
（`Exporter.kt`、`ExportPrintManager.swift`）。灰條在縮圖上說得過去 ——
0.18 倍之下一個 15pt 的字只有 3 像素高，畫出來也是一團灰。在使用者匯出、
要拿給別人看的那張圖上，說不過去。

而且兩個平台不一致：

| | 縮圖 | PNG 匯出 |
|---|---|---|
| Apple | `PageThumbnailRenderer`（UIKit，真字） | 灰條 |
| Android | 灰條 | 灰條 |

同一本筆記在 iPad 的清單上看得到字、在 Android 上看不到 —— 那才是使用者真正
撞到的那件事。

### 不用內嵌字型：PDF 交給系統畫

核心的 PDF 匯出器本來就輸出**真正的文字物件**，中文走 Type 0 複合字型
（`/F_CJK`、UTF-16BE）。字型沒有內嵌，靠檢視器代換 —— 而兩個平台的系統
算繪器都做得到：

- **Apple**：PDFKit。實測核心產的 PDF，中文標題是完整的字。
- **Android**：系統內建的 `PdfRenderer`。

所以新增 `PageImageRenderer`（兩邊各一份），走「核心產 PDF → 系統算繪 → PNG」。
**內嵌 0 位元組**，也沒有多一個第三方相依。與 HTTP、LLM、PDF 讀取是同一個
分工：平台做得比我們好的事就交給平台。

### 怎麼確定畫出來的是字，不是豆腐框

這是這件事唯一容易自欺的地方。**灰條、豆腐框（▯）與真字形，三者都會有暗
像素** —— 只數「有沒有墨」三種都會過。

分得開的問法是**筆畫密度**：筆畫少的字與筆畫多的字，只有真字形才會差很多。
同樣八個字，在 Android 上「一」是 696 個暗像素、「鬱」是 4744 個，差 6.8 倍。
豆腐框畫出來兩者會一模一樣。

兩個平台各留一條這樣的回歸測試（`PageImageRendererTest.kt`、
`PageImageRendererTests.swift`），外加「只打字的頁面不可以匯出成空白」。

### 順手修掉一句寫錯的註解

`build-xcframework.sh` 裡當初寫「關掉 pdf feature 只是讓 Apple 也走純 Rust
那條，**功能不會少**」。少了 —— 少的就是字。Apple 不帶 PDFium 的判斷仍然成立，
但理由要算在 PDFKit 那裡，不是算在「fallback 一樣好」。

### 核心那條灰條保留

它仍然是系統算繪失敗時的後備，也是測試與命令列唯一的路。版面（位置、行寬、
行數、行高）照實算這件事因此還是要維持。

## 2026-09-16（收尾之二）· Android instrumented 的三條紅燈

CI 修完之後只剩這一個工作紅。本機用同一組映像（api-35 google_apis）
跑 `connectedDebugAndroidTest` 直接重現，三條：

### 1. 手冊裡不可以寫作業系統名稱

我在錄音那一節加了「**Android 版這一版只有錄音沒有轉錄**」。
`DocsAssetTest.documentsDoNotNameOperatingSystems` 擋下來，而它是對的 ——
理由有兩個：

- 同一份手冊六個語系、所有平台共用。指名某個平台，其他平台的使用者
  會誤判自己有沒有那個功能。
- **那句話遲早會變成謊話。** Android 一旦補上轉錄引擎，手冊就錯了，
  而不會有人記得回來改。

所以不是放寬規則，是改寫成用「你這台裝置有沒有」來描述，並給一個
使用者自己看得到的判準：「轉錄需要一個在裝置上跑的引擎，而不是每台
裝置都有 —— 沒有的話錄音照常運作，只是錄音列不會出現轉錄文字。」
六個語系都改。

**Apple 端的同名測試漏了 `manual.js`**（手冊的內容在那裡，不在 HTML
裡），所以這件事一路到 Android 才被擋下來。已補上，兩邊現在驗同一組檔案。

### 2. `theManualCoversBackupAndSync` 比對的是排版不是內容

與 Apple 端上一輪修過的是同一個問題：`manual.js` 重新產生時走
`JSON.stringify`，鍵名從 `id: "data"` 變成 `"id":"data"`。內容還在，
測試卻紅。改成兩種寫法都算。

### 3. 套索被當成「漏接核心筆刷」

`everyBrushMapsToACoreToolExceptTheEraser` 只放行橡皮擦。套索是 L-06 才
加的**選取**工具，和橡皮擦一樣沒有對應的核心筆刷 —— 那次沒有跟著改這條
測試，所以它一直把新工具誤判成漏接。這條是**先前就存在的紅燈**，不是
這一輪造成的。

本機 200 條 instrumented 測試現在全過。

### 結果：CI 八個工作全綠

`88996dc` 的這一輪八個工作**全部成功**，包含先前一直沒回報完的
`Test (windows-latest)`。CI 從 2026-09-15（S-20 那一筆）紅到現在，
這是這段期間第一次整排綠。

## 2026-09-16（收尾）· CI 整排紅燈：一條 lint 讓五個工作一起倒

### 看起來像五個問題，其實是一個

CI 從 9/15 的 S-20 那次提交起就是紅的，而且**每一個工作都紅**：
Android build、Android instrumented tests、FFI bindings、Format
compatibility、三個平台的 Test。

原因是 `.github/workflows/ci.yml` 設了 `RUSTFLAGS: -D warnings` ——
任何一條 clippy lint 都會讓 `cargo` 失敗，而上面那五個工作**全都要先編
核心**。所以它們不是五個獨立的故障，是同一個編譯步驟倒了五次。

這一次真正擋住全部的是 `padnote-shapes` 裡一個不需要的 `mut`（我自己在
`SpeechBubble` 寫下的閉包）。本機 `cargo check` 只把它當警告，而我當時
用 `grep -E "^error"` 過濾輸出 —— **警告被我自己的 grep 濾掉了**。

教訓寫進 STATE：本機要用 `RUSTFLAGS="-D warnings" cargo clippy
--workspace --all-targets` 對齊 CI，不要只看 `cargo check` 的錯誤行。

### 其餘的 clippy

`padnote-llm` 的 `match` 改 `?`、`padnote-ink` 的索引迴圈改
`iter().enumerate()`、`padnote-core` 的 `chunks_exact` 改 `as_chunks`、
三處 `collapsible_if`、`_point_marker` 搬到 `mod tests` 之前。

`padnote-llm-llama` 的 `n_cur` 是**模型上下文裡的絕對位置**，不是迴圈
次數；clippy 建議的 `for n_cur in (start..).take(n)` 讀起來更難懂，
所以在迴圈上標 `allow` 並寫明理由 —— 這種時候關掉 lint 是對的，
但關掉之前要說得出為什麼。

新加的縮圖繪圖函式參數過多（9/7）。把 `pixels/width/height/scale` 收成
一個 `Canvas` 型別：那四個永遠一起出現，而且拆開來傳很容易把 `width`
與 `height` 寫反 —— 那種錯畫出來是整張圖歪斜，不會有任何錯誤訊息。

### rustfmt

`cargo fmt --all`，34 個檔案。多數是這次之前就沒對齊的，最常見的一項是
edition 2024 的 import 排序（小寫排在大寫之後）。

### 這次是逐一跑過 CI 的每一個工作才推的

`cargo fmt --all --check`、`cargo clippy --workspace --all-targets`
（帶 `-D warnings`）、`cargo test --workspace`、`relay_ffi`、
format-compat、`generate-bindings.sh` + swiftc 語法檢查、
`build-android-libs.sh`、`gradlew assembleDebug`、
`android-release.sh --unsigned`、`cargo deny check`。

## 2026-09-16（深夜）· S-57 縮圖畫得出物件、S-59 Android 編輯器工具列分兩排

### S-57：縮圖不再是一張白紙

`padnote-export::to_png` 是**沒有 PDFium 時的 fallback**，而 Android 第一版
就走這裡（`pdf` feature 關閉）。它原本只畫底紋與筆畫 —— 一本只打字的筆記
在 Android 的清單上是一張全白的圖，而 Apple 那邊看得到整頁的版面。
「預覽跟畫布不一樣」那句抱怨，Android 這一半就是它造成的。

現在畫：**圖片**（解 PNG 後最近鄰取樣貼上）、**表格**（外框、格線、表頭底色
都照核心的版面算）、**形狀與連接線**（幾何走 `padnote-shapes`，與畫布同一份）、
**文字**（灰條，見下）。

順序與畫布一致：圖片 → 形狀 → 表格 → 文字。自己排一套的話，重疊的物件在
縮圖上的上下關係會與畫面相反。

形狀住在**物件樹**裡，不在 `page.blocks()` 中 —— `to_png` 因此多收一個
`objects: Option<&ObjectTree>`。不傳的話縮圖上會少掉整張流程圖。

`geom_kind` 那個 `match` 刻意不寫 `_ =>`：核心加了形狀而這裡忘了補時，
要在**編譯期**壞掉，不是在縮圖上默默少一個圖形。

#### 文字為什麼是灰條

畫真正的字需要一份內嵌字型。中文字型動輒好幾 MB，而且授權要另外拍板
（`deny.toml` 對授權的立場很明確）—— 那是一個決策，不是一個算繪問題，
所以留成 S-60。

灰條不是偷懶：位置、行寬、行數、行高全部照實算，只有字形是抽象的。
縮圖的尺度是 0.18–0.4 倍，一個 15pt 的字在上面只有 3–6 像素高，真的畫
出來也是一團灰。**版面對不對才是縮圖要回答的問題。**

實測：兩本範例筆記的縮圖現在看得到標題列、議程表的格線與表頭底色、
段落行條，以及歡迎頁下方那三顆圓角標籤 —— 與實際頁面一致。

### S-59：Android 編輯器的工具列分兩排

原本所有東西攤在同一個 `FlowRow`：返回、低延遲、掌拒、手寫／打字、模式提示、
框選、分頁導覽、顯示模式、新增頁、「⋯」。在 320dp 的手機上會換成四五行，
**佔掉半個螢幕**，而且手寫的筆刷列在打字模式下照樣列著 —— 使用者看到一整排
筆，點下去卻畫不出東西。

改成與 Apple 一致的兩層：

- **第一排是「這個畫面本身」**：返回 · 手寫／打字 · 分頁導覽 · 顯示模式 ·
  新增頁 · 「⋯」。
- **第二排是「目前模式的工具」**：手寫模式是低延遲、掌拒與筆刷列；
  打字模式是框選、新增文字方塊、插入連結。
- 模式提示獨立成一行細字，兩個模式都顯示。

低延遲與掌拒搬到第二排是有理由的：它們是**手寫的**設定，留在第一排的話，
打字模式下它們也一直在那裡，而那時候兩個都沒有意義。

實測：打字模式下畫布的起點從 y≈480 上移到 y≈275，等於在 640 高的螢幕上
拿回三分之一的版面。

## 2026-09-16（晚）· 未提交刪除的處置、S-40～42、Android 版面對齊 Apple

### 那批未提交的刪除：**維持還原**，並說明為什麼

擁有者把判斷交回來，結論是還原是對的：

- `sync_is_hidden` 修的是「在 A 刪掉、B 上還看得到」那個 bug，**帶著四條
  回歸測試**。刪掉它不只是少一個函式，是把那個 bug 放回去。
- `collab_check_server` 是一道安全控制：它擋掉指向公開網路的明文 `ws://`。
  Android 那邊連同呼叫端一起被拿掉，等於協同可以在公開網路上走明文。
- 三個函式都還有呼叫端，Android 因此**編譯不過**。
- repo 裡沒有任何紀錄（DEVLOG / TODO / ADR）說要移除它們。

四條測試已隨程式碼一起回來，`cargo test --workspace` 82 個 suite 全綠。
原本的工作區 diff 仍在 scratchpad 的 `pre-restore.patch`，要反悔隨時能拿回去。

### S-40：錄音卡片進得了匯出

縮圖與「匯出為圖片／列印」在上一輪已經補上。這一輪補完剩下的那條路：
`.padnote` 套件（PDF 匯出走它）原本只把 3D 模型與連結卡片算繪成衍生圖片
帶進去，錄音卡片會整張消失。加上 `renderObjectImage(NoteAudioAttachment)`
與 `objectKind: "audio"` 的標記，並把 `audioAttachments` 寫進筆記本中繼資料
—— 少了後者，同步到另一台裝置的是一張「有圖片、沒有卡片」的頁面。

兩個平台的 `derivedObjects` 都加上 `"audio"`：不加的話，匯入時那張 PNG 會被
當成普通圖片載入，同一張卡片變成兩份，而且各自能拖到不同的地方。

### S-42：錄音長度改由核心算

新增 `padnote_audio::ogg_opus_duration_us` 與 FFI 的 `audio_duration_seconds`。

**為什麼在核心**：Apple 可以問 AVFoundation、Android 可以問
MediaMetadataRetriever —— 但那是兩份實作，而卡片上寫的是**同一份資料**。
兩個平台顯示不同的秒數，使用者會以為同步壞了。而且格式是我們自己寫的，
granule 的語意與 pre-skip 的處理只有核心最清楚。

只讀最後一頁的 granule（它是累計值），並扣掉 pre-skip —— 不扣的話每段
錄音都會多出 80 ms，與播放器顯示的長度對不起來。讀不出來回 0 而不是丟錯：
長度是顯示用的，為了一個欄位讓插入失敗，代價完全不對等。

實測：5 秒的檔案在 Android 的卡片上顯示 `00:05`。

### S-41：Android 可以從首頁把錄音插進別本筆記

**音檔要複製，不能引用。** 錄音住在筆記本套件裡，而套件是同步的單位 ——
留一個指向別本筆記的引用，另一台裝置只會同步到目標那一本，打開之後拿到的
是一張播不出來的卡片，而畫面上看不出為什麼。

檔名撞到時加時間戳：直接沿用來源檔名的話，兩本筆記各有一個同名錄音時會
互相覆蓋。

順帶修掉一個自己寫出來的 Kotlin 陷阱：`created?.let { null } ?: 錯誤訊息`
在成功時的值是 `null`，而 `null ?: x` 就是 `x` —— 插入明明成功卻跳出
「插入失敗」。改成明確的 `if (created == null)`。

### Android 的首頁改成 Apple 的版面

原本兩個平台長得像兩個產品。最刺眼的是三張主要動作卡：Apple 是一排帶圖示
與副標的卡片，Android 是三顆 180dp 寬的純文字卡 —— 在手機上疊成三顆佔掉
半個螢幕的大按鈕。

改法：

- 加上畫面標題（原本第一眼看到的是一張身分卡，不知道自己在哪個畫面）。
- 三張動作卡改成 `weight(1f)` 等寬、帶圖示與副標，第三張從「新增子資料夾」
  換成「素材圖庫」（與 Apple 一致）。等寬在任何寬度下都是一排。
- 「繼續」改成橫向捲動的卡片列。
- 錄音列加上播放鈕與「⋯」選單（裡面就是 S-41 的入口）。原本只有一個
  麥克風符號，要聽得先開那本筆記再找到它。
- 「全部筆記」加上資料夾列，清單改成兩欄的縮圖格狀。
- 「資料與同步」改成帶圖示與右箭頭的列，並補上「選擇同步資料夾」——
  它原本只在編輯器的「⋯」裡，使用者要先開一本筆記才找得到。
- 補上「說明與條款」兩張卡與頁尾。操作說明原本也只在編輯器的選單裡。

縮圖那一格多了一道判斷：Android 的縮圖目前只畫得出筆畫與底紋（S-57），
所以一本只打字的筆記會是一張全白的圖。**一片空白就改畫「圖示 + 名字」的
佔位** —— 直接顯示的話，格狀清單上會是一排白方塊，看起來像縮圖壞了，
而其實是還沒實作。抽樣判斷而不是掃全圖：每次重組都全掃會卡住捲動。

## 2026-09-16（下午）· 七項回報：表格、形狀庫、模式分界、框選、縮圖、文件、圖示

### 1. macOS 上的表格面板只剩一格

一個 3×3 的表，編修面板上只畫得出**一個**輸入框，而下面的控制列（合併、
增刪欄列）完全正常 —— 所以看起來像「表格壞了」。

成因是 SwiftUI 的 `Grid` 放進雙向 `ScrollView` 時在 Mac Catalyst 上會塌成
一格。iPad 上同一段程式碼是好的，這也是為什麼它活到現在。換成
`VStack`＋`HStack` —— 兩個平台的行為一致，而且這裡本來就不需要 `Grid`
的對齊能力。

順帶補上**即時預覽**：欄寬、字級、合併與表頭底色原本都要「插進去才知道」，
而那時候面板已經關了。預覽與畫布走同一個 `NoteTableView` / `TablePreview`，
所以看到的就是會得到的。

### 2. 形狀庫從 20 種擴到 55 種

新增 35 種：直角三角形、平行四邊形、梯形、七／八邊形、十字、箭號、
四向箭頭方塊、雲朵、心形、閃電、月牙、水滴、L 形、四／六／八角星、太陽、
旗幟、對話框、匾額、扇形，以及 ISO 5807 的人工作業、延遲、已儲存資料、
彙整、抽取、跨頁連接、顯示、打孔紙帶、打孔卡、對照。

**持久化的號碼只能往後加。** `ShapeKind` 會以 u8 寫進 `.padnote`，
0–19 已經在使用者的檔案裡了 —— 動其中一個，就是把他既有的圖形換成別的
形狀。新的一律從 20 起算。`s46_canvas_objects` 那一行寫死的數量就是這道
防線，加形狀時要一起改它。

選單格子從 88pt 縮到 56pt（Android 84dp → 52dp）。五十幾個形狀用原本的
尺寸要捲四五屏，而使用者在找的那一個十之八九不在第一屏。名稱與 ISO 語意
改走輔助說明與無障礙標籤 —— 每格掛兩行字的話格子就小不下來。名稱同時
接上語系表：`NoteShapeAttachment.name(of:)` 是**持久化用的識別字**，
直接拿來顯示的話中文介面會出現「arrowblockright」。

### 3. 「打字模式」下筆還在畫線

`PKCanvasViewDrawingPolicy` 只能表達「誰可以畫」，表達不了「誰都不能畫」。
原本打字模式設 `.pencilOnly` —— 擋得掉手指，擋不掉 Apple Pencil。
拿筆的人在「打字模式」裡照樣在畫畫，而畫面上沒有任何東西告訴他模式換了。
Android 更直接：`InkCanvas` 根本沒有看模式，兩個模式都畫得出來（實測）。

兩邊都補上一道明確的開關（Apple 關 `drawingGestureRecognizer`，Android 在
`onTouchEvent` / `pointerInteropFilter` 最前面讓出事件），並且在畫布上加一張
**兩個模式都顯示**的徽章：這個模式下筆會不會畫線、物件動不動得了。
只在打字模式掛提示的話，切回手寫時畫面上沒有任何差別 —— 而兩邊「同一個
手勢會發生什麼事」完全不同。

### 4. 框選：一次搬一整組

在此之前物件只能一個一個碰。排好的一組圖文要整組往下移 20pt，就得重複做
七次，而且每次都會差一點點。套索只認手繪筆畫，碰不到任何物件。

框選刻意做成一個**明確的模式**，不是「在空白處拖曳就框選」—— 打字模式下
拖曳已經有兩個意思（拖物件＝搬它、拖空白＝捲畫布），再疊一個上去三者會
互相搶，而搶輸的那一次使用者看到的是「我明明在拖，畫面卻在捲」。

判定用**相交**不是「完全包住」：使用者掃過一排卡片時很少會把框拉得比那一排
還大，要求完全包住的話十次有九次什麼都沒選到。刪除時形狀連同它的連接線
一起刪 —— 只刪形狀的話，線會留在畫布上，兩端各指著一個不存在的東西。

### 5. 頁面縮圖與畫布不一致

縮圖的合成器**根本沒有畫表格、形狀與連接線**（現在再加上錄音卡片）。
所以一頁上有表格與流程圖時，側邊欄的縮圖與匯出的圖片裡它們全都不見 ——
使用者看到的是「預覽跟畫布不一樣」，而且會以為自己的內容掉了。

四種型別的幾何一律走核心（`layout()` / `outline()` / `ShapeGeometry`），
與畫布用的是同一份。自己再算一次的話，匯出的表格高度或連接線落點會和
畫面上差一點點 —— 而「差一點點」正是使用者說不出哪裡怪、只覺得怪的那種。

### 6. 手冊與隱私權政策對不上現況

逐條對過目前的實作，六個語系一起改：

- 打字模式那一節說「只認觸控筆，手指會捲動」→ 現在筆也不畫線。
- 說「點一下空白處新增文字方塊」→ 早就改成點兩下（單擊留給捲動與選取）。
- 說可以「向下延長此頁（+800pt）」→ 頁面高度早就固定了。
- 縮圖那句「與畫布等比例、位置一致」→ 在今天之前是錯的（少畫表格與形狀），
  現在對了，但仍然只畫上半部，所以改成講清楚。
- 新增：範例筆記、說明文件卡片、插入錄音、錄音插入頁面、框選、55 種形狀。
- 補一條常見問題：「為什麼打字模式下筆畫不出東西？」
- **Android 這一版只有錄音沒有轉錄** —— 原本的手冊對所有平台都說「裝置端
  轉錄」，那對 Android 使用者是假的。

隱私權政策補上**最重要的那一個缺口**：App 有 Google 登入與雲端硬碟同步，
而政策裡完全沒提。新增一節說明授權範圍只到 `appDataFolder`、憑證只存在
本機、以及怎麼撤銷。生效日一起更新。

兩份文件的算繪器都加上 `**粗體**` 的支援 —— 之前文字全走 `textContent`，
標記會原樣顯示成兩個星號。

### 7. Android 的圖示是預設的機器人

`res/` 底下根本沒有 `mipmap`，manifest 也沒有 `android:icon` —— 所以系統
用預設圖示。從 `assets/brand/kairumo-icon-v1.png` 產出五個密度的舊式圖示，
另外把筆尖與波形去底當成自適應圖示的前景、紙色當底色。

前景**不能**直接放整張原圖：系統遮罩（圓形、圓角方形、水滴…）會沿著畫面
裁一刀，原圖自己的圓角底板會被切出一圈缺角。去底時亮度門檻取 150 而不是
195 —— 底板有紙紋，接近門檻的中間調會在前景下緣留下一排鬼影（第一版看到了）。

## 2026-09-16 · 四項使用者回報：文件視窗、範例內容、頁面錄音、插入子項

### 1. macOS 上「操作說明」與「隱私權政策」按了沒反應

不是找不到檔案，檔案一直都在 bundle 裡。原因是 `apple/Info.plist` **根本沒有被
打包進去**：`project.yml` 沒有宣告 `INFOPLIST_FILE`，而 pbxproj 裡那一行是
手改的 —— 任何人跑一次 `xcodegen generate` 就會把它抹掉。

抹掉的後果有兩個，而且都**沒有任何編譯錯誤**：

- `CFBundleURLTypes` 消失 → Google OAuth 的 redirect 回不到 App。
- 沒有 `UIApplicationSceneManifest` → Catalyst 的 `UIApplicationSupportsMultipleScenes`
  預設為 NO → `openWindow(id:)` **靜默失效**。按下卡片什麼也不會發生，
  Console 連一行訊息都沒有。

修法是兩件事一起：`project.yml` 補上 `INFOPLIST_FILE: Info.plist`（沒有它，
下一次 xcodegen 又會壞一次），`Info.plist` 補上多視窗的鍵。
實測：Catalyst 建置的 Info.plist 兩個鍵都在，兩份文件各自開出獨立視窗。

Android 這邊本來就是好的（gradle `copyUserDocs` 有把 `docs/manual`、`docs/legal`
複製進 assets），模擬器上實測打得開。

### 2. 範例筆記本是兩本空白頁

`seedDefaultNotebooks()` 只建立了**中繼資料** —— 標題、摘要、頁數，沒有任何
一個字。一本叫「歡迎使用 Kairumo」的筆記打開是一片白，比沒有範例還糟：
使用者會以為這個 App 只能手寫。

兩本各三頁，圖／文／表混排（`apple/Sources/SeedContent.swift`、
`android/.../library/SeedNotebooks.kt`）：

- 歡迎使用 Kairumo：三合一說明 + 三顆圓角標籤形狀 / 工具列對照表 / 備份與隱私
- 課堂與會議記錄：議程表 + 重點 / 可編修的長條圖 / 待辦表 + 三節點流程圖

**文案只在建立當下取一次語系字串**，不像標題那樣掛 `titleKey` 跟著語言變 ——
種子跑完那些字就是使用者自己的內容了，跟著變的話他改過的字會被翻譯蓋掉。

表格內容在 catalog 裡是**一條字串**（`\n` 分列、`|` 分欄）。拆成十五條的話
譯者看不到上下文，而且加一列要改六個語系的鍵名。

### 3. 錄音進不了頁面

在此之前錄音只有兩個位置：首頁清單，與筆記本層級的 `recordingAudioPath`。
兩者都**沒有座標**，所以「把這段錄音擺在對應的那一段筆記旁邊」做不到。

新增 `NoteAudioAttachment`／`AudioObject`：和圖片、表格同一層級的畫布物件，
有頁次、有位置、有尺寸，進得了堆疊順序與圖層面板。兩邊的 JSON 鍵名一致
（`audioAttachments`），所以跨平台同步得過去。

播放狀態以**附件 id** 為鍵而不是錄音 id —— 同一段錄音可以插在兩頁上，
按第 2 頁那張時第 1 頁不該一起變成暫停鈕。

卡片的選取用**長按**不是點擊：點擊要留給播放鈕，兩者都掛點擊的話
按播放會先被外層吃掉。

### 4. 「更多」插入子項目

實際壞掉的是**連結卡片**：`LinkPreviewSheet` 的插入路徑漏了 `pageIndex`，
所以在第 5 頁按「插入連結」，卡片會落在第 1 頁 —— 畫面上什麼也不會出現。
其他插入路徑（圖片、表格、形狀、3D）都有那一行，只有連結漏了。
Android 那邊本來就沒漏。

另外連結卡片兩邊都只能搬、不能改：補上旋轉、縮放、編修（網址／標題／說明）
與刪除（Android 在此之前**刪不掉**）。卡片高度也改成照模型走 ——
原本只綁寬度、位置用寫死的 `+50` 推算中心，卡片一變高選取框就對不上。

「插入物件」選單原本插不了表格、形狀、連結與錄音（只有「更多」裡有）。
一個叫「插入物件」的選單插不了其中四種，使用者找不到就會以為功能不存在。

## 2026-09-15 (32) · 版本號的唯一入口

### ASC 上的號碼為什麼會亂

    3.2.0  → build 24        2.10.0 → build 23, 24
    3.0.0  → build 22        2.9.0  → build 22
    2.10.1 → build 24        2.8.0  → build 20, 21   2.7.0 → build 20

build 24 被三個版本用過、22 被兩個用過。成因不是誰手滑，是結構問題：
Apple 與 Android 各自用不同指令打包、各自升號，而升號**只看 repo 裡的數字**。

**build 號的唯一性是 Apple 那邊的狀態，不是 repo 裡的狀態。** 這是這次的核心
認知。本機算出來的「下一個號碼」在 ASC 已經有更高的號碼時就是錯的，
而且錯誤要等到打包完十幾分鐘後上傳被拒才會知道。

### 三道結構性的改動

1. `asc-latest-build.py` 查 ASC 上已用過的最大 build 號。
   沒有 API 金鑰時回 0 而不是報錯 —— 它是防線不是必要條件。

2. `bump-version.sh` 取 `max(本機六個來源, ASC) + 1`。明確指定的號碼若不大於
   ASC 上已有的，**當場**擋下並告訴你該用哪個號碼。

3. `release.sh` 訂死「**一次發版只升一次版本號**」：
   `apple` / `android` 單獨執行時不升版，用的是 repo 目前的版本；
   要升版用 `all` 或 `bump`。單平台模式下給升版參數會被擋下 ——
   那正是兩邊號碼分家的起點，擋在入口比事後對帳便宜太多。

版本重設為 **3.6.0 (30)**：3.6.0 蓋過 ASC 上最高的 3.2.0，30 蓋過最高的 24。
兩個平台的產物都實際驗過帶著新號碼（Android aapt2 讀出 versionCode=30；
Apple 的 build settings 是 CURRENT_PROJECT_VERSION=30）。

## 2026-09-15 (31) · 不經商店的安裝路徑

### `.ipa` 不是「可以傳給別人的安裝檔」

新增 `scripts/dist.sh`，把當下的程式碼打包成能直接安裝的檔案（不升版、不
commit、不碰商店 —— 那些是 `release.sh` 的事）。mac 與 Android 很順：
Developer ID 簽章 + 公證 + 釘選的 DMG、apksigner 驗過的 universal APK，
兩者給誰都能裝。

iOS 不是。第一版交出一個通過所有驗證的 Ad Hoc `.ipa`，然後才發現
**iOS 根本沒有安裝 .ipa 的功能** —— AirDrop 過去、丟進「檔案」App 再點下去，
系統完全沒有反應。不是檔案壞了，是這個格式只有 Mac 上的 Apple Configurator /
Finder 送得進裝置，而且目標裝置的 UDID 還得事先登錄。

「打包成功、驗證全過」跟「對方裝得起來」是兩件事。這次的驗證只證明了前者，
卻用前者的口氣回報 —— 這正是 `STATE.md` 裡那條「誠實區分已驗證與待實機」
要擋的東西。

補上兩條真的能用的路：

- **自己的裝置** → `--ios-install`：development 簽章，解出 `.app` 交給
  `devicectl` 直接裝。Xcode 會順手把接上的裝置登錄進帳號，不必先查 UDID。
- **別人的裝置** → TestFlight（`release.sh`）。不收 UDID、對方不用 Mac。
  這是唯一不需要事先登錄裝置的路。

裝置偵測用 `hardwareProperties.reality == "physical"`。第一版拿 `platform`
判斷，結果九台模擬器全被撈進來，一路編譯完才在安裝時報
`capability not supported`。`pairingState` 也不行 —— 模擬器同樣是 `paired`。

### 順手補起來的洞

- `apksigner --print-certs` 的行首是 `V2 Signer:` 而不是 `Signer #1`。
  grep 抓不到就回傳 1，`set -e` 讓腳本在「其實驗證成功」的地方無聲中止。
  驗證用的 grep 一律接 `|| true`，結果另外判。
- Android 側載金鑰做成**固定**的一把（`android/.local/`），不是拋棄式。
  Android 認金鑰不認版本 —— 換金鑰的新版沒辦法覆蓋安裝，使用者得先移除舊版，
  資料一起沒了。

v2.10.1 (24) 的 iOS 與 Mac 組建已上傳 App Store Connect。

## 2026-09-14 (30) · 圖層面板、Mac 上傳被擋下的兩個設定

### 物件堆疊與群組 —— 最後一項「建了用不到」

核心的物件樹一直有完整的堆疊與群組操作，也有列舉出口，但兩個平台的介面
只做到選取與搬動 —— 使用者碰得到物件，卻**碰不到它們的順序**。兩個方塊疊在
一起時沒有任何辦法把下面那個拉上來。

兩平台各補一個圖層面板，規則放在純函式裡（`ObjectLayerOps` / `ObjectLayer`），
同一組案例兩邊各驗一次 —— 不然「同一個操作在兩個平台結果不同」只有使用者
會發現。面板由上到下＝由前到後，那是圖層面板的慣例；反過來的話使用者每按
一次「上移」都要在腦中翻譯一次。

核心補了兩支：

**`set_object_z_index`（絕對索引）。** 原本只有「上移一層／移到最上層」這類
相對操作。相對操作在併發下會疊加：兩台裝置各按一次「移到最上層」，合併後會
得出誰也沒預期的順序（`format-spec.md` §6.2 早就寫明要用絕對索引）。
整批重排時就是逐個帶索引進來。

**`object_node`。** `root_objects` 只回傳根層，而群組之後成員就不是根物件了 ——
平台若只看根層，**整組形狀會從畫面上消失**，而檔案裡其實好端端地存在。

### Mac 上傳被 altool 擋下

兩個錯誤，都是設定檔漏一行，而且**在本機完全看不出來**：App 建得起來、
跑得起來、測試也全過，直到上傳那一刻：

- **90296**：缺 `com.apple.security.app-sandbox`。Mac App Store 的硬性要求。
- **90242**：`Info.plist` 缺 `LSApplicationCategoryType`。

新增 `Kairumo-Mac.entitlements`，用 `[sdk=macosx*]` 條件掛 —— iOS 一律沙盒化，
帶這個鍵反而會讓佈建檔對不上。

**連帶要修的：沙盒會讓同步資料夾失效。** `CloudSyncFolder` 原本用
`bookmarkData()` 建一般書籤。沙盒裡的書籤必須是 security-scoped 的，
否則下次啟動時書籤解得開、卻沒有存取權 —— 而且不會有任何錯誤，
同步只是靜靜地什麼都沒搬。更新過期書籤前也要先取得 scope，
不然過期的書籤永遠不會被更新。

這幾件事寫成 7 條測試，直接讀專案設定檔驗 —— 發現它們的代價本來是
跑完一整輪封裝與上傳。

### 一份不是這個專案決定要有的東西

`crates/padnote-sync/src/gdrive.rs` 出現在工作區裡（未追蹤），`lib.rs` 多了
一行 `pub mod gdrive;`，**整個 workspace 因此編不過**：`async_trait` 不在相依裡，
而且它實作的方法名稱與 `CloudProvider` 完全對不上（真正的 trait 是
`list` / `get_range` / `append` / `put` / `supports_native_append`，且不是 async）。

它的第一個欄位是 `access_token` —— 那是 OAuth，也就是帳號系統，與決策 D-11
相衝（`docs/plans/account-sync-evaluation.md` 的結論正好相反）。

處理方式是最小且可還原的：`lib.rs` 還原成已提交的版本，`gdrive.rs` 移到
`docs/plans/gdrive-provider-draft.rs.txt`。**沒有刪除任何東西**，
要不要接回去是專案擁有者的決定。

### 測試

核心 942、Apple 306 + 5 UI、Android 200，全綠。

## 2026-09-13 (29) · 形狀跨得過平台了

v2.7.0 交付時我明講了一個還沒補的落差：Apple 的形狀存在筆記檔的 JSON 裡，
Android 走核心物件 —— 所以同一張流程圖傳到另一台裝置會**整個消失**，
而且不會有任何錯誤訊息：檔案同步成功、筆記打得開，就是那些方塊不見了。

### 第三個「寫得進去、讀不回來」

`insert_connection` 有 FFI，`connection_object` 沒有。與形狀、表格同一類漏洞，
這已經是第三個了：出口只開了一半，而且在單機測試時完全看不出來。
補上之後，Apple 的匯出改成把形狀與連接線寫進**核心的物件樹**。

連接線的端點用的是**核心給的物件 id**，不是平台原本那個 —— 用舊 id 的話，
線會連到不存在的形狀上，畫面上是一條從空氣連出來的線。匯出時兩端都找不到
對應物件的連線直接跳過，而不是寫一條斷掉的進去。

Android 這邊原本只有形狀存進核心，連接線只活在記憶體裡（重開就沒了），
一併補上；刪形狀時連著的線也一起移除。

### 兩件被 Android 測試抓到的事

**`DocsViewer` 的包裝層過時了。** 那條測試的註解自己寫著「哪天來源改成完整
文件，這裡會提醒去簡化 DocsViewer」—— 上一輪補 charset 之後它就觸發了。
包裝層移除，改成直接 `loadUrl`：少搬一份近 100 KB 的字串進記憶體，
相對路徑也自然生效。這是測試把自己的前提寫清楚換來的。

**上一輪清 OS 名稱漏了「iCloud」。** 我的搜尋清單沒包含它，四個精簡語系裡
還留著，連帶還有幾處「Mac 版視窗」。現在這個檢查在 Apple 與 Android 兩邊
各有一條測試守著。

### 測試

核心 938、Apple 280 + 5 UI、Android 183，全綠。

## 2026-09-13 (28) · 同步的環閉起來、表格與流程圖接上、文件亂碼

使用者列了五項落差，這一輪做完前四項，第五項（Android 應用層 22 項）進行中。

### 「A 裝置寫、B 裝置打開就有」—— 之前只有一半

資料夾同步早就在了，但它只搬 `Packages/` 底下的檔案，而使用者真正在編輯的
筆記活在 `NotebookStore` 裡，套件只是按一個按鈕才產生的衍生物，**而且沒有
回頭的路**。結果是：檔案同步得很成功，另一台裝置上什麼也沒出現。

補上 `NotebookPackageBridge.importDocument`，並把流程定成
**匯出 → 搬檔 → 匯入**（順序不能顛倒：先搬檔的話上傳的是上一輪的舊內容）。

過程中測試抓到四個 bug，沒有一個會跳錯誤訊息：

**連結卡片同步一次多一份。** 連結與 3D 模型匯出時會算繪成圖片（PDF 裡才看得
到），匯入時又被當成一般圖片收回來 —— 同一張卡片存在兩份，每同步一趟再多一份。
改成在外觀裡標記 `object`，匯入時跳過衍生圖片。

**頁面 id 不穩定，頁數翻倍。** 每次匯出都隨機生一批頁面 id，兩台裝置的頁因此
永遠不會收斂：合併之後不是一頁有兩邊的內容，而是變成兩頁。加了
`add_page_with_id`，頁面身分跟著筆記走。

**`AddPage` 沒有依 id 去重。** 雙方的 oplog 都帶著同一頁的 AddPage，合併後頁數
直接變兩倍。

**`create` 一定給你一頁。** 沿用既有 id 時那一頁是多餘的，而「先加再移」在多裝置
合併時**不保證互相抵銷** —— 交錯之後會留下一頁空白。加了 `create_empty`：
不產生它，就沒有需要抵銷的東西。

**匯出會洗掉自己的筆畫。** 只寫「這次新增的」而基準線記成「匯入當下的全部」，
這台裝置自己的內容在下一次匯出時會被扣成空的，而它的檔案又被整個重寫。
基準線改成記「別台裝置的部分」：`別人的 = 合併後的 − 自己的`。

Android 那邊原本只認一本固定檔名的 `notebook.padnote`，同步下來的筆記本永遠
不會被開啟。加了 `NotebookLibrary`（含舊資料搬家，測得比功能還細）。

### 表格與流程圖：缺的一直是「讀回來」

先前判斷「表格與 z-order 沒開 FFI」是錯的。寫入操作一直都在 —— 缺的是**讀取**：
平台拿不到「這一頁有哪些表格、裡面是什麼」「有哪些物件」「這個形狀長什麼樣」。
少了讀取，功能就是單向的：寫得進檔案，畫面上卻列不出來，也就選不到、編不了。
這與圖片區塊、筆記本中繼資料是同一類漏洞，而且在單機測試時完全看不出來。

補上 8 支讀取出口，兩個平台都接上表格（增刪列欄、合併、表頭）與形狀流程圖
（ISO 5807 九符號 + 範本）。表格的版面下沉到新的 `padnote-table` crate ——
欄寬、列高、斷行各算一份的話，表格的高度會不一樣，而高度會影響它底下的東西。

Android 的形狀搬動後重開會跳回原位：位移走的是**變換**，不改寫原始邊界
（ADR-0010），讀回來時要把變換套上去。

### Apple 的輸入診斷

Android 早就有延遲量測，iPad 出問題時卻沒有等價的資訊可看 —— 上一輪 Android
畫布全白那次就是靠那條線找到的。演算法與格式與 Android 逐字相同，否則兩邊的
數字沒有可比性，而那正是它唯一的用途。

### 隱私權政策整頁亂碼

`privacy.html` **完全沒有 `<head>`，也沒有 `<meta charset>`**，直接從 `<title>`
開始。WKWebView 載入本機檔案時沒有 HTTP 標頭可依據，只能猜編碼。手冊只有
`<script charset>`，HTML 本身同樣沒宣告 —— 它只是還沒踩到。

順帶發現 `apple/Resources/Docs` 是手動複製的。改了 `docs/` 卻忘了複製的話，
App 裡顯示的還是舊版，而且兩邊都看不出來 —— 與 Android 綁定那次同一類漂移。
加了 `sync-docs.sh`，裡面也會擋住沒有 charset 的檔案。

文件本身也過時了：還在教已經移除的「延長此頁」，而且完全沒有「備份與同步」
一節 —— 使用者問過「備份的功能在哪裡」，那本身就是問題的一部分。六語系補齊，
並移除所有作業系統名稱（同一份手冊要給所有平台的使用者看）。

### TestFlight 裝不起來是腳本的問題

`apple-release.sh` 只封裝 `generic/platform=iOS`、以 `-t ios` 上傳 —— 那是 iOS
專用組建。Mac 版 TestFlight 找不到 macOS 組建，就回報「要求的 App 無法使用或
不存在」。Mac Catalyst 必須用 `generic/platform=macOS,variant=Mac Catalyst`
另外封裝、以 `-t macos` 上傳。腳本改成預設兩個平台都做。

### 文件視窗

手冊與隱私權政策在桌機上改成**真正的視窗**：可以移動、拉大小、擺在旁邊一邊看
一邊操作。工作表這三件事都做不到。

核心 935、Apple 270 + 5 UI、Android 177，全綠。

## 2026-09-13 (27) · 數字製圖：可重新編修、仿 Excel 的控制、兩個平台同一張圖

### 問題是「插進去就改不動了」

原本的 `ChartStudioView` 只有長條／折線／圓餅三種，而且交出去的是
`onInsertChart: (UIImage) -> Void` —— **一張點陣圖**。圖一插進畫布，
裡面的數字就再也拿不回來，想改一個值只能整張刪掉重做。

修法不是「加一個編輯按鈕」，而是換掉存的東西：存的是 `ChartSpec`（設定），
不是算繪好的圖。點陣圖仍然存進 blob（匯出 PDF 與尚未支援圖表的讀取器靠它），
但**設定跟著區塊走**，走的是既有的 `SetBlockAppearance`（op 32）。

### 版面引擎放進核心（新 crate `padnote-chart`）

圖表是「資料 + 樣式 → 幾何」，那是純邏輯。各平台自己畫一份的話，同一組數字
在 iPad 與 Android 上會長得不一樣 —— 軸的刻度不同、長條的寬度不同、圓餅的
起始角不同。使用者看到的是「我的圖變了」。

所以核心算出**所有幾何**（長條的矩形、折線的頂點、扇形的角度、刻度位置、
圖例與資料標籤的落點），平台層只負責把這些形狀畫出來。連文字寬度的估算都在
核心 —— 各自去問系統字型的話，同一張圖在兩邊的軸會退到不同位置。

幾何**不寫進檔案**：每次從設定即時算。把算好的座標存起來反而會讓兩邊有機會
不一致（一邊用舊座標、一邊重算）。

### 圖型從 3 種變 11 種

直條、堆疊直條、橫條、折線、平滑曲線、區域、堆疊區域、圓餅、環圈、散佈、雷達。
加上 Excel 使用者會預期的控制：軸標題與固定範圍／刻度間距、格線、圖例位置、
資料標籤（外側／內側／置中 + 小數位數）、每個數列的顏色、長條寬度、環圈孔徑。

幾個刻意的決定：

**長條圖的基線一定是 0，折線圖不是。** 長條不從 0 起算的話，長度比例會騙人 ——
那是統計圖表最常見的誤導。折線看的是趨勢，允許不從 0 起算。

**刻度間距一定是 1/2/5 的十次方倍。** 直接把範圍除以格數會得到 0.3333 這種刻度，
軸上就會出現一串沒人想讀的數字。

**圓餅只吃第一個數列**，而且介面會講出來 —— 默默把第二個數列畫上去會得到一個
誰也看不懂的圖，而使用者只會納悶第二欄的數字為什麼沒反應。

**平滑曲線用 Catmull-Rom。** 曲線必須**通過**每一個資料點；不通過資料點的
「平滑曲線」畫的是一組不存在的數字。

### 順手補上的核心漏洞：圖片區塊列不出來

寫這個功能時才發現 `text_block_ids` 有、`image_block_ids` 沒有。也就是說圖表
是**單向**的：寫得進 `.padnote`，另一台裝置卻列不出有哪些圖片區塊，也就找不到
它的設定 —— 使用者會看到一張改不動的圖，而設定好端端地躺在檔案裡。
補上 `image_block_ids` 與 `image_block_size`。

### 另一個漏洞：Android 綁定有兩份

`android/Generated/` 一份、`android/app/src/main/java/uniffi/` 一份，而 Gradle
只看後者。新增的 FFI 不會進 App，**而且編譯照樣會過**，因為舊的那份還在。
正確的產生方式一直是 `build-android-libs.sh`（它用 Android 的 feature 組合，
`generate-bindings.sh` 用的是預設組合，會少掉 `RelayServer`）。
在 `generate-bindings.sh` 裡把這件事寫成註解，免得下一個人又踩一次。

### FFI 的錯誤欄位不能叫 `message`

UniFFI 產生的 Kotlin 錯誤繼承自 `Throwable`，而 `Throwable` 已經有一個
`message` —— 撞名會讓整份 Kotlin 綁定編不過（Apple 端完全看不出來）。改成 `reason`。

### 測試

核心 54（`padnote-chart` 46 + FFI 8）、Apple 26、Android 27。
釘的是會誤導使用者的那幾件事：長條的基線、堆疊的總和、扇形的角度總和、
設定的無損往返、以及「每一種圖型都畫得出東西」——
新增類型時最容易發生的事，是忘了接上版面引擎，圖表會靜靜地空白。

## 2026-09-13 (26) · 筆刷畫不到物件上、備份與同步找不到、平台落差清查

### 筆刷在插入物件上沒作用 —— 是層級問題

插入物件（圖片、文字方塊、3D、連結、圖釘）是疊在 `PKCanvasView` **之上**的
SwiftUI 視圖，預設會吃掉觸控。於是使用者拿筆想在一張圖上圈重點，
筆畫根本到不了畫布 —— 在一個手寫筆記 App 裡，那是最該能做的事之一。

修法是**手寫模式下整層不攔截觸控**。代價是手寫模式不能直接拖動物件，
要搬動或編輯就切到打字模式。這個取捨是刻意的：手寫模式的主角是筆，
物件操作有它自己的模式。

### 「備份的功能在哪裡？」「同步的功能在哪裡？」

兩個都在，但都藏在「系統診斷」裡。**使用者找不到就是設計的問題** ——
而且備份與同步正是會在**出事之後**才想起來的功能，那時沒有人會去翻診斷頁。

首頁新增「資料與同步」區塊，三張卡片直接進去。標題旁邊直接寫
**「不需要帳號，也沒有我們的伺服器」** —— 使用者會找「登入」，
找不到會以為功能不存在，而那是決策 D-11 的結果不是缺漏。

### Android 只有一支固定的黑色鋼筆

清查時才看清楚：Android 連**橡皮擦都選不到**，顏色固定黑、筆寬固定 3pt。
核心的 `ToolKind` 與 `add_stroke` 從一開始就支援，缺的一直只是 UI。

補上筆刷（鋼筆／原子筆／螢光筆／鉛筆／橡皮擦）、六色色票、筆寬滑桿與預覽點。
兩個設計決定：

**橡皮擦不是一種 `ToolKind`。** 核心的 `ToolKind` 是筆刷種類，擦除走
`erase_stroke` —— 它是一個動作不是一種筆。所以它是引擎的一個狀態。

**擦除是整筆擦掉，不切斷筆畫。** 切斷需要把一筆拆成兩筆並改寫取樣點，
那會破壞「存原始取樣點」的不變式（ADR-0002）。整筆擦除是 append-only 的墓碑，
與同步、回溯都相容。

### 平台落差清查（`docs/PLATFORM-PARITY.md`）

逐層對帳，不用印象：

- **核心層沒有落差** —— 兩邊同一個 `padnote-core`。但核心開出 104 個 FFI 方法，
  Android 只用了 29 個。
- **值得注意的是兩邊都沒接的那幾項**：表格、形狀與流程圖、物件堆疊與群組 ——
  核心做好了、測試齊全，**兩個平台都碰不到**。那是「建了用不到等於沒建」，
  而且做一次兩邊都受益。
- **應用層 23 項 Android 完全沒有**，從多筆記本、資料夾、多頁一路到素材庫。
- **Android 有而 Apple 沒有的也記了**：輸入診斷列與延遲量測 —— Apple 出問題時
  沒有等價的資訊可看。

補齊順序不照清單由上而下，而是照「少了它就不算筆記 App」排。

## 2026-09-13 (25) · Android 畫布文字方塊，以及外觀跨不過平台的缺口

### 動手前先發現：文字方塊的樣式**根本不會跨平台**

匯出到 `.padnote` 時，文字方塊只帶了「文字」與「位置」—— 顏色、邊框、
段落設定全部留在 Apple 自己的 JSON 裡。使用者在 iPad 上把方塊設成透明底、
加了行距，換到 Android 打開會變回白底無行距。

**那不是「還沒支援」，是資料遺失。** 而如果照著現況在 Android 再做一份，
兩邊就永遠對不起來 —— 這正是跨平台一致性規則要擋的事。

所以先補核心：新增 `SetBlockAppearance`（op 32），帶一段**核心不解讀的 JSON**。
核心不需要知道「淡黃色」或「圓角 12」是什麼意思 —— 那是平台的 UI 詞彙；
但那些值必須跨得過平台。鍵名寫進 `format-spec.md` §6.2，兩個平台共用同一組。

順帶補上 `text_block_ids(page)`：先前平台層拿得到某個區塊的內容與外觀，
卻**列不出有哪些區塊** —— 也就打不開別的裝置寫進來的文字方塊。

### 兩個平台共用的三條規則

1. **`"clear"` 是哨符不是顏色。** 它與 `#FFFFFF` 是兩回事，而且不能走顏色
   轉換 —— 多數 hex 轉換會丟掉 alpha，透明就變成黑色。Apple 端上一輪就是
   這樣出過 bug。
2. **`null`（沒設定）與 `0`（設成 0）是兩回事。** 編碼時 `null` 的欄位
   **不寫進 JSON**，否則接收端會把每一個從另一個平台來的方塊都當成「行距 0」。
3. **認不得的鍵一律忽略，不是報錯。** 另一個平台可能帶了我們還沒實作的欄位，
   那時該做的是保留其餘設定。

### Android 端

`TextBox` 的欄位與 Apple 的 `NoteTextAttachment` 一一對應；內距 14 也一樣 ——
差幾點就會讓同一段文字在兩個平台換行位置不同，版面就分家了。

一個 Compose 特有的換算要小心：行距在 Compose 是 `lineHeight`（字級 + 行距），
不是 Apple 的「額外間距」。直接把數字填過去，行數會不一樣。

編輯面板的控制項與 Apple 的「Word 文字編修」對齊，**改了就算數**沒有確認按鈕，
而且段落用「減／數值／加」而不是滑桿 —— 行距 0–24pt 這種範圍下滑桿很難精準，
也看不到目前是多少。同樣的取捨兩邊都做了一次。

## 2026-09-13 (24) · 文字方塊的四項修正

實機（macOS）回報四件事。其中兩件的根因都不是「沒做」，是「做了但被別的
東西蓋掉」。

### 1. 編輯面板蓋住正在改的方塊

這個專案**解過同一個問題**：圖片美化面板以前是 modal sheet，蓋住整個畫布，
調濾鏡時看不到自己在調什麼，後來改成浮在畫布上的 `FloatingPanel`。
文字編修還留在 sheet。

套用同樣的做法，但多做兩件事：浮動面板版**沒有取消／確認按鈕**（改了就算數，
畫布上同步看得到），而且**拿掉面板內的預覽區** —— 正在改的那個方塊就在畫布上，
面板裡再放一份預覽只是佔位置，而且兩份看起來不一樣時使用者不知道該信哪一個。

建立**新**方塊時仍然用 sheet：那時畫布上還沒有東西可看，蓋住沒關係。

### 2. 底色設不成透明 —— 選項一直都在，只是會被立刻覆蓋

「透明畫布」這個色票從一開始就在。問題在它旁邊的自訂顏色 `ColorPicker`：
它綁的是**衍生值**（從 hex 算出 `Color`，再寫回 hex），而

```swift
func toHex() -> String? { … String(format: "#%02X%02X%02X", …) }   // 丟掉 alpha
```

於是使用者剛選的 `"clear"` 會被轉成 `#000000` 寫回去。看起來就是「設不了透明」。

改成 `ColorPicker` 用自己的狀態、只在真的變動時寫回。順帶把透明色票畫上一條
斜線 —— 不畫的話它跟白色長得一模一樣，使用者根本認不出哪一個是透明。

### 3. 文字方塊不能拖曳縮放

圖片早就有右下角的縮放把手，文字方塊沒有 —— 要改大小得先開一個**蓋住它**的
面板，而且面板裡只有「方塊寬度」滑桿，**高度完全沒得改**。
（程式裡甚至有一個 `resizeBaseWidth` 狀態，宣告了卻從來沒被用過。）

補上把手，寬高一起拉。下限 120×60 不是隨手取的：比一行字還窄的方框，
每個字都會自己換一行，看起來像壞掉。

### 4. 沒有段落設定

原本只有對齊與清單 —— 那是「字」的設定，不是「段落」的設定。新增行距、
段距、首行縮排、整段縮排四項，畫布與匯出**套同一組值**（行距差幾點，
整塊文字的行數就不同，版面又會分家）。

全部是 `Optional`：舊檔沒有這些欄位，套上非零預設的話，升級之後每一則舊筆記
的排版都會變。

用「減／數值／加」而不是滑桿：這些值的合理範圍很小（行距 0–24pt），
滑桿在那種範圍下很難精準，而且看不到目前是多少。

### Android 的狀態

這四項在 Android 上**目前不適用** —— Android 版的畫布還沒有文字方塊
（WP5 做的是筆跡引擎）。等 Android 有文字方塊時，段落欄位與透明底色的
資料模型已經在 `NoteTextAttachment` 裡，行為要照這裡的規則實作。

## 2026-09-13 (22) · S-45 掌拒收回（Apple）與 S-54 錯誤訊息在地化

### 先更正清單

S-54 寫著「目前 44 個鍵」—— 那是舊的，實際已經 512 條。但**真正的缺口還在**，

而錯誤訊息正是最需要看得懂的那一刻。

### S-45：Apple 的手寫模式原本沒有掌拒

畫布在手寫模式下是 `drawingPolicy = .anyInput` —— 手指能畫，代價是
**手掌也能畫**。Apple 端從來沒有用過核心的 `InkArbiter`。

解法分兩層：

1. **系統層**：偵測到觸控筆就切成 `.pencilOnly`。PencilKit 的掌拒做在系統層，
   比我們在應用層能做的任何判斷都可靠 —— 有現成的就不要自己寫。
   但不能一律 `.pencilOnly`：沒有 Apple Pencil 的人需要用手指寫字。
2. **收回**：切換是有延遲的。使用者的自然動作是手掌先碰螢幕、筆才落下，
   那一瞬間手掌已經畫出東西了。依核心的 `retract` 把筆落下前 500ms 內
   完成的筆畫收回 —— 時間窗與核心仲裁器用同一個值。

觸控觀察寫在 `AdaptiveCanvasView` 本體而不是 extension：在 extension 裡
override UIKit 方法雖然編得過，但那是靠 `@objc` 動態派發矇混，
不是 Swift 保證的行為。而且一律呼叫 `super`，PencilKit 的繪製路徑不受影響。

**沒有 `creationDate` 的筆畫一律保留** —— 收回一筆不確定的筆畫，
比留下一道誤觸的線嚴重得多。

### S-54：背景執行緒也要查得到字串表

錯誤訊息是在背景執行緒組成的（遷移、備份、同步都跑在背景），而
`LocalizationManager.localized` 是 `@MainActor` 隔離的。新增
`localizedUnsafe` 與一份目前語言的快照：字串表是唯讀的靜態資料，
從哪個執行緒讀都一樣。

另一個細節：一個訊息裡有好幾個 `%1@` / `%2@`。用 `replacingOccurrences`
一次全換的話，會變成「原稿 3 頁、套件 3 頁」這種永遠相等的句子。

## 2026-09-13 (21) · 個人資料備份與一鍵復原

### 容器格式在核心

備份檔要能在任何一台裝置上還原 —— iPad 上做的備份換到 Android 也要開得起來。
兩個平台各寫一份格式的話，那件事第一天就不成立。所以容器、索引、校驗全部
在 `ffi_backup`，平台層只負責「哪些東西要進去」與「使用者按了什麼」。

佈局：魔術字 + 版本 + JSON 索引（逐檔路徑／大小／SHA-256，加上平台設定）
+ 連續的檔案內容 + 整體 SHA-256。

**為什麼逐檔都要自己的雜湊**：只有整體雜湊的話，備份檔壞掉時只知道「壞了」，
不知道壞在哪 —— 而使用者最想問的正是「我的筆記還在嗎」。逐檔雜湊讓還原時能
明確說出哪幾個檔案不可信，其餘照樣救回來。

### 三個「寧可不做」的決定

**壞掉的檔案不寫入。** 寧可少一個檔，也不要用壞掉的內容覆蓋掉使用者現有的資料。

**新版格式拒絕解析。** 猜著解析的後果是還原出一堆看起來正常、其實錯位的檔案。

**路徑不可信。** 備份檔可能來自別處，`../` 能寫到目錄之外就是一個可以覆蓋
使用者其他檔案的漏洞。有測試專門釘這一條。

### 復原之前一定先備份現況

使用者按下復原的那一刻，手上那份資料就要被覆蓋了。萬一備份檔本身有問題，
沒有安全網他會**同時失去兩份**。

### 測試抓到一個會毀掉備份的 bug

檔名原本只帶到秒。同一秒內建立的兩份備份會同名而互相覆蓋 —— 而「復原前先
備份現況」正好就發生在使用者按下復原的同一秒，結果是**安全備份把要復原的
那一份蓋掉**，復原出來的是剛才那份毀損的資料。

三條 Apple 測試同時紅了才看出來。檔名改成帶日期時間 + 一段亂碼，
安全備份另外標上 `safety` 讓使用者分得出來。

### 設定也要帶，但不是全部

Apple 只挑 `kairumo.` 開頭的鍵；整包 UserDefaults 倒出來會夾帶系統與其他框架
的東西，還原時寫回去可能造成很難追的行為。二進位值（security-scoped bookmark）
也不帶 —— 換一台裝置就失效，帶過去只會讓使用者以為同步資料夾還在。
Android 同理排除 `sync.treeUri`。

## 2026-09-13 (20) · 問題 3＋5：固定頁面模型

### 根因不在繪圖程式碼

畫布的座標寬度原本就是「視窗寬度」。同一則筆記在 Mac 寬視窗寫的物件座標可能
在 x=1400，到了 iPhone 就在畫面外；匯出時再依當下的寬度取一次圖，
於是「畫布上看到的」與「匯出的」永遠對不起來。**那是座標空間的錯，
不是繪圖程式碼的錯** —— 先前只修繪圖是治標。

### 尺寸只有一個來源

`padnote_doc::{PAGE_WIDTH, PAGE_HEIGHT}` = 800 × 1132（A4 直式比例），
透過 `standard_page_size()` 開到 FFI，Apple 與 Android 各自的 `PageGeometry`
都從它取值。各寫一份常數的話遲早會差一點點，而差一點點的後果是同一則筆記
在 iPad 上是三頁、在 Android 上變成四頁。

維持 800 寬是為了讓既有內容的**水平位置完全不動**；改成真正的 A4 595×842
會讓所有東西水平縮放，動得比需要的多。

### 界線必須就是匯出邊界

畫布上畫出頁面邊緣（實線）與可列印區（虛線）。頁面之外畫成灰底 ——
寬螢幕上畫布比頁面寬，不畫的話使用者會以為整片都能寫。

**畫一條僅供參考的框線比不畫還糟**：他會相信它。所以匯出端一併改掉 ——
`PageThumbnailRenderer` 不再用傳進來的畫布寬度取圖，一律以頁面為準。

### 「延長本頁」移除，改成自動準備下一頁

四個入口的按鈕全部拿掉，自動延長改成：筆跡接近頁尾時把下一頁準備好。
刻意**不自動翻頁** —— 使用者可能只是把最後一行寫到很下面，畫面自己跳走比
繼續留在原地更糟。也只在目前是最後一頁時才新增，否則在中間的頁面寫到底
會憑空多出一堆空白頁。

### 既有過長頁面的重新分頁

`PageRepagination` 比照 WP4c 的紀律：先備份、備份失敗就停手、
**每一本都要驗過才算數**（重新分頁前後筆畫總數與物件總數必須相同，
少一個就還原這一本並記成失敗）、一本失敗不影響其餘、可重入、可回滾。

兩個設計決定值得記下來：

**頁次偏移先算成一張表**，不邊搬邊算。邊搬邊算的話後面的頁次會被前面剛插入的
頁影響，錯位一頁就整本亂掉，而且很難看出來。

**橫跨分頁線的筆畫整筆搬到它開始的那一頁**，不從中間切斷。切斷會把一個字
剖成兩半，那比讓它稍微超出界線更難接受。

五種附件各有 `pageIndex` 與 `y` 卻沒有共同型別，所以抽了一個
`MutablePagePositioned` 協定一視同仁地搬 —— 漏掉一種的後果是那種物件
全部留在原本的頁次上。

## 2026-09-13 (19) · 問題 4：雲端同步（採建議 A）

### 動手前先發現一個會默默吃掉手寫的問題

架構不變式 1 是「每台裝置只寫自己 `device_id` 的檔案」—— 有了它，檔案層級的
衝突在數學上不可能發生，同步就只是把檔案湊在一起。`doc/ops/` 一直遵守這條。

**但筆畫檔不是。** 它原本叫 `ink/<page>.strokes` —— 每頁一個檔、與裝置無關。
單機用完全正常；一旦把套件放進共用資料夾，兩台裝置在同一頁上寫字就會寫同一個
檔名，後到的那份蓋掉先到的，使用者的手寫就這樣不見了，**而且沒有任何錯誤訊息**。

改成 `ink/<page>-<device>.strokes`，讀取時把該頁所有裝置的檔案串起來。
串接順序不影響結果：`materialize` 會先收齊墓碑再過濾。舊版命名的檔案繼續讀得到
—— 使用者手上已經有那種檔案，讓它們消失會是最嚴重的一種資料遺失。

四條測試釘住：兩台裝置的筆畫都要在、檔名確實分開、舊版命名仍讀得到、
在另一台擦掉的筆畫不會復活。

### 為什麼聯集複製就夠了

每個檔案都是 append-only 且只有一台裝置在寫，所以兩邊都有時，較長的那份必然是
較新的**超集**。同步因此退化成「把對方沒有的送過去、把自己沒有的拉回來」——
不需要合併，不需要仲裁，不需要伺服器。

這個推論成立的前提就是上面那個修正。沒有它，整個方案是錯的。

### 策略在核心，I/O 在平台層

Android 的雲端資料夾是 SAF 的 tree URI，**沒有 POSIX 路徑**，Rust 碰不到；
Apple 端則是可以直接讀寫的檔案系統路徑。兩邊的 I/O 天差地遠，但「複製哪些、
往哪個方向」必須完全一樣 —— 兩個平台對「同步」有不同的理解，在使用者眼中
就是資料遺失。所以 `plan_folder_sync` 放在核心，兩邊共用。

`manifest.json` 是唯一整份覆寫的檔案，「較長的是超集」對它不成立。
兩邊都改過時不挑邊，保留雲端那份並告訴使用者 —— 默默挑一個的後果是
另一台裝置改的標題無聲消失。

### 踩到的坑：SAF 會自己補副檔名

`createFile("application/octet-stream", "manifest.json")` 建出來的是
**`manifest.json.bin`**。那樣的資料夾兩個平台都讀不懂，而且建立本身回報「成功」。
修法是依副檔名給 MIME，建完再驗一次名字，對不上就改名，改不回來就當作失敗 ——
不要留下一個名字不對的檔案。

另一個相關的：SAF 的 `"w"` 不保證截斷。覆蓋較短的舊版時要用 `"wt"`，
否則尾端殘留上一版的位元組，壞掉的是雲端那一份。

### 為什麼不做建議 B（密語金鑰）

依你的決定只採 A。記在 `plans/account-sync-evaluation.md`：B 的代價是
「忘記密語 = 永久失去那本筆記」，那件事沒有伺服器就沒有補救。

## 2026-09-13 (15) · 修正：實機上畫布全白

### 先更正一件事

上一則把「模擬器截圖是白的」解釋成「`screencap` 抓不到前緩衝圖層」。
**那個判斷是錯的。** 實機回報一模一樣的徵狀 —— 畫布全白 —— 證明前緩衝路徑

### 真正的原因：Kotlin 的名稱遮蔽

`drawStroke` 是寫在 `Canvas` 上的擴充函式。函式內的 `density` 解析到的是
**`Canvas.density`**（接收者的成員蓋過外層類別的屬性），而不是建構子傳進來的
螢幕密度。未設定的 `Canvas.density` 是 0，於是：

```
drawLine(a.x * density, …)   // 全部乘成 0 —— 整條筆畫塌到原點
paint.strokeWidth = … * density   // 線寬 0
```

編譯器不會有任何警告，畫面上就是一片空白。

找出來的方式不是讀程式碼，是把多重緩衝層的底色暫時改成淡黃色 ——
畫布變黃就代表表面看得見、問題在筆畫；還是白的就代表表面被蓋住。
一次建置就把可能性砍半。接著印出 `paint.strokeWidth`，`sw=0.0` 直接指到兇手。

欄位已改名為 `pxPerDp`，這個遮蔽陷阱不會再犯第二次。

## 2026-09-13 (14) · WP5c/d：前緩衝渲染與預測筆跡

### 預測筆跡只進畫面，永不進資料

`MotionEventPredictor` 猜的是「筆接下來大概會到哪」，用來補「手已經到了、
畫面還沒跟上」的視覺落差。它是**猜測**，不是使用者真的寫下的東西。所以
預測點只畫到前緩衝，絕不餵給 `InkEngine`、絕不進 `.padnote` —— 寫進去的話，
使用者的筆記裡會混進他沒寫過的線條。這是既有的架構不變式，不是這裡的臨時決定。

實作上還有一個容易漏的細節：畫完預測線**不更新**「最後一個點」。更新的話，
下一段真實軌跡會從猜測的位置接續，誤差一路累積下去。

### 延遲量測：先說清楚它量的是什麼

新的 `InkLatencyMeter` 量的是「取樣點在硬體上發生的時刻
（`getEventTimeNanos`）→ App 把它交給合成器」。**這不是筆尖到光子的完整延遲**，
面板本身的掃描與亮起時間量不到，那要靠高速攝影機。

說清楚比給一個好看的數字重要：拿它去跟別家 App 的「延遲」比較，只有在對方
用同一個定義時才有意義。它真正有用的是**同一台裝置上開關前緩衝的前後對比**。

量測器本身也有測試守著三件事：`percentile(100)` 不能越界（那正是最該看的
最差情況）、時鐘不同源算出的負延遲要丟掉而不是汙染統計、緩衝區不能無上限
成長（連續書寫十分鐘不該讓量測器自己變成記憶體問題）。

### 失敗時要退回去，不是黑畫面

各家 OEM 對前緩衝的支援不一致。建不起來就回報 `false`，UI 自動退回一般的
Compose 畫布並顯示一行說明。手寫可以比較鈍，但不能不能用。使用者也能手動
切換開關，直接比較兩條路徑。

### 踩到的坑

**按「清除」只清資料不夠。** 前緩衝與多重緩衝各自持有已經畫上去的像素，
不主動清的話，按了清除畫面還是舊的墨跡，要等下一次抬筆才更新。

**多重緩衝層每次 commit 都是全新的緩衝。** 只畫「這次新增的」的話，抬筆瞬間
先前的筆畫會整片消失 —— 要重畫全部內容。

**窄螢幕上工具列把畫布推下去。** 標題加了 `weight(1f)` 被擠成一欄一個字，
整個版面塌掉。工具列改成水平捲動，而資訊鈕留在捲動區外 —— 它被推出畫面的
時候，正好就是使用者要看延遲數字的時候。

## 2026-09-13 (13) · WP5a/b：Android 筆跡輸入與畫布

### 掌拒不寫第二份

核心早就有 `padnote-input` 的 `PointerArbiter`，而且已經透過 `InkArbiter`
開到 FFI。Android 沒有理由再寫一套判定邏輯 —— 那會變成「同一支筆在兩個平台
行為不一樣」，而且是那種只有使用者會發現的不一樣。所以 Kotlin 這一層只做
**如實轉換**：`MotionEvent` → `FfiPointerEvent`。

### 轉換層有三個錯了不會當掉的地方

1. **只讀 `getX()` 會掉點。** S Pen 取樣率遠高於畫面更新率，一個
   `ACTION_MOVE` 裡通常塞著好幾個歷史取樣點。不讀 `getHistorical*`，
   快速書寫就會變成折線。測試裡塞了三個歷史樣本，斷言四個點一個都不能少。
2. **接觸半徑要換成 dp。** 核心的手掌門檻是 22「點」。直接餵 px，在 3x 螢幕上
   連筆尖都會被當成手掌 —— 而在 1x 的模擬器上完全正常。這種錯最難在開發機上
   發現，所以測試直接釘住 1x 與 3x 兩組數字。順帶：`touchMajor` 是**直徑**，
   核心要的是長半徑。
3. **`AXIS_ORIENTATION` 是 -π..π，核心要 0..2π。** 負值會被核心夾成 0，
   於是扁筆頭的方向在螢幕左半邊全部錯，而且不會有任何錯誤訊息。

### 測試抓到核心的一個真實缺口

原本寫的掌拒測試是「手掌碰一下、抬起、筆才落下」，結果失敗 ——
`retract_suspects` 只看 `active`，而已經抬起的指標在 `on_ended` 就被移除了，
收不回來。

這不是測試寫錯。使用者把手放上螢幕時，手掌常常是「碰一下、滑一小段、
隨著手安定下來抬起」，接著筆才落下 —— 那一小段在筆落下之前就結束了，
畫面上留下一道誰也不知道哪來的短線。模組註解自己寫著「只擋得住一半的情況」，
指的就是這個。

修法：`PointerArbiter` 多留一個 `recent_draws`，記住**剛結束**且被採納為墨跡的
非筆指標，收回時間窗內一併回報。配套四條測試：超出時間窗的舊筆畫不能被抹掉、
同一筆畫不能被收回兩次（平台層會去刪第二次，可能誤刪別的）、已經被擋掉的
不該回報（去刪一個不存在的東西）、換頁後要忘記上一頁。

### 畫布走原始事件，不走 Compose 手勢

`pointerInteropFilter` 而不是 Compose 的指標事件：Compose 的手勢層已經把歷史
取樣點合併成「這一幀的位置」了。手寫必須拿原始 `MotionEvent`。

寬度用核心 `half_width()` 的同一條公式 `base × (0.35 + 0.65 × pressure)`，
與 Apple 端的轉換器同源 —— 同一筆畫在兩個平台粗細才一樣。

### 驗證
- `cargo test --workspace`：799 通過（`padnote-input` 由 33 增為 38）
- Android instrumented 測試 **18/18** 在模擬器上通過，含：
  手掌（接觸半徑 45dp）不產生任何筆畫、筆畫寫進 `.padnote` 後重開讀得回來、
  被收回的筆畫重開後不會復活、歷史取樣點不掉點、dt 夾在 65535µs
- 模擬器實機操作：畫 6 筆有 6 筆；開啟「僅限觸控筆」後手指畫出 0 筆
- iOS 與 Mac Catalyst 建置皆 **BUILD SUCCEEDED**

instrumented 測試而非純 JVM 測試是刻意的：`MotionEvent` 的建構與歷史點機制
只有真的 Android runtime 才有，用 mock 測這一層等於在測自己寫的假物件。

### 還沒做
- **WP5c 前緩衝渲染**（`androidx.graphics.lowlatency`）與 **WP5d 預測筆跡**
  （`MotionEventPredictor`）。這兩項的效果是**延遲**，模擬器上量不出來，
  各家 OEM 對前緩衝的支援也不一致。沒有實機與觸控筆就驗不了，
  所以先不寫 —— 寫一段驗不了的程式碼，只是把風險藏起來。

## 2026-09-13 (12) · WP4c：儲存層遷移（先寫回滾，再動資料）

### 這一步的規則寫死，不留彈性

這是整個 WP4 裡唯一會碰到使用者真實資料的一步，所以 `NotebookMigration`
的每一條規則都是硬性的：

1. **原始檔案一律不覆蓋、不刪除。** 遷移只讀 `notebooks_v1.json` 與
   `Drawings/`，產物寫到 `Documents/Packages/`。有一條測試逐檔比對位元組，
   確認遷移前後原檔完全相同。
2. **動手前先備份。** 備份失敗就整個停手 —— 沒有退路的遷移不該開始。
3. **每一本都要驗過才算數。** 匯出完立刻讀回來，逐頁比筆畫數、逐筆比取樣點數、
   逐點比座標。驗不過的那一本把套件**刪掉**並記成失敗：留下一份看起來成功、
   其實內容不對的檔案，比明確失敗更危險 —— 使用者會信任它。
4. **一本失敗不影響其餘**，報告逐本交代結果與原因。
5. **可重入**：重跑不會產生重複，也不會白做已經遷好的。
6. **可回滾**：從備份還原並清掉產物。

### 指紋不能只看修改時間

可重入要靠內容指紋判斷「這本變了沒」。第一版想用 `lastModifiedDate` ——
錯的。手繪是存在獨立的 `.drawing` 檔，改手繪**不會**更新那個日期，
所以使用者畫了一整頁之後重跑會被判定成「沒變」而跳過。指紋改成
修改時間 + 每頁筆畫數 + 附件數，並有一條測試專門釘住這件事。

另一個相關的坑：核心是 append-only 的，舊套件沒清掉就重匯，內容會**疊起來**
（2 筆 + 3 筆變成 5 筆）。重跑前先刪舊套件，也有測試守著。

### 測試自己寫錯的那一條

`testRerunningSkipsUnchangedNotebooks` 第一次是紅的。原因是測試每次呼叫
`sampleDocuments()` 都產生新的 `lastModifiedDate`（預設 `Date()`），
兩次各叫一次等於資料真的變了 —— 那樣測到的是「有變就重做」，
不是這條要測的「沒變就跳過」。改成兩次餵同一批文件。

### 有按鈕，使用者才碰得到

能力建好卻沒開到使用者面前，等於沒建 —— 這個坑先前踩過。所以在
「系統診斷與版本資訊」裡加了「跨平台格式」區塊：狀態、轉換按鈕、
失敗逐本說明、還原備份、以及一句說明「原始筆記不會被更動」。
放診斷頁而不是主畫面：這是進階動作，不該是使用者第一天就會按到的東西。

遷移**不會在啟動時自動執行**。在啟動路徑上偷偷跑一次會動到使用者的資料，
而且出事時他們連自己做過什麼都不知道。

UI 測試從選單一路按到轉換完成，確認狀態列真的變成「已轉換 N 本」且無失敗。
過程中順手把首頁選單與轉換按鈕加上 accessibility identifier —— 原本靠
`label CONTAINS 'ellipsis'` 去猜，會先命中筆記卡片上的那個「⋯」。

### 型別名稱長度（iOS 閃退的那個舊帳）

新增的區塊會進 `AppDiagnosticsSheet.body` 的型別名稱，所以量了一次：
editor 7,102、home 6,523、diagnostics 1,988 字元。當初造成 iOS 閃退的是
89,768，距離很遠。

### 驗證
- `cargo test --workspace`：794 通過、0 失敗
- `KairumoTests`：40 條全過（遷移與回滾 16 條）
- `KairumoUITests`：含新增的遷移流程，全過
- iOS 與 Mac Catalyst 建置皆 **BUILD SUCCEEDED**
- Android `assembleDebug` 成功（字串表同步到 440 條）

### 還沒做的
App 的**讀取路徑**仍走既有的 JSON + `.drawing`。把讀取切到核心格式是另一件事，
而且要在使用者實際跑過遷移、確認產物無誤之後才值得談 —— 在同一次改動裡

## 2026-09-13 (10) · WP4a：筆畫轉換器與往返保真度

### 這一步只做「證明得了」的部分

WP4 的驗收條件是「iOS 建立的筆記在 Android 打開後，筆畫數、座標、顏色與原稿
一致」。要能檢查這句話，得先有兩樣東西：核心能把筆畫**完整**吐回來，以及
Apple 端有一個 PKDrawing ⇄ 核心格式的轉換器。這一步先把這兩樣做出來並釘上
測試；儲存層的實際遷移（含備份與回滾）留到下一步，因為那會動到使用者手上的
真實資料，不該和轉換器的對錯混在同一次改動裡。

### 核心：`FullStroke` 與 `visible_stroke_details`

原本的 `visible_strokes` 刻意只回傳摘要（id、點數、外框）—— 一頁數萬個點過
FFI 很慢，渲染路徑本來就不該走那裡。但摘要驗不出座標錯位、壓感遺失、筆刷對應
寫反這些錯，所以另開一條互通專用的出口 `FullStroke`，把每個取樣點原樣帶出來。
兩者的分工寫進了註解，免得日後有人拿 `FullStroke` 去做渲染。

### 壓感不從 `PKStrokePoint.force` 取

直覺寫法是 force 夾到 0–1 當壓感。實際上 PencilKit 沒有公開 force 的數值範圍，
手指與 Apple Pencil 也不一致，硬夾的結果是重壓的筆畫整段飽和。改成從
PencilKit **實際畫出來的每點寬度**回推 —— 依核心 `half_width()` 的
`width = base × (0.35 + 0.65 × pressure)` 反解。這樣 Android 端用同一條公式
畫出來的粗細，才會跟 iPad 上看到的一樣。測試逐格掃過 0–1 確認兩個方向互為反函數。

### 踩到的坑

**tilt 與 altitude 是互補角，不是同一個東西。** PencilKit 的 altitude 是
「筆與螢幕平面的夾角」（π/2 為垂直握筆），核心的 tilt 是「偏離垂直的角度」。
直接對接的話，筆越立起來核心會以為越躺平 —— 而且畫面上完全看不出來。

**第一版 Rust 測試紅在測試自己身上。** 我把 pressure / tilt / azimuth 也寫成
位元組相等，結果失敗。格式規格 §5.4 明訂這三個欄位各用一個 u16 定點數儲存
（整點 16 bytes），本來就有量化誤差。把期望改成「誤差不超過一個量化格」，
這條測試才擋得住真正的錯（欄位接錯、角度用錯最大值）。同樣地，Swift 端的
altitude 容差要放到 1e-4：PKStrokePoint 存 0.6 讀回來是 0.60001…，那是
PencilKit 的儲存精度，收得比它還小只會紅在一個不能也不該修的地方。

### 新增 Apple 單元測試 target

轉換器是純邏輯，塞進 UI 測試裡跑很浪費。新開 `KairumoTests`（`apple/Tests`），
14 條測試在 0.02 秒內跑完。UI 測試維持原樣。

### 對現有 Apple 功能的影響：無

`InkInterop` 是一組純函式，沒有被畫布或 `NotebookStore` 呼叫 —— 現有的
iOS / iPadOS / macOS 路徑一行都沒改。核心那邊是新增兩個方法，既有 API 不動。

### 驗證
- `cargo test --workspace`：790 通過（新增 5 條 `s47_ink_interop`）、0 失敗
- `KairumoTests`：14 條全過
- iOS 與 Mac Catalyst 建置皆 **BUILD SUCCEEDED**
- Android `assembleDebug` 成功（`.so` 與 Kotlin 綁定已用新 FFI 重新產生）

WP4b：把轉換器接上實際的匯出／匯入 —— 從 `NotebookStore` 產生一份 `.padnote`

## 2026-09-13 (9) · WP3c：介面字串收斂成單一來源

### 為什麼要動這 430 條字串

它們原本只活在 `LocalizationManager.swift` 的字典字面值裡。Android 一旦自己
再寫一份，同一句話就有兩個版本 —— 改了一邊忘了另一邊只是時間問題，而且是那種
上架後才被使用者發現的錯。所以收斂成 `i18n/ui-strings.json`，由
`scripts/i18n_tool.py` 同時產生 Swift 與 Kotlin 兩份表。

硬前提是不影響 Apple 現有行為，所以做法刻意保守：**產生出來的字與原本逐字相同**，
`LocalizationManager.localized(_:)` 的公開簽名與回退順序（目前語系 → en → 繁中 →
key 本身）一個字都沒動，只是字典改從產生檔取。

### 憑據不是「我覺得一樣」

`i18n_tool.py verify` 把產生的 Swift 檔與 Kotlin 檔各自**讀回來**再跟 catalog
逐條比對，三者必須完全相同才算過。這條檢查也進了 pre-push hook —— 有人手改產生檔
就會在推送前被擋下來。

### 踩到的坑：跳脫被做了兩次

第一次 verify 就抓到 4 條不一致。原因是從 Swift 抽出來時把 `\"` 當成兩個字元
原樣收進 catalog，輸出時 `swift_escape` 又跳脫一次，變成 `\\"` —— 畫面上會多出

## 2026-09-13 (8) · WP3b：協同中繼進核心 FFI，但**預設關閉**

### 為什麼是 feature 而不是直接換掉 Apple 的那份

Apple 版的 Swift 中繼（Network.framework）已經在使用者手上穩定運作。
把 tokio 拉進 iOS 的二進位不但沒有好處，還會動到已經穩定的功能 ——
硬前提就是不准這樣。所以 `relay` 這個 feature **預設關閉**：Android 建置時開，
Apple 不開。兩邊仍然共用 `padnote-relay` 的同一份 JSON 協定，
加密走 WP3a 的 `padnote_crypto::session`，所以 iOS 與 Android 能進同一個房間。

驗證這件事本身也要有憑據：`cargo tree -p padnote-core` 在未開 feature 時
**tokio 出現 0 次**，開了才是 3 次。

### bind 與 serve 拆開

`padnote-relay` 原本的 `run_server` 是「綁定完就進迴圈」，沒有機會回報實際埠號。
App 端常常用 port 0 讓系統挑，然後必須把**實際**綁到的埠顯示給使用者（邀請隊友
要填）。所以拆成 `bind()` / `serve(listener, hub, shutdown)`。

### 踩到的坑：不要在 FFI 裡 block_on

第一版 `RelayServer::start` 用 `runtime.block_on(bind(addr))`，測試立刻炸：
`Cannot start a runtime from within a runtime` —— 呼叫端本身在 async runtime 的
執行緒上。改成用同步的 `std::net::TcpListener` 綁定（順便就拿到埠號），
設成非阻塞後再交給 runtime。這樣不管呼叫端在什麼執行緒上都安全。

### 另一個坑：綁定要用相同的 feature 組合產生

Kotlin 端出現 `Unresolved reference: RelayServer` —— 因為產生綁定那一步用的是
預設 feature 的函式庫，裡面根本沒有 relay 的型別。建置腳本已改為用與 Android
相同的 feature 組合產生綁定。

### 驗收

- `crates/padnote-core/tests/relay_ffi.rs`：起中繼 → 兩個 WebSocket 客戶端加入
  同一房間 → 驗 joined / peers / peer_joined / oplog 轉發 → 停止。2 個測試通過。
- Android 模擬器實機：畫面顯示「協同中繼：已啟動於埠 36451（已停止）」。
- 硬前提回歸：`cargo test --workspace` 785 通過、iOS 建置 BUILD SUCCEEDED。

## 2026-09-13 (7) · WP3a：協同加密下沉到核心，並用跨語言測試證明相容

### 兩邊的加密其實是兩套演算法

盤點發現核心與 Apple 版用的根本不是同一個東西：

| | 演算法 | 用途 |
|---|---|---|
| `padnote-crypto::envelope` | XChaCha20-Poly1305 + Argon2id | **落盤**的同步檔案 |
| Swift `CollaborationManager` | AES-256-GCM（CryptoKit） | **即時協同訊息** |

也就是說協同訊息這條路，核心從來沒有實作過。Android 若自己再寫一份，
兩邊要在同一個房間裡互相解得開就得逐位元組對齊 —— 那是典型的安靜失敗。

### 做法：核心實作「與已上線 Apple 版相同」的那一套

新增 `padnote_crypto::session`，AES-256-GCM，位元組佈局照抄 CryptoKit 的
`AES.GCM.seal(...).combined`：

```text
combined = nonce(12) || ciphertext || tag(16)
```

**刻意不動 Swift。** 硬前提是不影響已穩定的 Apple 版，而且使用者手上已經有
在跑的 iOS 版 —— 讓核心去配合既有格式，Android 就能直接與它互通，Apple 端
一行都不用改。日後 iOS 要改走核心也不會有 wire 格式變動。

### 相容性不是用推論的，是測出來的

`crates/padnote-crypto/tests/cryptokit_interop.rs`：Rust 加密 → 真的叫 `swift`
用 CryptoKit 解；CryptoKit 加密 → Rust 解。雙向都通過。
沒有 Swift 工具鏈的機器（Linux CI）自動跳過，不會因此變紅。

FFI 曝露 `session_key_generate` / `session_seal` / `session_open` 三個函式，
Android 端在模擬器上實機跑過 round-trip：畫面顯示「AES-256-GCM round-trip 通過」。

新增相依 `aes-gcm`（連同 aes / ctr / ghash / polyval）皆為 MIT OR Apache-2.0，
符合 deny.toml 的白名單。

### 硬前提回歸

`cargo test --workspace` 785 通過、0 失敗；iOS 建置 BUILD SUCCEEDED。

## 2026-09-13 (3) · iOS 實機閃退：SwiftUI 型別名稱把主執行緒堆疊撐爆

### 症狀與當機記錄

實機（iPhone 17 Pro / iOS 27）一碰筆記或頁面就閃退，模擬器（iOS 18 與 27、
Debug 與 Release）與 Mac 上都正常。當機記錄：

```
Exception Type:  EXC_BAD_ACCESS (SIGSEGV)
Exception Subtype: KERN_PROTECTION_FAILURE ... Stack Guard
Thread 0 Crashed:
0..56  swift::Demangle::TypeDecoder::decodeMangledType / decodeGenericArgs  ← 遞迴 57 層
57     swift_getTypeByMangledName
58     swift_getTypeByMangledNameInContext
59-60  Kairumo
61     SwiftUICore ViewBodyAccessor.updateBody
```

不是我們的程式碼在崩，是 **Swift runtime 解析型別名稱時遞迴到爆堆疊**。

### 根因：body 的 mangled 型別名稱長達 89,768 字元

SwiftUI 把 `body` 整棵子樹的型別（包含每個 `.sheet` 內容的完整型別）編進
外層的 mangled 名稱。量測結果：

| | 修正前 | 修正後 |
|---|---|---|
| `NotebookEditorView.Body` | **89,768** 字元 | **6,478** |
| `HomeWorkbenchView.Body` | 31,977 | 6,002 |

**為什麼只在實機當：iOS 主執行緒堆疊只有 1MB，模擬器有 8MB。** 同一份程式碼
在模擬器上解析得完，在實機上遞迴到一半就撞上 Stack Guard。這也解釋了為什麼
使用者在 Mac 上跑同一個 iOS 二進位（Designed for iPad）不會當 —— 那裡的
主執行緒堆疊同樣寬裕。

### 修法：在大型子視圖插入型別邊界

把 20 個大型子視圖改成回傳 `AnyView`（`editorTopBar`、`drawingToolbar`、
`canvasWorkArea`、`allNotebooksSection` …），並用 `erasedView { }` 包住每個
`.sheet` / `.fullScreenCover` 的內容。父視圖的型別裡只剩 `AnyView` 三個字，
子樹的型別各自獨立解析。

代價是那些子樹失去結構化 diff，多一點重繪成本 —— 相對於實機必當，這個交換
很划算。

**量測方式留在程式裡**：`KAIRUMO_TYPE_AUDIT=1` 啟動時會印出兩個 body 的
型別名稱長度。這是唯一能在模擬器上看見這個問題的方法，改大型視圖後應該複查。

### 一併修掉

- 版本號：`MacWindowTitle` 原本包在 `#if targetEnvironment(macCatalyst)` 裡，
  但使用者在 Mac 上跑的是 **iOS 版**（`otool -l` → `platform 2`），整段程式
  沒被編譯進去 —— 這是版本號改三次都沒出現的真正原因。拿掉條件編譯，
  並在編輯器工具列直接畫上版本標籤，不再只依賴系統視窗標題。
- 討論串可以刪除單一則留言；已解決時多一條明顯的狀態列。
- 操作手冊與隱私權政策打包進 App，首頁「說明與條款」離線可讀（WKWebView）。
- 兩份文件的語言切換改成下拉式選單。

## 2026-09-13 (2) · 拖曳抖動、視窗標題守門員，與一個會覆蓋筆記的 Binding

### 圖釘浮層拖曳抖動：又是 .local 座標系的回授迴圈

拖曳手勢用預設的 `.local` 座標系，而手勢掛在被 `.offset` 位移的視圖上：

畫面就是劇烈抖動。改用 `DragGesture(coordinateSpace: .global)`，
全域座標不受自身位移影響。

這與 ADR 之外那條「畫布物件拖曳晃動」的成因是同一類 —— 值得記成通則：
**手勢若會改變自己所在視圖的位置，座標系就不能用 .local。**

順帶修好對話框標題列被擠壓（作者名稱直排、「標記為已解決」變成直書）：
寬度 320→360，名稱與按鈕文字加上 `lineLimit(1)` 與 `fixedSize()`。

## 2026-09-13 · UI 缺陷修正：結構側欄、圖釘浮層、內建協同中繼

三個實機回報的缺陷。

### 線上協同連不上，是因為後面根本沒有人在聽

預設位址 `ws://127.0.0.1:9002` 是 Rust 版 `padnote-relay` 監聽的埠，
但 App 從來不會去啟動那支程式，使用者手上也沒有可連的服務 ——
於是每次都停在「連線中斷，正在自動重新連線 (第 4/5 次)」。

改成由 App 自己提供中繼：`LocalRelayServer`（Network.framework 的
`NWListener` + `NWProtocolWebSocket`）在位址指向本機時自動啟動，
協定與 `crates/padnote-relay/src/hub.rs` 完全一致（第一位加入者為房主、
presence/oplog 轉發、最近 200 筆 oplog 供斷線追趕、房空自動回收）。

這不違反 D5。D5 說的是「我們不營運雲端後端」，不是「裝置不能開房間」——
發起協同的那台裝置當中繼點，資料仍然不經過任何我們的伺服器。
埠被占用時不當成錯誤：那通常代表已經有一個 `cargo run -p padnote-relay`
在聽，照常連過去就好。

順帶把失敗原因顯示出來。原本連不上只剩無聲的轉圈，使用者無從判斷是
位址錯、埠沒開、還是對方關機了。

### 圖釘對話框固定在圖釘旁邊，等於擋住要討論的東西

對話框原本用 `.position()` 釘在圖釘附近、完全不能移動 —— 而圖釘一定
就插在要討論的那塊內容上。加上標題列拖曳與「縮小成標題列」，
縮小後整條列仍可拖曳（縮小卻不能移動只是換個地方擋住畫面）。

### Mac 視窗標題看不到版本號

標題原本在 `onAppear` 裡 `DispatchQueue.main.async` 設一次。那個時間點
`connectedScenes` 可能還是空的（視窗場景尚未接上），設定就靜靜地掉了 ——
標題退回 App 名稱「Kairumo」。SwiftUI 的 `navigationTitle` 之後也可能覆蓋
`scene.title`。

改成 `MacWindowTitle`：場景還沒出現就短暫重試，並在場景／視窗／App
重新啟用時再確認一次，只有目前值不同才寫入（不會閃爍）。
順便把版本字串收斂成單一來源 `AppVersion` —— 先前三個檔案各自從
`infoDictionary` 撈，還各寫了不同的硬編碼 fallback（1.0.0 / 1.2.0 / 1.4.0），
版本一升級就互相對不起來。

驗證：實際建置 Mac Catalyst 版執行，用 `CGWindowListCopyWindowInfo`
讀回視窗標題為 `Kairumo v2.0.0`，等待數秒後仍未被覆蓋。

### 窄寬度的工具列：ViewThatFits 需要一個「一定塞得下」的候選

`ViewThatFits` 在所有候選都放不下時，會**無條件採用最後一個**，並以它的
理想寬度算繪 —— 於是工具列比視窗還寬、左右對稱被裁掉。iPad 直向與 iPhone
上「首頁」與「匯出與列印」直接消失，連退出筆記都做不到。

補上 `WrapLayout`（SwiftUI `Layout`）當最後一個候選：由左至右排、放不下就換行，
所以永遠有一個塞得下的版本。退讓順序刻意是「收文字標籤 → 收進『更多』選單 →
才換行」——換行會移動按鈕位置，是最後手段，不是第一選擇。

關鍵是**每顆按鈕都要是 Layout 的直接子視圖**：舊的 FlowLayout 版本把筆刷群組
包在 `HStack` 裡，那一整段變成單一子視圖，永遠不換行、照樣溢出。所以工具列
內容抽成 `@ViewBuilder` 的一串攤平項目，單行版與換行版共用同一份；
只有真的需要整組一起移動的（色盤、undo 群組）才刻意包成一個 `HStack`。

驗證：iPad 直向工具列換成兩行、iPhone 上主工具列兩行＋繪圖工具列四行，
所有按鈕都在畫面內；iPhone 維持側欄收合。

`max(視圖寬度, 800)` —— 在 Mac 上是 1500 左右，物件的 x/y 存的又是畫布座標，

底部畫一道漸層表示還有內容。物件在縮圖裡放大約 5 倍，且與畫布等比。

## 2026-09-12 (12) · 畫布物件、流程圖、工具列與六國語系（S-46 ～ S-50）

五項需求一次做完：物件自由排列、插入圖片與試算表圖形、流程圖範本、
工具列模組化、六國語系。

### 堆疊順序記「絕對索引」而不是「上移一層」

`SetZIndex` 存的是目標位置，不是相對動作。相對操作在無伺服器的 CRDT 下會疊加：
兩台裝置各按一次「移到最上層」，合併後誰也說不準結果。改成絕對索引後，
後到的 op 直接覆蓋，結果與套用順序無關。

移動**只在同層內**。跨層移動等於改變父子關係，那是 `Group`／`Ungroup` 的職責；
混在一起會讓「上移一層」偶爾把物件丟出群組，使用者完全無法預期。

### 連接線要「連」而不是「畫」

流程圖的價值在於線會跟著方塊走。把箭頭存成獨立線段，移動方塊時線就斷了 ——
那只是畫圖。因此 `Connection` 存的是「從哪個圖形的哪個連接點到哪個」，
路徑在渲染時才算。測試驗的也是這件事：移動後線的端點仍落在形狀邊緣上。

形狀用 ISO 5807 的標準語意（菱形＝判斷、平行四邊形＝輸入輸出），不自創圖形，
並把 `semantic()` 的說明帶到 UI —— 使用者看得懂符號才有意義。

### 試算表變成表格物件，而不是一段 Markdown 文字

原本 xlsx 匯入後變成兩個文字區塊（表名 + Markdown 表格）。那能看不能編：
改一格要去編輯一長串 `|` 分隔的文字。現在展開成 `BlockKind::Table`，
逐格編輯、整塊可搬動。

`SetTableCell` 逐格記錄而非整表覆寫 —— 整表覆寫會讓兩人同時編輯不同格時互相蓋掉。
`cells` 用扁平陣列而非巢狀 `Vec`：增刪欄只要 splice，巢狀結構容易出現長度不一致的列。

順帶把舊測試 `xlsx_becomes_a_markdown_table` 改寫成
`xlsx_becomes_an_editable_table_object` —— 它斷言的是舊契約，留著會擋住正確行為。

### 語系完整性交給型別系統

字串表若放在各平台的 `.strings` / `strings.xml`，就有五份要各自維護的表，
漏翻譯只有跑到那一頁才發現。放在 core 並以 `[&str; LOCALE_COUNT]` 表達，
**少一個語言就編不過**。

測試不只檢查「非空」，還檢查每個語言沒有偷懶照抄英文（重疊率 < 30%）、
日文有假名、韓文有諺文、泰文是泰文字母、繁簡至少有 15 個字不同。

1. `ToolGroup::Extras` 的標籤鍵指到 `Key::Record` —— UI 上整個「進階」分組

   數量守衛，這種看似笨拙的檢查真的會抓到東西。
2. `sibling_count` 一開始用 `draw_order().len()`，那是**整棵樹**的數量。

### 平台層真的碰得到

上一輪的教訓是「能力建在 core 裡卻沒開 FFI，等於沒建」。這次同批完成：
`ffi_shapes.rs`（形狀／連接線／範本）、`ffi_ui.rs`（語系／工具列）、

## 2026-09-12 (11) · 串流調查（S-32）

### 結論：改用段級串流，幀級串流需要重新匯出計算圖

原本以為要「重新匯出帶 cache 的 encoder」。查 FunASR 的原始碼才發現
**官方的串流 encoder 匯出本來就沒有 cache 輸入**：

```python
def export_encoder_input_names(self):
    return ["speech", "speech_lengths"]
```

串流是靠兩件事達成的：
1. 餵入帶重疊的特徵窗（`overlap_feats = cat(cache["feats"], feats)`，
   保留 `chunk_size[0] + chunk_size[2]` 幀）
2. decoder 的 16 個 cache 跨呼叫保留

我把兩者都實作了：`StreamingFrontend`（fbank 與 LFR 的跨塊邊界狀態）
與 `CifState`（跨塊的積分狀態，有測試證明分塊結果等同整段）。

**但幀級串流仍然不正確。** 實測不同的特徵上下文長度：

```text
整段處理      : 欢迎大家来体验达摩院推出的语音识别模型      ← 與 FunASR 吻合
幀級串流 ctx=5 : 嗯迎你迎来家来到看体验摩摩院推的的语音式模模式
幀級串流 ctx=15: 嗯迎你迎来家来到体验达摩院的的的音音频式识模式式
幀級串流 ctx=30: 嗯迎你迎大家来体验达摩院推的的语音式式模式
幀級串流 ctx=60: 嗯迎你迎大家来体验达摩院的的的音音音式模模式
```

加大上下文能緩解但無法解決。原因是 `online: True` 匯出的 encoder
把**分塊注意力遮罩的狀態封在計算圖內**，從外部餵特徵時它無從得知
自己處於哪一個分塊位置。

### 採取的作法
**預設段級串流**：`feed()` 只累積，`finish()` 才辨識。這與
`padnote-recorder` 天然契合 —— 它給的就是 VAD 切好的語音段。

延遲因此由 VAD 的 `MAX_SEGMENT_MS` 決定，已從 8 秒調到 **5 秒**。
這是取捨：太長延遲高、太短 ASR 上下文少。⚠️ 真正的甜蜜點要用 H2 的
中文測試集實測不同長度的 CER 後才能定。

幀級串流的基礎設施留著且有測試，等能匯出暴露分塊狀態的圖時可以直接接上。

### 為什麼不硬做
繼續加大上下文只是在猜，而且每次都要人工看輸出判斷好壞 ——
沒有 H2 的測試集，我無法量化「好一點」是真的好還是我在自我說服。

## 2026-09-12 (10) · 簡繁轉換與完整中文管線

### 做了什麼
463 → **487 個測試**。`padnote-text`（簡繁轉換）與
`padnote-core::transcript`（後處理管線），串起完整的中文鏈：

```
ASR 輸出 : 下周三下午三点在研讨室开会请大家准时参加
管線輸出 : 下週三下午三點在研討室開會，請大家準時參加。
```

### 為什麼這是必要的一步
Paraformer 與 ct-punc 都是**簡體模型**。在此之前整條管線的輸出是
沒有標點的簡體中文 —— 對台灣使用者等於不能用。

### 授權：差一點把 GPL 拉進來
`zhconv` 的 `Cargo.toml` 宣告 `license = "GPL-2.0-or-later"`。
直接 `cargo add zhconv` 會讓專案的 Apache-2.0 立場崩掉。

但讀 README 才發現那是因為**預設綁了 MediaWiki 的轉換表**：

> The library itself is licensed under MIT OR Apache-2.0 … BUT it may bundle
> conversion tables from MediaWiki … For MIT compatibility, disable the
> default `mediawiki` feature and enable `opencc`.

改用 `default-features = false, features = ["opencc"]` 後，綁的是 OpenCC 詞典
（Apache-2.0）。**而且品質取捨剛好相反**：OpenCC 表把「下周三」正確轉成
「下週三」，MediaWiki 表沒有。授權乾淨的選項同時也是比較好的選項。

### 兩個真實缺陷

**OpenCC 表在上下文中會誤判。**
「里面」單獨轉換是對的（→裡面），但在「代數里面」中，最長匹配先吃掉
「数里」，剩下的「面」被單獨轉成食物的「麵」。以專案維護的修正表補救，
**每一條修正都有測試**，且有反向測試確保不誤傷真正的「麵條」。

**逐詞轉換會失去詞組上下文 —— 這是測試抓到的。**
ASR 的詞多半是單字。「下」「周」「三」分開轉，「周」永遠不會變「週」，
因為那需要看到整個「下周三」。改成**整段轉換後再依字數分回各詞**；
字數改變時（少數詞彙替換會）退回逐詞轉換 ——
寧可少一點上下文，也不能讓時間戳錯位。

C1（點文字跳回錄音）完全依賴時間戳不變，這條不能妥協。

## 2026-09-12 (9) · 中文 ASR 與標點（S-24 / S-30）

### 做了什麼
411 → **463 個測試**。`padnote-punct-ct`（中文標點）與
`padnote-asr-paraformer`（fbank + LFR + CMVN + CIF + encoder/decoder）。

### 驗證方式：每一層都有獨立的真值來源
- **fbank**：用 FunASR 產生參考特徵，Rust 實作逐點比對（最大差異 <0.05）
- **CIF**：純數學，以 one-hot 幀追蹤每一幀的貢獻
- **整體**：用 FunASR 官方範例音檔比對 Python 與 Rust 的輸出

### 關鍵發現

**fp32 的輸出與 FunASR 完全吻合，證明管線正確。**
```
FunASR (fp32 PyTorch): 欢迎大家来体验达摩院推出的语音识别模型这ca
本實作 (fp32 ONNX)   : 欢迎大家来体验达摩院推出的语音识别模型
本實作 (int8 ONNX)   : 欢迎大家来体验达摩院推出的语音识别识别模型cia
```

**int8 量化明顯降低中文辨識品質。** 出現重複字（「识别识别」）與結尾雜訊。
進一步測試排除嵌入表（只量化 MatMul）得到**相同的劣化**，體積幾乎不變
（157.4 vs 157.6 MB）—— 問題出在量化 transformer 權重本身，不是嵌入表。
⚠️ 這是 **n=1 的觀察不是測量**，真正的取捨要等 H2 的測試集。

**匯出的 encoder 沒有 cache 輸入 —— 它不是真串流模型。**
一開始我按 0.6 秒切塊送進 encoder，輸出是
「嗯迎欢们大家来关注的来体验摩的的的的推一个语语音识模模一式型模型」——
每塊各自缺少上下文。改成整段處理後立刻正確。
幸好 `padnote-recorder` 給的就是 VAD 切好的語音段，天然符合這個模型的形態。

**FunASR 的 `dither=1.0` 讓特徵非確定性。**
同一段音訊兩次呼叫的特徵相差 0.27。轉錄結果必須可重現，因此前端關掉抖動。

**ct-punc 的詞表是簡體的。**
471,067 個 token 中僅 1.3% 是單字；繁體字（線、數、點）不在詞表內。
實測簡體 0/31 未知詞、繁體 3/18。因此管線順序必須是
**先標點、再轉繁體**，這不是實作細節而是正確性需求。

### 踩到的坑

- CIF 的測試期望算錯（alphas 總和 2.0 會發射兩次，我寫成一次）——
  實作是對的，測試是錯的
- `ort` 的混合型別輸入清單需要 `.into_dyn()`

## 2026-09-12 (7) · Silero VAD（S-26）

### 做了什麼
376 → **395 個測試**。`padnote-vad-silero`（ort + Silero v4）、
遲滯開關邏輯、接進 `NotebookSession` 與 FFI、修正 manifest 的壞 URL。

### 為什麼換掉 EnergyVad —— 有數字
白噪音（振幅與語音相當）餵進兩個 VAD，100 個音框：

```
EnergyVad 誤判 100 個為語音
Silero    誤判   0 個
```

能量門檻法在真實教室（冷氣、投影機風扇）等於完全不可用。

### 選型過程

**先試純 Rust 的 tract，失敗了（ADR-0005）。**
`tract-onnx` 無法載入 Silero —— v4 與 v5 都含 8k/16k 的條件分支，
兩個分支輸出秩不一致，`ToTypedTranslator` 直接失敗。這是 tract 的能力邊界，
不是設定問題。

改用 `ort` 其實是**更好的架構決定**：同一個執行期之後還要服務
Paraformer-zh（S-24）與 PP-OCRv5（D4），一套推論庫服務三個用途。

**遲滯邏輯與模型推論分離。**
`SpeechGate` 是純邏輯、零相依、完整可測。用單門檻會在機率貼近臨界時
來回跳動，把一句話切成碎片 —— 有測試明確驗證遲滯區間內零狀態切換。

**內部緩衝而非要求對齊。**
Silero v4 只吃 512 樣本，但 `Segmenter` 用 20 ms（320 樣本）。
讓 VAD 內部緩衝，呼叫端不必為了模型改變粒度。

**模型缺失時降級而非失敗。**
錄音不該因為 VAD 用不了就停擺（S-25 的音檔優先原則）。
`uses_neural_vad()` 讓 UI 能提示使用者分段品質會下降。

### 踩到的坑

**manifest 裡的 URL 從來沒被驗證過。**
原本 silero 指向的 HuggingFace 路徑需要登入，`curl` 拿到的是 29 bytes 的
`Invalid username or password`，副檔名還是 `.onnx`。
**清單裡沒被實際下載過的 URL 等於沒有。** 已改用官方 repo 並補上真實雜湊，
同時加測試要求「已填雜湊的項目不得仍標記授權待審」。

**`ort` 2.0-rc 的 API 與舊版差異大**：`session.inputs` 變成 `inputs()`、
`name` 變成 `name()`、`to_array_view` 變成 `try_extract_tensor` 回傳
`(shape, slice)` 元組。

## 2026-09-12 (6) · 錄音編排（S-25）

### 做了什麼
348 → **376 個測試**。`padnote-recorder`（管線 + 轉錄 worker）、
接進 `NotebookSession`、FFI 曝露、端到端整合測試、可執行的示範程式。

### 為什麼這樣做

**把「音檔優先落地」做成型別層次的保證，而不是註解裡的承諾。**
`RecordingPipeline` **完全不持有 `AsrEngine`** —— 想在 `feed()` 裡呼叫模型？
沒有那個欄位可以呼叫。這讓「轉錄拖慢錄音」與「轉錄失敗丟音訊」在結構上
不可能發生，而不是靠紀律維持。這正是 Notability 最大差評的解法。

**`feed()` 內的順序不可調換。**
先把音訊寫進 Opus 檔，再做 VAD 分段。VAD 或分段出錯時，音訊已經安全了。

**開檔先於記錄 session。**
顛倒的話，當機會留下「有 session 記錄但沒有音檔」的孤兒。

**佇列溢位丟最舊的段，但音檔照寫。**
ASR 完全跟不上時，掉的只是待辨識的副本；錄音本身不受影響，
而且 `segments_dropped` 會回報給 UI 提示換小模型。

### 踩到的坑

**實際跑一次才發現的回報缺陷。**
示範程式印出「音檔時長: 0 ms」—— 因為 `recorded_audio_us()` 讀的是 pipeline，
而停止錄音後 pipeline 已被取走。單元測試沒抓到，因為它們都在錄音中查詢。
改成累計保存並補上測試。**這就是為什麼要真的跑一次，而不只是跑測試。**

**`#[cfg(test)] impl` 放在 `mod tests` 之後會觸發 clippy 的
`items_after_test_module`。**

### 外部驗證
`cargo run -p padnote-core --example record_session` 產出真實的 `.padnote` 套件，
`ffprobe` 確認音檔為 `Duration: 00:00:03.00, opus, mono` —— 完整流程的產出
是任何播放器都能開的標準檔案。

### 仍未驗證
- VAD 目前是**能量門檻法**，有背景噪音時會把冷氣聲當語音（S-26 待換 Silero）
- 背景 worker 的低優先權執行緒尚未實作（S-27，屬平台層）
- 真實 ASR 品質仍待 H2 的中文測試集

## 2026-09-12 (5) · 文件持久化與原生相依

### 做了什麼
325 → **348 個測試**。文件 op-log 持久化（S-23）、Opus 音訊編碼（S-13）、
whisper.cpp ASR 引擎（S-15）、PDFium 適配層（S-21）。

### 為什麼這樣做

**S-23 的範圍比原本大。**
原本只要把文字 op 落盤，但一查才發現**頁面、區塊、錄音 session 從來沒有
持久化過** —— 只有筆畫會落盤。所以做成完整的 12 種 `DocOp` 與 `open()` 重播，
而不是只補文字那一塊。

**record() 先落盤再套用。**
反過來的話，中途當機會讓記憶體與磁碟不一致，使用者看到的是
「有效果但沒存到」—— 那比直接失敗更糟。

**先實測哪些原生相依能編譯，再決定要不要寫。**
pdfium-render、audiopus、whisper-rs 都先用 probe 專案試編。能編譯才動手，
避免寫完一堆無法驗證的程式碼。

**Opus 用 ffprobe 做外部驗證。**
自己寫的測試只能證明「跟我想的一樣」。`ffprobe` 回報
`Duration: 00:00:02.00, 32 kb/s, mono` —— granule 算錯的話時長會顯示成 1/3，
這是真正獨立的驗證。

### 踩到的坑

**UniFFI 會靜默略過名為 `open` 的建構子。**
`open` 是 Swift 的存取修飾關鍵字。Rust 端編譯正常、綁定產生正常，
但 Swift 端就是看不到那個方法。改名為 `open_existing` 並加測試釘住。
**這類無聲失敗是 FFI 最危險的地方。**

**PDFium 不是執行緒安全的。**
`Pdfium` 持有的綁定既非 `Send` 也非 `Sync`，連 `thread_safe` feature 也不足以
滿足我們 trait 的約束。改成每次操作重新綁定（dlopen 有快取，成本遠低於渲染）。
更重要的影響是：**多頁渲染無法平行化**，J2 的效能預算只能靠 `PageCache`
的預抓，不能靠開執行緒。

### 誠實標記
- Opus：**已驗證**（ffprobe 外部確認）
- 文件持久化：**已驗證**（往返測試涵蓋頁面/文字/錄音/索引/墓碑）
- whisper：**編譯與錯誤路徑已測，轉錄品質未驗證**（需模型 + 中文測試集）
- PDFium：**介面與邊界檢查已測，實際解析未驗證**（需 libpdfium 執行期庫）

265 → **299 個測試**。`padnote-doc::text`（CRDT + 二進位編碼）、

**綁定不進版控。**
與 core API 不同步的綁定比沒有更危險。改 `ffi.rs` 後跑
`scripts/generate-bindings.sh`，CI 也會驗證產得出來。

### 踩到的坑
- **併發插入的測試一開始就寫錯**：忘記讓兩端先套用自己的操作，

- `uniffi` 的 bindgen 需要 `features = ["cli"]`，否則 `uniffi_bindgen_main` 找不到
- `#[derive(uniffi::Object)]` 的結構仍受 `missing_debug_implementations` 檢查

經二進位編碼 → 加密 → SyncEngine → 本機資料夾 → 拉取 → 解密 → 解碼 → 套用，

「同位置併發輸入兩邊都保留」「磁碟上為密文」等迴歸測試。

## 2026-09-12 (3) · 引擎、模型與 PDF 層

### 做了什麼
205 → **265 個測試**。新增 `recognize::registry`（HWR fallback 鏈）、
`core::setup`（引擎與權限中心）、`padnote-models`（下載器）、
`padnote-pdf`（介面 + LRU 頁面快取），以及機器可讀的 `models/manifest.json`。

### 為什麼這樣做

**權限與引擎狀態機放在 core 而非各平台 UI。**
「錄音要不要麥克風權限」「轉錄缺哪個模型」若寫在 Swift，Android 版要重寫一遍，
兩邊必然長歪。core 判斷、UI 只負責畫。

**`Feature::CoreNotes` 的需求清單刻意是空的。**
手寫與打字不依賴任何權限或模型 —— 全新安裝、零權限的狀態下就該能用。
這是產品定位的基石，用測試把它釘住。

樂觀假設會讓功能在執行期才爆炸，那時已經來不及給使用者好的錯誤訊息。

填佔位雜湊看起來「完成度高」，但有人會誤以為可以出貨。現在的行為是
**下載器直接拒絕**，而且有測試確保它連網路請求都不發出。

**網路 IO 抽象成 `Fetcher` trait。**
續傳與驗證邏輯是最容易寫錯、又最難在真機上重現的部分。抽象掉之後，
「伺服器不支援 Range」「回傳空資料」「本機半檔比宣告還大」這些情境
全部可以離線測。

- `OpenOptions::create(true).write(true)` 未指定 `truncate` 會觸發 clippy 警告；
  續傳情境必須明示 `truncate(false)`，否則會毀掉既有進度
- `RenderKey` 用 f32 當 HashMap key 不可行，改存 ×100 的整數

的架構是否成立。而且它純軟體、當場可驗證，不像 S1 要等硬體。先殲滅可驗證的最大風險。

**筆畫不進 CRDT（ADR-0002）。**
一筆畫數百個點，全進 CRDT 會讓 op 爆炸。改用 append-only + 墓碑 —— 新增與刪除
天生可交換冪等，這正是收斂所需的全部性質，不需要完整 CRDT 的機制。

**刻意先不引入外部相依。**
M0 全程零 crates.io 相依，確保任何環境都能 build。等真正需要（serde/sha2）
才引入，且每個都要過 `deny.toml` 白名單。
