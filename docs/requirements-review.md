## 1. 跨平台 🟡

### 已涵蓋
架構上是保證的，不是靠紀律維持：業務邏輯全在 `padnote-core`（Rust），
UniFFI 已能產生 **Swift 與 Kotlin 綁定**（實際產出並通過 iOS SDK 語法檢查）。

`roadmap.md` M4 已含 Android（WP28）與 Windows/Linux Desktop（WP30）。

### 缺口
**Windows 的低延遲墨跡沒有設計。** Apple 走 CAMetalLayer、Android 走
`androidx.graphics.lowlatency`，Windows 對應的是 **Windows Ink / DirectInk**
或 DirectComposition 的低延遲路徑 —— 目前完全沒有對應方案。
Compose Multiplatform Desktop 走 Skia/JVM，**做不到 9ms 的墨跡延遲預算**。

**→ 建議**：Windows 的墨跡層需要原生實作（C++/WinRT 或 C# + Rust core），
不能沿用 Compose MP。列為 **S-35**。

## 2. 輸入準確度與壓感 🟡

### 已涵蓋
`InkPoint` 已保存 `pressure` / `tilt` / `azimuth` / 微秒時間戳，
且**存原始取樣點不做破壞性平滑**（ADR-0002），未來換演算法歷史筆記也受益。
壓感曲線刻意非線性（線性會讓輕壓幾乎看不見）。

### ✅ 已完成（S-36，2026-09-12）

原本這一項的五個缺口現在都有實作與測試（`crates/padnote-input`，33 條測試，
並已透過 `InkArbiter` 曝露給 Swift／Kotlin）：

| 項目 | 狀態 | 實作 |
|---|---|---|
| **掌拒** | ✅ | 多重訊號判定 + **回溯撤銷**（見下） |
| 手指 vs 觸控筆 | ✅ | `PointerKind`：Pen／Eraser／Finger／Mouse／Unknown |
| 滑鼠／觸控板 | ✅ | 特別處理：不受掌拒邏輯影響、永不被收回 |
| **懸停預覽** | ✅ | `Phase::Hover` + 位置回報，**並提前啟動掌拒** |
| 壓感觸發 | ✅ | `PressureAction` 五種可設定（決策 D-08） |

### 兩個關鍵設計

**回溯撤銷。** 使用者的自然動作是手掌先碰螢幕、筆才落下 ——
手掌那一筆此時已經在畫了。`Decision::retract` 讓筆落下（或**懸停**）時
能收回 500 ms 內開始的非筆筆畫。
沒有這個機制，掌拒只擋得住「筆之後」的誤觸，擋不住最常見的那一種。

**懸停時提前啟動掌拒。** 筆在螢幕上方時手掌往往已經貼上去了。
提前擋掉能讓回溯撤銷少被用到 —— **不畫出來再收回，比畫出來再收回好**。
某些裝置的懸停偵測不穩，因此這個行為可以關閉。

### 仍未涵蓋
| 項目 | 備註 |
|---|---|
| 慣用手偵測 | 左撇子的手掌在畫面另一側 |
| 書寫姿勢學習 | 依使用者習慣自動調整門檻 |
| **實機調校** | **所有門檻都是起點值**，需真實書寫驗證（併入 H1） |
| Apple Pencil 雙擊／擠壓 | 需 `UIPencilInteraction`（S-40） |

完整設計見 [`input-design.md`](input-design.md)。

## 4. UI/UX 🔴

**完全沒有開始。** 目前只有 `apple/InkSpike/` 的墨跡延遲驗證程式，
以及 `apple/Examples/SessionUsage.swift` 的 API 呼叫範例。

這不是疏漏 —— `roadmap.md` 的 M1 才進入 UI，而我們仍卡在 M0 的
S1（墨跡延遲實機量測）。但既然提出來了，**UI 設計可以與 M0 並行**，
因為它不依賴 S1 的結果。

**→ 建議**：新增 `docs/ui-design.md`，內容包含：
- 主要畫面的資訊架構（筆記本庫 / 編輯器 / 設定）
- 工具列的分組與收合行為
- GoodNotes 的哪些具體作法要學、哪些要避免（它的設定深度過深是常見抱怨）
- 深色模式、動態字級、VoiceOver（已列為 I8）

列為 **S-37**。

## 6. ⛔ 與 10 款競品格式完全相容 —— 以目前描述無法達成

這一項我必須明確說清楚，而不是含糊帶過。

### 為什麼做不到

**(a) 多數競品的格式是專有且未公開的**

| App | 格式 | 狀況 |
|---|---|---|
| Goodnotes | `.goodnotes` | ZIP 容器，內部為專有結構、版本間會變動，部分內容加密 |
| Notability | `.note` | 專有，未公開 |
| Samsung Notes | `.sdoc` / `.snb` | 專有 |
| Noteshelf | 專有 | 未公開 |
| Nebo | 專有 | 未公開，且只能存自家雲 |
| OneNote | `.one` | 有部分文件但極複雜 |
| Notion | — | **沒有本機檔案格式**，只有 API |
| Granola | — | **沒有本機檔案格式** |
| Apple Notes | SQLite + protobuf | 專有，在受保護的容器內 |
| Obsidian | **Markdown** | ✅ 開放 |

**(b)「彼此互通」需要對方也讀得懂我們的格式**

即使我們完美解析 Goodnotes 的檔案，**Goodnotes 也不會讀 `.padnote`**。
互通是雙向的，而另一半不在我們的控制範圍內。

**(c) 逆向工程專有格式有法律風險**

多數競品的服務條款禁止逆向工程。這與專案「乾淨授權」的立場衝突
（我們才剛為了 GPL 與模型授權做過兩次嚴謹稽核）。

### 可以做到的替代方案

**方案 A：以 PDF 作為通用交換格式** ⭐ 建議
**10 款競品全部都能讀寫 PDF 標註。** 這是唯一真正通用的交換途徑。
- 匯出：帶標註的標準 PDF（已列為 E3/H1）
- 匯入：PDF + 標註層（已實作 PDF 介面）

**方案 B：Markdown 雙向互通**
Obsidian 完全相容；Notion、OneNote 也都支援 MD 匯入匯出。
我們的 MD 匯出已實作，**MD 匯入未實作**。

**方案 C：單向、盡力而為的匯入**
針對少數格式做「盡力而為」的匯入（不保證完整、不保證未來版本）。
`features.md` 的 H5 已列為 P3。**但必須先確認各家服務條款是否允許。**

**方案 D：開放我們自己的格式**
`format-spec.md` 已公開發佈，任何人都能實作讀寫。這是我們能單方面做到的
「互通」——讓別人有機會讀我們，而不是反過來。

**→ 建議**：把需求改寫為「**以 PDF 與 Markdown 為主要交換格式，
並對主要競品提供盡力而為的單向匯入**」。列為 **D-09（需拍板）**。

## 7. Google 文件／Office 365／MD／JSON 🟡

### 目前狀態
- **Markdown**：匯出 ✅ 已實作；匯入 🔴 未實作
- **JSON**：`.padnote` 的 manifest 是 JSON，格式規格已公開；
  但「匯入任意 JSON」需要定義映射規則 🔴
- **Office（docx / xlsx / pptx）**：🔴 完全未實作
- **Google 文件／試算表／簡報**：🔴 完全未實作

### 工作量評估

| 格式 | 可行性 | 備註 |
|---|---|---|
| Markdown 匯入 | ✅ 容易 | 已有文件模型可映射 |
| JSON 匯入 | ✅ 容易 | 需先定義 schema 對應 |
| `.docx` | 🟡 中等 | 有 Rust crate（`docx-rs`）；純文字與基本樣式可行，複雜排版不行 |
| `.xlsx` | 🟡 中等 | `calamine` 可讀；但試算表要放進筆記本，**需先定義呈現方式** |
| `.pptx` | 🔴 困難 | Rust 生態缺成熟解析器；多半要自己解 OOXML |
| Google 三件套 | 🟡 中等 | 需 OAuth + Drive API 的 export 端點（可轉成 docx/pdf 再解析） |

⚠️ **Google 文件會引入新的外部依賴**：需要 Google Cloud 專案與 OAuth 審核，
與決策 D3 把 Google Drive 排到最後的理由相同。

⚠️ **試算表與簡報放進手寫筆記本，需要先回答產品問題**：
是嵌入為唯讀圖片？可編輯表格？還是轉成文字？這不是技術問題。

**→ 建議**：分兩階段。
- **階段一（可立即做）**：Markdown 匯入、JSON 匯入匯出 → **S-39**
- **階段二（需先拍板呈現方式）**：Office 與 Google → **D-10**

## 8. 手寫筆支援 🟡

### 目前狀態
| 筆 | 狀態 |
|---|---|
| Apple Pencil（1/2/Pro） | 🟡 已列為 I3（雙擊／懸停），資料模型支援壓感傾斜方位 |
| Samsung S Pen | 🟡 roadmap M4 提及，無設計 |
| Windows Ink（MPP / Wacom AES） | 🔴 未涵蓋 |
| 第三方藍牙筆（Adonit、Wacom Bamboo…） | 🔴 未涵蓋 |
| 一般被動式觸控筆 | 🟡 等同手指，需 §2 的掌拒 |

### 需要釐清的地方
**「WiFi 手寫筆」並不存在於主流產品中。** 目前市面上的主動式觸控筆走的是：
- **內建數位板協定**（Apple Pencil、S Pen、MPP、Wacom AES／EMR）——
  由作業系統直接提供事件，不需要配對
- **藍牙 LE**——通常只用來傳**按鈕事件與電量**，壓感仍走螢幕數位板

也就是說，「支援某支筆」多半等於「正確處理作業系統給的觸控事件」，
而不是「連上那支筆」。真正需要藍牙的只有按鈕與手勢。

**→ 建議**：需求改寫為「**完整支援各平台原生的數位板協定，
並支援藍牙筆的按鈕與手勢事件**」。列為 **S-40**，
並在 `docs/input-design.md` 一併設計。
