# ADR-0015：筆跡單一真相 —— 每一筆都是事件，畫布、縮圖、雲端只讀同一份

> 狀態：**提議**（2026-10-31），等待拍板後分階段實作
> 相關：ADR-0002（筆畫不進 CRDT、append-only 串流）、ADR-0011（Drive appDataFolder 同步）、
> `apple/Sources/PageInkStore.swift`、`StrokeDelta.swift`、`InkSyncLedger.swift`、`ProInk.swift`、
> `NotebookSyncCoordinator.swift`、`android/.../ink/InkEngine.kt`

## 背景：為什麼同一類問題一修再修

使用者反覆回報四件事：**擦掉的筆跡又出現**、**畫布與預覽頁顯示不同**、**別台看不到剛寫／剛擦的**、
**時好時壞**。每一次都找到一個具體原因並修掉，但下一次又以另一條路徑出現。原因不在任何一行程式，
而在架構：

### 1. 一頁筆跡在 iPad 上同時有十幾份「真相」

| 位置 | 內容 | 誰寫 |
|---|---|---|
| `PKCanvasView.drawing` | 畫面上的 PencilKit 筆畫 | PencilKit、程式指派 |
| `PageInkStore.inMemoryDrawings` | 「權威」記憶體副本 | 編輯、合併 |
| `continuousCanvases` 快取 | 連續模式的副本 | 連續模式 |
| `NotebookStore.drawingCache` | 讀檔快取 | 存檔、讀檔 |
| `<id>_p<n>.drawing` | 磁碟副本（以**頁碼**為鍵） | 存檔、同步匯入 |
| `.padnote/ink/<page>.strokes` | 核心 append-only 串流 | 增量寫入、匯出 |
| `inkDiskBaselines` / `coreBaselines` | 合併與寫入用的兩種基準線 | 各自的時機 |
| 同步基準線（別台的部分） | 匯出時扣掉 | 匯入 |
| `ErasedInkLedger` | 這台擦掉的 PencilKit 筆畫（內容指紋） | 寫入套件時比對 |
| `PKInkSnapshotStore` | 上次匯出時自己的筆畫 | 匯出 |
| `.proink.json` / `.proink-foreign.json` | 專業筆畫（自己的／別台的） | 編輯、匯入 |
| `.proink-suppressed.json` | 擦掉的別台專業筆畫 | 擦除 |
| `.proink-ledger.json` | 退休、已匯出、墓碑…… | 編輯、匯出 |
| 縮圖快取 | 以「筆畫數＋外框」推測內容 | 側欄 |

每一份都要靠通知、重讀、時間戳與比對才能跟其他份保持一致。**任何一條路徑漏掉一份，畫面就分歧。**

### 2. 「刪除」不是一個事件，而是事後比對兩份快照推論出來的

使用者擦掉一筆時，iPad 端沒有任何地方記下「刪除了 id=X」。刪除要等到稍後寫入套件時，
拿「現在」跟某一條「基準線」比對才推論得出。基準線被清掉（同步匯入、切換模式時都會清）、
過期、或比對時序不對，刪除就**永遠不會被記下** —— 套件裡沒有墓碑，下一次匯入就把它帶回來。
這是「擦掉又出現」反覆發生的根源。本輪找到並修掉的三條路徑都是同一個形狀：

1. 套件基準線在同步匯入後被清空，之後擦的筆畫不再寫進「已擦除」名單。
2. 合併基準線在合併**之前**被清空，這台剛擦、還沒寫出去的筆畫被磁碟上的舊內容帶回來。
3. 專業筆畫擦掉後、墓碑匯出前遇到一次匯入，被當成「別台的筆畫」寫回 foreign 檔。

### 3. 身分靠內容指紋

PencilKit 的 `PKStroke` 沒有 id，現在用「點列雜湊」當身分。同樣的筆畫畫兩次是同一個身分；
改顏色、搬動就是「刪除＋新增」；不同版本 PencilKit 編解碼的細微差異會讓同一筆變成兩筆。

### 4. 同步搬的是「整份快照」，判斷靠檔案時間

匯出把整份工作副本打包、上傳；匯入把整份套件 materialize、寫回十幾個檔案，再以修改時間判斷
「誰比較新」。這造成延遲（去抖動 0.4–1.5 秒＋匯出週期）、互推（匯入讓檔案變新又觸發匯出），
以及大量「先寫還是先讀」的時序問題。

### 5. 兩個平台是兩套模型

Android 的 `InkEngine` 直接把筆畫寫進核心的 append-only 串流（擦除寫 `Remove` 墓碑，ADR-0002），
iPad 卻以 PencilKit 的 `PKDrawing` 為主，核心只是「匯出目標」。同一個操作在兩邊走完全不同的路，
行為自然不一致。

## 決策

**核心的 append-only 筆跡串流（ADR-0002）成為兩個平台唯一的真相。每一個使用者動作在發生的當下就變成
一筆事件寫進去；畫布、縮圖、匯出、同步全部只讀它的 materialize 結果。**

### 不變式（每一條都要有自動化測試守著）

- **I1 唯一真相**：一頁的筆跡＝該頁事件串流的 materialize 結果。其他任何副本都只是它的快取，
  可以隨時丟掉重建，且以「版本號」判斷新舊，不以內容推測、不以檔案時間推測。
- **I2 事件即時落地**：新增、擦除、搬動、改色、復原在使用者動作完成的當下產生事件
  （`Add` / `Remove` / `Replace`），以穩定 id 指向筆畫，寫入本機串流（背景佇列，主執行緒不等）。
  **不靠事後比對推論。**
- **I3 墓碑優先**：被 `Remove` 的 id 永遠不會再被同一個 `Add` 帶回來（與到達順序無關）。
  復原刪除＝以**新 id** 再 `Add` 一次，不是撤銷墓碑。
- **I4 同一份畫面**：畫布、側欄縮圖、匯出、搜尋都讀同一個 materialize 結果與它的 `revision`。
  縮圖的快取鍵就是 `(pageId, revision)`。
- **I5 同步搬事件**：雲端放的是每台裝置自己的事件區塊（ADR-0011 的 `sync/<device_id>/`），
  匯入＝把別台的事件併進本機串流（交換律、冪等），之後走 I4 —— 沒有「整份覆蓋」、沒有修改時間判斷。
- **I6 兩個平台同一個模型**：Apple 與 Android 都呼叫同一組核心 API；平台只負責輸入與繪製。

### 結構

```
            使用者動作（落筆／擦除／套索／復原）
                          │  當下產生事件（穩定 id）
                          ▼
   ┌────────────── 核心 InkLog（每頁 append-only） ──────────────┐
   │  Add / Remove / Replace，帶 device_id + HLC 時戳             │
   │  materialize() → [Stroke]、revision（每次變動 +1）          │
   └──────┬───────────────────┬────────────────────┬─────────────┘
          │ 訂閱 revision      │ 本機新事件           │ 別台事件
          ▼                   ▼                    │
   畫布／縮圖／匯出      同步：推送自己的事件區塊 ──→ 雲端 ──→ 拉取併入
```

### 平台端

- **Android**：已經大致是這個模型。要補的是：縮圖與畫布統一讀 `revision`；同步改為事件區塊。
- **Apple（主要工作量）**：
  1. **筆畫 id**：每一筆在建立時發一個 UUIDv7。PencilKit 筆畫以側表對應
     （`PKStroke.path.creationDate` + `randomSeed` → id），在 `canvasViewDrawingDidChange`
     當下比對「上一個畫面」與「這一個畫面」（不是磁碟、不是基準線）產生事件 —— 本輪的
     `recordErasures` 已經是這個做法的雛形。
  2. **移除副本**：`PageInkStore`、`.drawing` 檔、兩種基準線、`ErasedInkLedger`、
     `PKInkSnapshotStore`、`.proink*.json` 全部由 InkLog 取代；舊檔只在遷移時讀一次。
  3. **專業筆刷與 PencilKit 同一條串流**：專業筆畫已經是自繪、有 id，直接寫事件即可。
  4. **長期**：把 PencilKit 筆刷也改由自繪引擎繪製（與 Android 同一套筆點陣），
     PencilKit 只留作輸入與預測。兩個平台的筆跡從此逐像素相同。這一步可以晚做，不阻擋 1–3。

### 同步

- 每台裝置只寫自己的事件區塊：`sync/<device_id>/ink/<notebook>/<seq>.chunk`（加密、壓縮）。
- **推**：本機有新事件後 300 ms 內打包上傳（Drive 沒有 append，ADR-0011 已決定以新增區塊退化處理）。
- **拉**：以 Drive changes token 輪詢（前景 5–10 秒；有協同連線時由 relay 即時推送同一種事件）。
- **併**：每台裝置一個游標（已處理到第幾個區塊），重複併入不會有副作用。
- 協同（relay）送的也是同一種事件 —— 現在協同與檔案同步是兩套筆跡格式，之後合成一套。
- 「即時」的上限因此是：本機 ≤ 1 幀；別台 ≈ 上傳延遲＋輪詢間隔（協同中為網路延遲）。

## 遷移計畫（每一階段都可單獨上線，前一階段的不變式測試要先綠）

| 階段 | 內容 | 驗收 |
|---|---|---|
| 0（本輪已做） | 止血：刪除在編輯當下記錄、合併不清基準線、匯入濾掉未匯出的墓碑、縮圖以版本號為鍵、匯入後重讀記憶體副本 | 下方「本輪修正」 |
| 1（已做） | 核心事件 API（`apply_ink_events`）、版本號（`ink_version`）；移除違反不變式的整頁重寫與筆跡壓實 | 核心不變式測試：3 台裝置 × 20 組亂數種子收斂且零復活；維護後同步不復活；版本號 |
| 2（已做） | Apple 編輯路徑在當下寫事件；匯出不再重建本裝置筆畫檔、改為只追加的補齊 | 單元測試：擦除當下生效、原作者重新匯出不復活、復原擦除兩台都回來；同步整合測試 |
| 3（暫不做，見下方決定） | 同步改為事件區塊；舊套件匯入一次轉成事件 | 多裝置模擬：3 台隨機寫擦 1000 次後內容一致、零復活 |
| 4（延後到舊版退場，見下方決定） | 移除舊副本與帳本檔、清理遷移程式 | 檔案清單只剩 InkLog 與快取 |
| 5（可選，另立案） | Apple 全面自繪筆刷 | 兩平台同一筆逐像素比對 |

### 要寫進 CI 的不變式測試

- **擦掉不復活**：擦除 → 立刻匯入一份含該筆的舊套件 → 該筆不存在（核心與兩平台各一）。
- **收斂**：N 台裝置、隨機的新增／擦除／復原、隨機的同步順序與重複 → 所有裝置 materialize 結果相同。
- **畫面一致**：每次編輯後，畫布筆畫集合＝縮圖所用的筆畫集合＝重開筆記後的集合。
- **即時性**：本機事件寫入 ≤ 16 ms（主執行緒 0 等待）；推送在 300 ms 內排入上傳。

## 後果

- 好處：刪除、新增不再需要推論；畫面只有一份來源；同步不再依賴檔案時間；兩平台行為一致；
  「時好時壞」的時序問題整類消失（每個副本都只是快取）。
- 代價：Apple 端的編輯與同步路徑要大幅改寫（`NotebookSyncCoordinator`、`StrokeDelta`、
  `InkSyncLedger`、`ProInk` 的帳本部分）；需要一次性資料遷移；舊版 App 讀不懂新的事件區塊，
  遷移期間需要相容層（新版同時寫舊格式一個版本週期）。
- 風險：PencilKit 側表 id 在極端情況（系統改寫筆畫、複製貼上）可能對不上 —— 對不上時視為
  「刪除舊 id＋新增新 id」，結果仍正確，只是事件多一筆；第 5 階段後此風險消失。

## 第 1 階段的發現與實作（2026-10-31）

盤點後確認：核心早已是 ADR-0002 的事件串流 —— 每頁每台裝置一個 append-only 檔
（`ink/<page>-<device>.strokes`），`Add`／`Remove`，`materialize` 墓碑優先、與順序無關；
Android 直接寫它。所以第 1 階段不是「新建 InkLog」，而是**補齊 API、拿掉核心裡違反不變式的兩處**：

- **筆跡壓實會讓擦掉的筆跡復活（兩個平台）。** `optimize_storage` 把一頁所有裝置的記錄
  materialize 後寫回本裝置的檔案、**丟掉全部墓碑、刪掉別台的檔案**。iPad 的 `StorageJanitor`
  每天自動跑、Android 的維護也會呼叫。之後任何一台的檔案同步回來，被擦掉的筆畫就沒有墓碑擋著 ——
  這是「擦掉過一陣子又出現」在兩個平台都會發生的核心層原因。→ **停用筆跡壓實**；回收要等第 3 階段
  有各裝置游標之後才能安全地做。
- **插入垂直空白整頁重寫，並刪除別台的檔案。** 搬過的筆畫沿用舊 id，別台檔案同步回來後同一個 id
  有兩個 `Add`，取到哪個看檔名排序；被擦掉的筆畫也一起復活。→ 改為「擦掉舊 id＋以新 id 加入」，
  只追加在自己的檔案。`rewrite_ink_page` 已移除，核心裡不再有任何會刪除別台檔案或丟掉墓碑的路徑。
- **新 API**：`PadnoteSession.apply_ink_events(page, removedIds, added)`（一個動作的事件一次追加）、
  `PadnoteSession.ink_version(page)`（所有裝置筆畫檔的指紋；任何新增、擦除、同步進來都會改變）。

### 第 2 階段的具體做法（下一步）

1. Apple 編輯路徑在 `recordDrawingEdit` 當下（本輪已有的 `recordErasures` 位置）算出事件，
   在寫入佇列上呼叫 `apply_ink_events`：擦掉的 → 其套件 id 的墓碑；新增的 → 以穩定 id 加入。
   PencilKit 筆畫的套件 id 先沿用現在的內容 id／`CollabInkIds` 對照（`PKStrokeId`），
   日後換成建立時發的 UUIDv7。
2. 匯出不再整份重建本裝置的筆畫檔（`exportPreservingOtherDevices` 刪除本裝置舊檔再寫新檔的那段）：
   筆畫已經在編輯當下寫進去了，匯出只處理文件 oplog 與附件。`PKInkSync.plan`、`ErasedInkLedger`、
   `PKInkSnapshotStore`、專業筆畫帳本的退休／墓碑邏輯隨之退場。
3. 畫布與縮圖改讀 `ink_version`，`PageInkStore` 只剩「記憶體快取」角色。

## 第 2 階段的實作（2026-10-31）

- **`InkEventSink`**（每個編輯器一份，以筆記本 id 登記）：畫布與專業筆畫層把動作交給它，在核心寫入佇列上
  （與 `CoreInkFlush` 同一條序列）寫進套件。
  - **畫布**：以 `lastSyncedDrawing`（畫布上一刻**真正顯示**的那一份）為基準比對。不用編輯器的記憶體副本 ——
    同步進來的別台筆畫在落筆中先進記憶體、抬筆後才換上畫布，拿記憶體比對會把使用者還沒看到的筆畫當成
    「這台擦掉的」寫出墓碑。擦掉的 → `eraseInk`（依內容找到套件 id 寫墓碑）；加回來的 → `reviveInk`。
  - **專業筆刷**：`persist` 與上一次存檔比對；新增 → 加入；消失 → 墓碑；**內容改了（搬動、改圖層）→
    擦掉舊 id、以新 id 加入**。擦掉別台的專業筆畫當下寫墓碑。
- **匯出不再重建本裝置的筆畫檔**：`exportPreservingOtherDevices` 不刪、不覆蓋 `ink/`；改以
  `reconcileOwnInk` 只追加缺的：帳本的墓碑、上次匯出後擦掉的自己的筆畫（`PKInkSnapshotStore` 比對）、
  套件裡還看不到的新筆畫。筆畫檔從此只會變大，補位（`pad_ink_to`）不再需要。
- **「寫過就不再寫」規則**（`PKStrokeId.wasWritten`）：一筆的任何身分曾經寫進套件，就不能只憑「工作副本裡有它」
  再寫一次 —— 它有墓碑時，可能是別台擦的、這台還沒匯入，再寫就是救活。只有確定是使用者加回來的
  （畫布上一刻沒有、這一刻有；或上次匯出之後才出現）才以新世代的身分寫入。
- 修掉 `PKInkSnapshotStore.save` 在資料夾不存在時**無聲失敗**（`try?`）：之前「上次匯出寫出了什麼」可能根本沒記下來。

### 第 2 階段收尾（2026-10-31）

- **編輯器自己的動作也在當下寫事件**：套索刪除、搬動、剪下、跨頁搬移等走 `recordDrawingEdit` 的動作，
  由 `InkEventSink.editorEdited` 寫事件；**只有那一頁畫布上一刻顯示的筆畫才會被寫成墓碑**（測試：
  `testEditorEditsOnlyEraseStrokesTheUserCouldSee`）。來自畫布的編輯已由畫布寫過，這裡比對不出擦除，不重複。
- **擦除、專業筆刷事件寫入後立即通知焦點通道推送**（`FocusSyncController.noteLocalEdit`），不必等下一次落筆。
- **移除已失效的補位機制**（`minInkBytes`、`growInkFiles`、匯出時的 `padInkTo`）：筆畫檔只會追加、本來就只會變大。

## 階段 3–5 的決定（2026-10-31）

實作完第 1、2 階段後重新評估，以下三項**刻意不照原計畫做**，理由寫在這裡，之後若前提改變再回頭：

- **第 3 階段「同步改為事件區塊」——目前不需要。** 原計畫的目的是讓同步搬「事件」而不是「快照」。
  第 1、2 階段之後，每台裝置的筆畫檔已經是**只追加、永不重寫**的事件串流，「同步只傳較大的檔案」對只追加的檔案
  而言就是「傳新的事件」；匯入一律經過 `materialize`（墓碑優先、與順序無關）。正確性的前提都已成立。
  切成區塊只省頻寬（一頁的筆畫檔通常只有幾十 KB），換來的是新的雲端格式、遷移與相容層 —— 目前不划算。
  若日後單頁筆畫檔大到同步明顯變慢，再以「檔案尾端增量上傳」或區塊化處理。
- **第 4 階段「移除舊帳本」——保留為保險與相容層。** `PKInkSync.plan`（別台筆畫的墓碑）、`ErasedInkLedger`、
  `PKInkSnapshotStore`、專業筆畫的退休記錄仍在用：(1) 匯出時的補齊以它們為依據，涵蓋事件寫入失敗或
  未經編輯器的改動；(2) **使用者手上還有舊版 App 的裝置**會繼續整份重建自己的筆畫檔，別台筆畫墓碑的自動清理
  與內容指紋對照仍需要它們。等所有裝置都升級（以最低支援版本控管）後再移除。
- **第 5 階段「Apple 全面自繪筆刷」——不在本輪範圍。** 這是把 PencilKit 的鋼筆、原子筆等改由自繪引擎繪製，
  牽涉筆觸外觀、壓感手感、效能與既有筆記的外觀變化，需要另外立案、做外觀比對與實機手感驗證。
  它解決的是「兩平台逐像素相同」與「PencilKit 筆畫沒有 id」，不是本 ADR 要解決的同步正確性問題。
- **畫布與縮圖讀 `ink_version` ——改用等價做法。** 縮圖以 `PageInkStore` 版本號＋專業筆畫版本號為鍵、
  同步匯入後重讀記憶體副本（階段 0），已滿足 I4。每次重畫縮圖都開套件讀 `ink_version` 反而更慢。
  `ink_version` 保留給平台需要「不開編輯器也判斷某頁變了沒」的場合（例如列表縮圖快取）。

### 仍需人工驗證

- 兩台（或以上）實機：擦掉別台的筆畫、復原擦除、套索搬動、專業筆刷改圖層，同步數輪後內容一致且不復活。
- 舊版 App 與新版混用的過渡期：舊版整份重建筆畫檔時，新版寫下的墓碑仍然有效（墓碑在新版自己的檔案裡）。
