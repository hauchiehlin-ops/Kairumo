# 輸入設計：掌拒、輸入分流與壓感

> 工作項 S-36　|　決策 ADR-0007（D-08）　|　實作 `crates/padnote-input`
> 日期：2026-09-12

---

## 1. 為什麼這件事排在 UI 之前

手寫 App 若沒有掌拒，使用者把手掌靠在螢幕上寫字會畫出大片塗鴉。
**這是產品的生死線，不是體驗優化。** 再漂亮的 UI 也救不了一個
「一寫字就亂畫」的 App。

---

## 2. 分層：平台只轉換，core 做判斷

```text
平台原生事件 ─▶ PointerEvent ─▶ PointerArbiter ─▶ Decision
（UITouch /                （統一格式）      （Rust core）    { verdict, retract }
 MotionEvent /
 PointerRoutedEventArgs）
```

平台層**只做一件事**：把原始事件轉成 `PointerEvent`。
分類與採納由 `PointerArbiter` 決定。

**為什麼判斷不放平台層**：掌拒的判準是靠真實使用調出來的經驗值，會不斷修改。
邏輯若散在 Swift 與 Kotlin，兩邊必然長歪，而且**無法寫測試** ——
偏偏這種靠經驗值調的東西最需要迴歸測試。目前 26 條測試全部釘在 core。

---

## 3. 掌拒的判準

依強度排序，先命中先決定：

| 順位 | 訊號 | 判定 | 理由 |
|---|---|---|---|
| 1 | 平台說這是筆（`UITouch.type == .pencil`） | **Draw** | 最強訊號，直接採信 |
| 2 | 滑鼠 | Draw／Gesture | 不會有手掌問題 |
| 3 | 接觸半徑 > 22 點 | **Reject** | 筆尖 1–3、指尖 8–15、手掌側緣 > 25 |
| 4 | 筆正按著，或剛抬起 300 ms 內 | **Reject** | 手掌通常比筆**晚**離開螢幕 |
| 4b | **筆懸停在上方** | **Reject** | 筆在上方時手掌往往已經貼上去了 |
| 5 | 僅筆模式 | Gesture | 使用者還是要能捲動，不是完全忽略 |
| 6 | 同時 ≥2 根手指 | Gesture | 縮放／平移 |
| 7 | 其餘 | Draw | |

### 接觸半徑未知時不判手掌
平台不提供面積時填 `0`。**不能因此把所有觸控都當手掌** ——
那會讓不回報面積的裝置完全無法書寫。

---

## 4. 最難的情況：手掌先落、筆後落

使用者的自然動作是**手掌先碰到螢幕，筆才落下**。此時手掌那一筆已經開始畫了。

```text
t=0ms    手掌接觸  → 當下無從得知，判 Draw（已經開始畫）
t=200ms  筆落下    → 判 Draw，同時回收 { retract: [手掌的 id] }
```

因此 `Decision` 帶 **`retract` 欄位**：筆落下時，回溯撤銷 500 ms 內開始的
非筆筆畫。

**沒有這個機制，掌拒只能擋住「筆之後」的誤觸 —— 擋不住最常見的那一種。**

### 時間窗的取捨
- 太短：擋不住手掌先落
- 太長：會收回使用者真正想用手指畫的內容

500 ms 是起點值。⚠️ **真正的甜蜜點要用實機觀察真實書寫姿勢後調整**，
這也是為什麼判準要有測試 —— 調整時才不會弄壞其他情況。

---

## 4b. 懸停：提前啟動掌拒

`Phase::Hover` 有兩個用途：

1. **落筆預覽** —— `hover_position()` 回報筆尖會落在哪，UI 畫游標
2. **提前啟動掌拒** —— 筆懸停時就收回可疑筆畫，不必等它落下

第二點的價值在於：**不畫出來再收回，比畫出來再收回好。**
回溯撤銷會讓使用者看到筆跡閃一下再消失；提前擋掉則完全不會出現。

某些裝置的懸停偵測不穩（誤報或延遲），因此
`palm_reject_on_hover` 可以關閉。

手指的「懸停」在多數平台不存在，就算有也不觸發預覽。

## 5. 書寫中改判

手掌落下時可能只碰到一小塊，壓平後面積才變大。因此 `Moved` 階段
仍會檢查接觸面積，超過門檻就改判並回收已畫的部分。

反之，**已採納的觸控不會因為其他原因中途改判** ——
那會讓筆畫斷成兩截。

## 6. 壓感語意（ADR-0007 / D-08）

使用者可設定按壓深度要觸發什麼：

| 選項 | 說明 |
|---|---|
| **線寬**（預設） | 壓感調變粗細 |
| 濃度 | 壓感調變透明度 |
| 線寬 + 濃度 | 兩者同時 |
| 快顯工具列 | 重壓（≥0.85）叫出工具列 |
| 關閉 | 固定線寬 |

**為什麼預設是線寬**：那是使用者對「筆」的既有預期。
把重壓綁到叫工具列會讓用力寫字的人不斷誤觸。

### 壓感曲線
線性映射會讓輕壓幾乎看不見筆跡，手感很差。曲線把可用範圍往上抬：

```text
輸出 = floor + (1 - floor) × 壓力^gamma      floor = 0.35, gamma = 1.0
```

`gamma < 1` 讓輕壓更敏感，`> 1` 讓重壓更明顯 —— 兩者都開放給使用者調。

## 7. 各平台的事件來源

| 平台 | 來源 | 筆的辨識 | 接觸面積 |
|---|---|---|---|
| iOS / iPadOS | `UITouch` | `type == .pencil` ✅ | `majorRadius` ✅ |
| macOS | `NSEvent` | 觸控板／滑鼠 | 部分 |
| Android | `MotionEvent` | `TOOL_TYPE_STYLUS` ✅ | `getSize()` / `TOUCH_MAJOR` ✅ |
| Windows | `PointerRoutedEventArgs` | `PointerDeviceType.Pen` ✅ | `ContactRect` ✅ |

四個平台都提供筆的分類與接觸面積 —— 這是判準能跨平台成立的前提。

## 8. 手寫筆支援的真相（S-40 的前提）

**「WiFi 手寫筆」在主流產品中不存在。** 主動式觸控筆走的是：

- **內建數位板協定**（Apple Pencil、S Pen、Microsoft MPP、Wacom AES／EMR）
  → 壓感、傾斜、方位由**作業系統直接提供**，不需要配對
- **藍牙 LE** → 通常只傳**按鈕事件與電量**

也就是說「支援某支筆」多半等於「正確處理 OS 給的觸控事件」，
而本文件的 `PointerEvent` 已經涵蓋。真正需要額外工作的只有：

| 項目 | 需要做的事 |
|---|---|
| Apple Pencil 雙擊／擠壓 | `UIPencilInteraction` |
| S Pen 按鈕與空中手勢 | Samsung SDK |
| 藍牙筆的按鈕 | 各家 SDK（Wacom、Adonit…），優先序低 |
| 懸停預覽 | ✅ core 已實作；平台層需把 hover 事件轉成 `Phase::Hover` |
